## Purpose

Хранит PDF-квитанции на оплату по лицевым счетам и месяцам и позволяет опубликовать, перечислить и скачать их через API.

## Requirements

### Requirement: Хранение квитанций
Система SHALL хранить для каждой квитанции запись с лицевым счётом, месяцем (`ГГГГ-ММ`), ключом файла, размером в байтах, контрольной суммой SHA-256, датой публикации, признаком `is_test`, а также необязательными суммами капитального ремонта и коммунальных услуг с источником и временем их записи (требование «Суммы квитанции»). На сочетание «лицевой счёт, месяц» MUST приходиться не более одной квитанции. Содержимое файла MUST NOT храниться в БД, а храниться в файловом хранилище по ключу. Признак `is_test` квитанции SHALL совпадать с признаком её лицевого счёта.

#### Scenario: Запись о квитанции
- **WHEN** для счёта `000000000001` опубликована квитанция за 2026-10
- **THEN** в БД есть запись с этим счётом, месяцем `2026-10`, ключом файла, размером и SHA-256 файла, а в таблице нет содержимого файла

#### Scenario: Вторая квитанция за месяц
- **WHEN** в БД добавляется вторая запись для того же счёта и месяца
- **THEN** хранилище отклоняет добавление

#### Scenario: Квитанции разных месяцев и счетов
- **WHEN** публикуются квитанции за 2026-09 и 2026-10, а также за 2026-10 для другого счёта
- **THEN** все записи сохраняются

### Requirement: Публикация квитанции
Система SHALL предоставлять эндпоинт `PUT /api/accounts/{number}/receipts/{month}`, принимающий тело `application/pdf` и сохраняющий его как квитанцию счёта за месяц `{month}` (формат `ГГГГ-ММ`). Публикация разрешена в двух случаях: запрос содержит заголовок `X-Admin-Token` со значением из конфигурации `receipts.admin-token` (сравнение MUST быть устойчивым к атакам по времени), либо запрос содержит действительный токен входа пользователя с ролью `ADMIN`. Во всех остальных случаях ответ `403`, ничего не сохраняется. При успехе эндпоинт SHALL вернуть `201` для новой квитанции и `200` при замене существующей, с JSON `{month, size, sha256, published_at}` (имена в `snake_case`, без ключа файла и идентификаторов). Повторная публикация за тот же месяц MUST заменять файл, при этом старый файл удаляется после успешного сохранения нового.

#### Scenario: Новая квитанция
- **WHEN** администратор отправляет PDF на `PUT /api/accounts/000000000001/receipts/2026-10` с верным токеном
- **THEN** ответ `201`, в теле месяц `2026-10`, размер и SHA-256 отправленного файла, квитанция появляется в списке и скачивается

#### Scenario: Замена квитанции
- **WHEN** администратор повторно отправляет другой PDF за тот же месяц
- **THEN** ответ `200`, скачивание отдаёт новый файл, а старый файл удалён из хранилища

#### Scenario: Неверный или отсутствующий токен
- **WHEN** запрос отправлен без заголовка `X-Admin-Token` или с неверным значением и без токена входа администратора
- **THEN** ответ `403`, ничего не сохранено

#### Scenario: Токен не настроен
- **WHEN** значение `receipts.admin-token` не задано и запрос не содержит токен входа администратора
- **THEN** публикация отклоняется ответом `403`

#### Scenario: Публикация администратором по токену входа
- **WHEN** пользователь с ролью `ADMIN` отправляет PDF с заголовком `Authorization: Bearer <токен входа>` и без `X-Admin-Token`
- **THEN** ответ `201`, квитанция сохранена

#### Scenario: Администратор при ненастроенном токене
- **WHEN** значение `receipts.admin-token` не задано, а PDF отправляет `ADMIN` с токеном входа
- **THEN** ответ `201`

#### Scenario: Собственник и жилец
- **WHEN** пользователь с ролью `OWNER` или `RESIDENT` отправляет PDF с токеном входа, но без верного `X-Admin-Token`
- **THEN** ответ `403`, ничего не сохранено

#### Scenario: Недействительный токен входа
- **WHEN** запрос содержит просроченный или подделанный токен входа
- **THEN** ответ `401`, даже если `X-Admin-Token` верный

### Requirement: Проверка загружаемого файла
Публикация SHALL отклонять файл, который не является PDF (содержимое не начинается с `%PDF-`) — ответом `400`, пустое тело — ответом `400`, файл больше `receipts.max-size` (по умолчанию 5 МБ) — ответом `413`. Неверный формат месяца и месяц из будущего относительно текущей даты сервера MUST отклоняться ответом `400`. Неизвестный лицевой счёт SHALL давать `404`. При любой ошибке в хранилище и БД ничего не остаётся.

#### Scenario: Не PDF
- **WHEN** отправлено тело, не начинающееся с `%PDF-`
- **THEN** ответ `400`, файл не сохранён

#### Scenario: Пустое тело
- **WHEN** отправлено пустое тело
- **THEN** ответ `400`

#### Scenario: Слишком большой файл
- **WHEN** размер тела превышает `receipts.max-size`
- **THEN** ответ `413`, файл не сохранён, запись в БД не создана

#### Scenario: Неверный месяц
- **WHEN** месяц задан как `2026-13`, `2026-1` или `октябрь`
- **THEN** ответ `400`

#### Scenario: Месяц из будущего
- **WHEN** текущая дата сервера — 18 октября 2026, а месяц — `2026-11`
- **THEN** ответ `400`

#### Scenario: Неизвестный счёт
- **WHEN** публикация адресована счёту, которого нет
- **THEN** ответ `404`

### Requirement: Список квитанций
Система SHALL предоставлять эндпоинт `GET /api/accounts/{number}/receipts`, возвращающий JSON `{"receipts": [...]}` с квитанциями счёта: у каждой `month`, `size` и `published_at`; квитанции MUST быть отсортированы по месяцу от новых к старым. Для счёта без квитанций список пуст, для неизвестного счёта — `404`. В ответе MUST NOT быть ключей файлов и внутренних идентификаторов.

#### Scenario: Несколько квитанций
- **WHEN** у счёта опубликованы квитанции за 2026-08, 2026-10 и 2026-09
- **THEN** список содержит `2026-10`, `2026-09`, `2026-08` в этом порядке

#### Scenario: Нет квитанций
- **WHEN** у счёта нет квитанций
- **THEN** ответ `200` с пустым списком

#### Scenario: Квитанции другого счёта
- **WHEN** запрашивается список счёта, у которого квитанций нет, а у другого счёта они есть
- **THEN** чужие квитанции в списке не показываются

### Requirement: Скачивание квитанции
Система SHALL предоставлять эндпоинт `GET /api/accounts/{number}/receipts/{month}`, отдающий файл квитанции с типом `application/pdf`, длиной и заголовком `Content-Disposition` с именем вида `receipt-<номер счёта>-<месяц>.pdf`. Если квитанции за месяц нет, а также если неверен формат месяца или неизвестен счёт, ответ SHALL быть `404`. Отдаваемое содержимое MUST совпадать с загруженным байт в байт.

#### Scenario: Скачивание
- **WHEN** запрашивается опубликованная квитанция `2026-10` счёта `000000000001`
- **THEN** ответ `200`, `Content-Type: application/pdf`, тело совпадает с загруженным файлом, имя файла в `Content-Disposition` — `receipt-000000000001-2026-10.pdf`

#### Scenario: Квитанции за месяц нет
- **WHEN** запрашивается месяц, за который ничего не публиковалось
- **THEN** ответ `404`

#### Scenario: Квитанция другого счёта
- **WHEN** запрашивается месяц, за который квитанция есть только у другого счёта
- **THEN** ответ `404`

#### Scenario: Потерянный файл
- **WHEN** запись в БД есть, а файл в хранилище отсутствует
- **THEN** ответ `404`, ошибка записывается в журнал сервера

### Requirement: Файловое хранилище
Файлы квитанций SHALL храниться в S3-совместимом хранилище проекта (см. спецификацию `object-storage`), в бакете квитанций, под ключом-идентификатором, который создаёт сервер (UUID); имя файла от клиента MUST NOT использоваться для ключа. Ключ MUST проверяться на соответствие формату перед обращением к хранилищу. Объект записывается целиком, поэтому читатель никогда не получает неполный файл. Если сохранение записи в БД не удалось, записанный объект MUST быть удалён. Файлы MUST переживать пересоздание контейнеров бэкенда и хранилища, пока цел том хранилища.

#### Scenario: Ключ без обхода каталогов
- **WHEN** хранилищу передаётся ключ вида `../secret` или абсолютный путь
- **THEN** операция отклоняется, обращения к хранилищу нет

#### Scenario: Сбой БД после записи файла
- **WHEN** запись в БД не удалась после того, как файл записан
- **THEN** объект удалён из бакета квитанций, лишних объектов в нём нет

#### Scenario: Файлы переживают пересоздание контейнера
- **WHEN** контейнер бэкенда или хранилища пересоздан при неизменном томе хранилища
- **THEN** ранее опубликованные квитанции скачиваются

### Requirement: Конфигурация квитанций
Приложение SHALL поддерживать параметры `receipts.max-size` (максимальный размер файла, по умолчанию 5 МБ), `receipts.admin-token` (токен администратора), переопределяемые переменными окружения (`RECEIPTS_MAX_SIZE`, `RECEIPTS_ADMIN_TOKEN`); место хранения файлов задаётся параметрами `storage.s3.*` (спецификация `object-storage`), параметра `receipts.storage.path` больше нет. В профиле `prod` токен MUST NOT иметь значения по умолчанию (публикация отключена, пока он не задан); в профиле `dev` SHALL быть токен для разработки. Через nginx на пути `/api/` MUST проходить тело запроса не меньше `receipts.max-size` с запасом.

#### Scenario: Prod без токена
- **WHEN** приложение запущено в профиле `prod` без `RECEIPTS_ADMIN_TOKEN`
- **THEN** публикация квитанций отклоняется с `403`, чтение остаётся доступным

#### Scenario: Dev с токеном по умолчанию
- **WHEN** приложение запущено в профиле `dev` без переопределений
- **THEN** публикация с токеном разработки работает

#### Scenario: Загрузка через nginx
- **WHEN** администратор отправляет PDF размером 4 МБ через nginx
- **THEN** запрос доходит до бэкенда и принимается

### Requirement: Суммы квитанции
Квитанция SHALL иметь необязательные суммы: капитальный ремонт и коммунальные услуги (в рублях, неотрицательные, не более двух знаков после запятой и не более десяти знаков до запятой). Суммы MUST задаваться вместе или не задаваться вовсе. Вместе с суммами MUST храниться источник (`MANUAL` — указаны при публикации, `PARSED` — извлечены из PDF автоматически; значение `PARSED` зарезервировано для будущего разбора файла) и время записи сумм; без сумм источник и время отсутствуют. Публикация SHALL принимать необязательные параметры запроса `capital_repair` и `utilities` (десятичное число с точкой): если указаны оба, суммы сохраняются с источником `MANUAL`; если не указан ни один, суммы сбрасываются (у новой квитанции их нет, а при замене файла прежние суммы удаляются, так как относились к другому файлу); если указан только один параметр или значение неверно, ответ `400` и ничего не меняется. Ответы публикации и списка SHALL содержать `capital_repair_amount` и `utilities_amount` (числа или `null`); источник и время записи сумм наружу не отдаются. Автоматический разбор PDF при загрузке в это изменение не входит.

#### Scenario: Публикация с суммами
- **WHEN** администратор отправляет PDF на `PUT /api/accounts/000000000001/receipts/2026-10?capital_repair=1842.50&utilities=6318.27`
- **THEN** ответ `201`, в теле `capital_repair_amount` `1842.50` и `utilities_amount` `6318.27`, в БД источник `MANUAL` и время записи сумм

#### Scenario: Публикация без сумм
- **WHEN** администратор отправляет PDF без параметров сумм
- **THEN** ответ `201`, обе суммы `null`, источника и времени записи нет

#### Scenario: Замена файла без сумм
- **WHEN** у квитанции были суммы, а администратор заменяет файл без параметров сумм
- **THEN** ответ `200`, обе суммы `null`, источник и время сброшены

#### Scenario: Замена файла с новыми суммами
- **WHEN** администратор заменяет файл и указывает другие суммы
- **THEN** сохраняются новые суммы, время записи обновляется

#### Scenario: Нулевые суммы
- **WHEN** указаны `capital_repair=0` и `utilities=0.00`
- **THEN** суммы сохраняются как нули, а не как «не заданы»

#### Scenario: Указана только одна сумма
- **WHEN** передан только `capital_repair` или только `utilities`
- **THEN** ответ `400`, файл и запись не сохранены, прежние данные не изменены

#### Scenario: Неверное значение суммы
- **WHEN** сумма равна `-1`, `12.345`, `abc`, `1e3`, пустой строке или имеет более десяти знаков до запятой
- **THEN** ответ `400`, ничего не сохранено

#### Scenario: Суммы в списке
- **WHEN** у квитанции за 2026-10 суммы заданы, а у квитанции за 2026-09 нет
- **THEN** в списке у первой `capital_repair_amount` и `utilities_amount` содержат суммы, у второй — `null`, а источника и времени записи сумм в ответе нет

#### Scenario: Ограничения базы
- **WHEN** в БД добавляется квитанция с одной суммой без другой, с суммой без источника или с отрицательной суммой
- **THEN** хранилище отклоняет добавление

### Requirement: Вкладка «Квитанции»
Навигация шапки зависит от роли: у собственника (`OWNER`) пункты «Показания», «Квитанции» и «Заявки», у жильца (`RESIDENT`) только «Показания», у администратора (`ADMIN`) «Выставить квитанции» и «Заявки» (см. требования «Вкладка «Выставить квитанции»» и спецификацию `requests-screen`); пункт «Заявки» (у собственника и администратора) открывает вкладку заявок (см. спецификацию `requests-screen`), у жильца его нет. Клик по «Квитанции» SHALL открывать вкладку квитанций, клик по «Показания» — форму ввода показаний, активный пункт выделяется основным цветом. Вкладка квитанций содержит только список и скачивание. Активная вкладка собственника SHALL отражаться в адресе параметром `tab` (`tab=receipts` для квитанций, без параметра — показания); параметр `account` при переключении MUST сохраняться. Открытие адреса с `tab=receipts` SHALL сразу показывать вкладку квитанций и сохраняться при обновлении страницы; любое другое значение `tab` открывает показания. У жильца `tab=receipts` открывает показания; у администратора допустимы `tab=requests` (вкладка заявок) и отсутствие параметра (вкладка «Выставить квитанции»), любое другое значение, включая `tab=receipts`, открывает «Выставить квитанции». Шапка, данные лицевого счёта, их загрузка и состояния ошибок («Лицевой счёт не найден», «Не удалось загрузить данные», «К вашей учётной записи не привязан лицевой счёт») MUST быть общими для вкладок собственника и жильца.

#### Scenario: Переключение по клику
- **WHEN** собственник на экране показаний нажимает «Квитанции» в шапке
- **THEN** открывается вкладка квитанций, пункт «Квитанции» выделен основным цветом, пункт «Показания» нет, адрес содержит `tab=receipts` и прежний `account`

#### Scenario: Возврат к показаниям
- **WHEN** собственник на вкладке квитанций нажимает «Показания»
- **THEN** открывается форма ввода показаний, из адреса исчезает `tab`, `account` остаётся

#### Scenario: Прямая ссылка на вкладку
- **WHEN** собственник открывает `/?account=000000000001&tab=receipts`
- **THEN** сразу показана вкладка квитанций счёта `000000000001`

#### Scenario: Неизвестное значение вкладки
- **WHEN** адрес содержит `tab=unknown`
- **THEN** открыта форма ввода показаний

#### Scenario: Вкладка квитанций у жильца
- **WHEN** жилец открывает адрес с `tab=receipts`
- **THEN** открыта форма ввода показаний

#### Scenario: Администратор без показаний и квитанций
- **WHEN** в систему вошёл администратор
- **THEN** в навигации нет пунктов «Показания» и «Квитанции», открыта вкладка «Выставить квитанции», а адрес с `tab=receipts` её не меняет

#### Scenario: Администратор открывает заявки
- **WHEN** администратор нажимает «Заявки»
- **THEN** открывается вкладка заявок, адрес содержит `tab=requests`

#### Scenario: Счёт не найден
- **WHEN** API вернул `404` для запрошенного номера, а адрес собственника содержит `tab=receipts`
- **THEN** показано сообщение «Лицевой счёт не найден», а список квитанций не запрашивается

#### Scenario: Заявки не открываются
- **WHEN** жилец открывает адрес с `tab=requests`
- **THEN** вкладка заявок не открывается, показаны показания

#### Scenario: Заявки открываются
- **WHEN** собственник нажимает «Заявки»
- **THEN** открывается вкладка заявок, адрес содержит `tab=requests`

### Requirement: Список квитанций на вкладке
Вкладка SHALL показывать заголовок «Квитанции» (тот же стиль, что у заголовка показаний, выровнен по левому краю) и загружать список из `GET /api/accounts/{number}/receipts`. Квитанции SHALL показываться компонентом-аккордеоном (сворачиваемые панели, одновременно открыта не более одной) в порядке ответа API (новые первыми). Заголовок панели — месяц и год («Октябрь 2026», месяц с заглавной буквы). По умолчанию открыта панель самой новой квитанции, остальные свёрнуты. Внутри панели SHALL быть две суммы — «Капитальный ремонт» и «Коммунальные услуги» — в рублях с двумя знаками после запятой, десятичной запятой и неразрывным пробелом между тысячами («1 842,50 ₽»), а если сумма не задана (`null`) — прочерк «—», и ссылка «Скачать PDF». Размер файла и дата публикации MUST NOT показываться.

#### Scenario: Аккордеон по месяцам
- **WHEN** API вернул квитанции за 2026-10, 2026-09 и 2026-08
- **THEN** на вкладке три панели в порядке «Октябрь 2026», «Сентябрь 2026», «Август 2026», открыта первая

#### Scenario: Открыта одна панель
- **WHEN** пользователь нажимает на заголовок «Сентябрь 2026»
- **THEN** панель сентября раскрывается, а панель октября сворачивается

#### Scenario: Две суммы в панели
- **WHEN** у квитанции за 2026-10 капремонт 1842.5, коммунальные услуги 6318.27
- **THEN** в раскрытой панели видны «Капитальный ремонт» — «1 842,50 ₽» и «Коммунальные услуги» — «6 318,27 ₽»

#### Scenario: Суммы не заданы
- **WHEN** у квитанции обе суммы `null`
- **THEN** вместо сумм показан прочерк «—», ссылка «Скачать PDF» остаётся

#### Scenario: Большие и нулевые суммы
- **WHEN** сумма равна 1234567.8, а другая 0
- **THEN** показаны «1 234 567,80 ₽» и «0,00 ₽»

#### Scenario: Размера и даты нет
- **WHEN** открыта любая панель
- **THEN** в ней нет размера файла и даты публикации

### Requirement: Скачивание квитанции с вкладки
Ссылка «Скачать PDF» каждой панели (в раскрытом виде) SHALL вести на `GET /api/accounts/{number}/receipts/{месяц}` (с префиксом `/api` того же хоста), содержать номер счёта из адреса страницы и месяц строки в формате `ГГГГ-ММ` и скачивать файл без перезагрузки приложения. Для скачивания MUST NOT требоваться токен администратора.

#### Scenario: Адрес ссылки
- **WHEN** на вкладке счёта `000000000001` показана квитанция за 2026-10
- **THEN** ссылка «Скачать PDF» этой строки ведёт на `/api/accounts/000000000001/receipts/2026-10`

#### Scenario: Ссылки разных панелей
- **WHEN** на вкладке две квитанции за 2026-10 и 2026-09, и пользователь раскрывает каждую панель
- **THEN** у каждой панели своя ссылка с её месяцем

### Requirement: Состояния вкладки квитанций
Пока список загружается, вкладка SHALL показывать индикатор загрузки. Если квитанций нет, вкладка SHALL показывать сообщение «Квитанции пока не опубликованы». Если загрузка списка завершилась ошибкой сети или сервера, вкладка SHALL показывать сообщение «Не удалось загрузить квитанции» и кнопку «Повторить», повторяющую запрос. Ошибка списка квитанций MUST NOT влиять на шапку и вкладку показаний.

#### Scenario: Загрузка
- **WHEN** запрос списка ещё не завершён
- **THEN** вместо списка показан индикатор загрузки

#### Scenario: Пустой список
- **WHEN** API вернул пустой список
- **THEN** показано «Квитанции пока не опубликованы»

#### Scenario: Ошибка и повтор
- **WHEN** запрос списка завершился ошибкой, а затем пользователь нажимает «Повторить»
- **THEN** сначала показано «Не удалось загрузить квитанции», после нажатия запрос отправляется снова и при успехе показан список

#### Scenario: Ошибка не ломает остальное
- **WHEN** список квитанций не загрузился
- **THEN** шапка остаётся на месте, а вкладка «Показания» работает как обычно

### Requirement: Квитанции только по токену и роли
Эндпоинты `GET /api/accounts/{number}/receipts` и `GET /api/accounts/{number}/receipts/{month}` SHALL требовать аутентификации и доступа к счёту по правилам спецификации `authorization`: без токена — `401`; жилец (`RESIDENT`) и любой пользователь без доступа к счёту — `403`. Доступ к квитанциям имеют `ADMIN` (любой счёт) и `OWNER` (свои счета). Публикация `PUT /api/accounts/{number}/receipts/{month}` описана в требовании «Публикация квитанции» и не требует токена входа, если запрос содержит верный `X-Admin-Token`.

#### Scenario: Без токена
- **WHEN** клиент запрашивает список квитанций без токена
- **THEN** ответ `401`

#### Scenario: Собственник скачивает свою квитанцию
- **WHEN** собственник счёта скачивает опубликованную квитанцию этого счёта
- **THEN** ответ `200` с PDF

#### Scenario: Жилец
- **WHEN** жилец запрашивает список или файл квитанции своего счёта
- **THEN** ответ `403`

#### Scenario: Публикация по административному токену
- **WHEN** скрипт публикует квитанцию с верным `X-Admin-Token` и без JWT
- **THEN** публикация проходит так же, как до введения аутентификации

### Requirement: Вкладка «Выставить квитанции»
Для пользователя с ролью `ADMIN` вкладка «Выставить квитанции» SHALL быть первой из двух вкладок навигации (вторая — «Заявки»): она открывается сразу после входа и после обновления страницы, пока в адресе нет `tab=requests`, имеет заголовок «Выставить квитанции» и содержит форму публикации. Адрес вкладки параметров `tab` не получает; `account` для неё не используется. Остальным ролям пункт не показывается, вкладки с формой у них нет. Вкладка не зависит от какого-либо лицевого счёта: квартира, для которой публикуется квитанция, выбирается в форме.

#### Scenario: Вход администратора
- **WHEN** в систему вошёл администратор
- **THEN** открыта вкладка «Выставить квитанции» с формой, пункт «Выставить квитанции» выделен основным цветом, адрес без `tab`

#### Scenario: Пункта нет у остальных
- **WHEN** в систему вошёл собственник или жилец
- **THEN** пункта «Выставить квитанции» в навигации нет

#### Scenario: Обновление страницы
- **WHEN** администратор обновляет страницу
- **THEN** после восстановления сессии снова показана вкладка «Выставить квитанции»

### Requirement: Список квартир для публикации
Система SHALL предоставлять эндпоинт `GET /api/accounts`, возвращающий пользователю с ролью `ADMIN` JSON `{"accounts": [...]}` со всеми лицевыми счетами: у каждого `number`, `address` (строка вида «ул. Тестовая, д. Тест, кв. 1») и `apartment`; список отсортирован по номеру счёта по возрастанию, имена в `snake_case`, технических полей в ответе нет. Без токена ответ `401`, для `OWNER` и `RESIDENT` — `403`.

#### Scenario: Администратор
- **WHEN** администратор запрашивает `GET /api/accounts` при наличии тестовых данных
- **THEN** ответ `200`, в списке есть счёт `000000000001` с адресом «ул. Тестовая, д. Тест, кв. 1» и квартирой `1`, счета идут по возрастанию номера

#### Scenario: Собственник и жилец
- **WHEN** собственник или жилец запрашивает `GET /api/accounts`
- **THEN** ответ `403`, данных счетов в теле нет

#### Scenario: Без токена
- **WHEN** клиент запрашивает `GET /api/accounts` без токена
- **THEN** ответ `401`

### Requirement: Форма публикации квитанции
Вкладка «Выставить квитанции» SHALL показывать карточку «Опубликовать квитанцию» с полями: «Квартира» (обязательный выбор из выпадающего списка с поиском; изначально ничего не выбрано; элементы вида «кв. 1 · ул. Тестовая, д. Тест (счёт 000000000001)», список загружается из `GET /api/accounts`), «Месяц» (выбор месяца, изначально пустой; месяцы позже текущего недоступны), «Файл PDF» (выбор одного файла), «Капитальный ремонт, ₽» и «Коммунальные услуги, ₽» (необязательные числа с запятой и двумя знаками) и кнопку «Опубликовать». Кнопка MUST быть недоступна, пока не выбраны квартира, месяц и файл, и во время выполнения запроса. Форма публикует квитанцию для выбранной квартиры и MUST NOT подставлять квартиру сама. Компоненты формы MUST быть из Ant Design, вёрстка корректна на узком экране.

#### Scenario: Форма у администратора
- **WHEN** администратор открывает вкладку «Выставить квитанции»
- **THEN** видна карточка «Опубликовать квитанцию» с пустыми полями, квартира не выбрана, кнопка «Опубликовать» недоступна

#### Scenario: Кнопка становится доступной
- **WHEN** администратор выбрал квартиру, месяц и файл
- **THEN** кнопка «Опубликовать» доступна, суммы можно не заполнять

#### Scenario: Без квартиры
- **WHEN** выбраны месяц и файл, а квартира нет
- **THEN** кнопка «Опубликовать» недоступна

#### Scenario: Поиск квартиры
- **WHEN** администратор вводит в поле «Квартира» часть номера квартиры или счёта
- **THEN** в списке остаются подходящие элементы

#### Scenario: Список квартир не загрузился
- **WHEN** запрос `GET /api/accounts` завершился ошибкой
- **THEN** над формой сообщение «Не удалось загрузить список квартир» с кнопкой «Повторить», кнопка «Опубликовать» недоступна

#### Scenario: Месяц из будущего
- **WHEN** администратор открывает выбор месяца
- **THEN** месяцы позже текущего недоступны для выбора

### Requirement: Проверка формы публикации
Перед отправкой форма SHALL проверять данные и не отправлять запрос при ошибке, показывая сообщение у поля: файл должен быть PDF (по расширению `.pdf` или типу `application/pdf`) — иначе «Выберите файл в формате PDF»; размер файла не должен превышать 5 МБ — иначе «Файл больше 5 МБ»; суммы заполняются обе или ни одной — иначе «Укажите обе суммы или оставьте оба поля пустыми»; суммы не могут быть отрицательными. Окончательная проверка остаётся за сервером.

#### Scenario: Не PDF
- **WHEN** администратор выбирает файл `receipt.docx`
- **THEN** у поля файла сообщение «Выберите файл в формате PDF», запрос не отправляется

#### Scenario: Слишком большой файл
- **WHEN** администратор выбирает PDF размером 6 МБ
- **THEN** у поля файла сообщение «Файл больше 5 МБ», запрос не отправляется

#### Scenario: Одна сумма
- **WHEN** заполнена только сумма капитального ремонта
- **THEN** сообщение «Укажите обе суммы или оставьте оба поля пустыми», запрос не отправляется

#### Scenario: Без сумм
- **WHEN** обе суммы пусты
- **THEN** запрос отправляется без параметров сумм

### Requirement: Отправка и результат публикации
Форма SHALL отправлять `PUT /api/accounts/{number}/receipts/{month}` для лицевого счёта выбранной квартиры с телом выбранного файла и типом `application/pdf`, а при заполненных суммах — с параметрами `capital_repair` и `utilities` (точка как разделитель, два знака). При ответе `201` форма SHALL показать сообщение «Квитанция за <Месяц Год> (кв. <номер>) опубликована», при `200` — «Квитанция за <Месяц Год> (кв. <номер>) заменена»; затем очистить месяц, файл и суммы, оставив выбранной квартиру (чтобы можно было загрузить следующий месяц). При ошибке поля формы MUST сохраняться, а сообщение показываться над кнопкой: `400` — «Квитанция не принята. Проверьте, что файл является PDF, а суммы указаны верно»; `413` — «Файл слишком большой. Максимум 5 МБ»; `404` — «Лицевой счёт не найден»; `403` — «Недостаточно прав»; прочие ответы и сбой сети — «Не удалось опубликовать квитанцию. Попробуйте позже». Ответ `401` завершает сессию по правилам спецификации `login-screen`.

#### Scenario: Новая квитанция
- **WHEN** администратор выбрал квартиру 1 (счёт `000000000001`), публикует PDF за октябрь 2026 с суммами `1842,50` и `6318,27`, а API отвечает `201`
- **THEN** запрос идёт на `/api/accounts/000000000001/receipts/2026-10` с `capital_repair=1842.50` и `utilities=6318.27`, показано «Квитанция за Октябрь 2026 (кв. 1) опубликована», месяц, файл и суммы очищены, квартира остаётся выбранной

#### Scenario: Другая квартира
- **WHEN** администратор выбрал квартиру 2 (счёт `000000000002`) и публикует PDF
- **THEN** запрос идёт на `/api/accounts/000000000002/receipts/<месяц>`

#### Scenario: Замена
- **WHEN** API отвечает `200`
- **THEN** показано «Квитанция за Октябрь 2026 (кв. 1) заменена»

#### Scenario: Слишком большой файл на сервере
- **WHEN** API отвечает `413`
- **THEN** показано «Файл слишком большой. Максимум 5 МБ», выбранные квартира, месяц и файл сохранены

#### Scenario: Ошибка связи
- **WHEN** запрос завершается сетевой ошибкой
- **THEN** показано «Не удалось опубликовать квитанцию. Попробуйте позже», поля формы не очищены

#### Scenario: Двойное нажатие
- **WHEN** запрос ещё выполняется
- **THEN** кнопка «Опубликовать» недоступна и повторный запрос не отправляется

### Requirement: Подтверждение замены
Если у выбранной квартиры уже есть квитанция за выбранный месяц, нажатие «Опубликовать» SHALL сначала запрашивать подтверждение «Квитанция за <Месяц Год> (кв. <номер>) уже опубликована. Заменить?» с пояснением «Файл и суммы будут заменены». Список квитанций выбранной квартиры форма SHALL запрашивать (`GET /api/accounts/{number}/receipts`) при выборе квартиры и после каждой публикации; пока он не загружен или не загрузился, замена не может быть определена, поэтому кнопка недоступна, а при ошибке показывается «Не удалось проверить опубликованные квитанции» с кнопкой «Повторить». Запрос публикации отправляется только после подтверждения; отказ оставляет форму без изменений.

#### Scenario: Месяц уже опубликован
- **WHEN** у квартиры 1 есть квитанция за «Октябрь 2026», а администратор публикует файл за 2026-10
- **THEN** показан запрос подтверждения замены, запрос публикации не отправлен

#### Scenario: Тот же месяц у другой квартиры
- **WHEN** квитанция за 2026-10 есть у квартиры 1, а администратор публикует 2026-10 для квартиры 2, у которой её нет
- **THEN** подтверждение не запрашивается, запрос отправляется сразу

#### Scenario: Подтверждение
- **WHEN** администратор подтверждает замену
- **THEN** отправляется запрос публикации

#### Scenario: Отказ
- **WHEN** администратор отказывается от замены
- **THEN** запрос не отправляется, поля формы сохранены

#### Scenario: Список квитанций квартиры не загрузился
- **WHEN** запрос списка квитанций выбранной квартиры завершился ошибкой
- **THEN** показано «Не удалось проверить опубликованные квитанции» с кнопкой «Повторить», кнопка «Опубликовать» недоступна

### Requirement: Форма только для администратора
Вкладка «Выставить квитанции» и форма публикации MUST показываться только роли `ADMIN`. Вкладка «Квитанции» у собственника SHALL показывать только список и скачивание: без полей выбора файла и кнопок «Опубликовать», «Заменить», «Удалить». Удаление квитанций в интерфейсе отсутствует для всех ролей.

#### Scenario: Собственник
- **WHEN** в систему вошёл собственник
- **THEN** вкладки «Выставить квитанции» нет, на вкладке «Квитанции» нет полей выбора файла и кнопок публикации

#### Scenario: Удаления нет
- **WHEN** администратор открывает вкладку «Выставить квитанции»
- **THEN** кнопки «Удалить» на ней нет
