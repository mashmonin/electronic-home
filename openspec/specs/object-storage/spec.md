## Purpose

Описывает собственное S3-совместимое хранилище файлов проекта (SeaweedFS в Docker): закрытость, бакеты, подключение, ключи объектов, целостность записи, проверку состояния и перенос ранее сохранённых квитанций.

## Requirements

### Requirement: Собственное S3-совместимое хранилище в контейнере
Окружение SHALL включать сервис объектного хранилища SeaweedFS с S3 API, запускаемый в Docker вместе с остальными сервисами (`docker compose`), без установки чего-либо на хост, кроме Docker. Данные хранилища MUST находиться на именованном томе и переживать перезапуск и пересоздание контейнера. Доступ к S3 API MUST требовать ключ доступа и секретный ключ (анонимный доступ запрещён). Бэкенд SHALL запускаться после того, как хранилище готово принимать запросы (проверка готовности в Compose).

#### Scenario: Хранилище запускается вместе с окружением
- **WHEN** запущено окружение `dev` или `prod`
- **THEN** сервис хранилища поднят, проверка готовности пройдена, бэкенд стартует после неё

#### Scenario: Данные переживают пересоздание
- **WHEN** контейнер хранилища пересоздаётся без удаления тома
- **THEN** ранее сохранённые квитанции и вложения остаются доступны

#### Scenario: Анонимный доступ запрещён
- **WHEN** клиент без ключей обращается к S3 API (чтение или запись объекта)
- **THEN** хранилище отказывает в доступе

### Requirement: Закрытое хранилище
Хранилище MUST быть доступно только внутри контейнерной сети. В prod его порты MUST NOT публиковаться на хост, веб-консоль и интерфейс администрирования не публикуются; nginx не проксирует S3 API. В dev порт S3 API может публиковаться только на `127.0.0.1` (для бэкенда, запущенного из IDE). Бакеты MUST быть приватными: публичных и предподписанных ссылок система не выдаёт, всё скачивание идёт через бэкенд с проверкой прав.

#### Scenario: Порт закрыт в prod
- **WHEN** запущено prod-окружение
- **THEN** подключиться к S3 API хранилища с хоста или снаружи нельзя

#### Scenario: Нет прямых ссылок
- **WHEN** пользователь получает список квитанций или сообщения заявки
- **THEN** в ответах нет адресов хранилища, ключей объектов и предподписанных ссылок

### Requirement: Бакеты
Система SHALL использовать три бакета: для квитанций (по умолчанию `electronic-home-receipts`), для вложений чатов (по умолчанию `electronic-home-attachments`) и для актов проверки счётчиков (по умолчанию `electronic-home-meter-acts`, переменная окружения `S3_METER_ACTS_BUCKET`, параметр `storage.s3.meter-acts-bucket`). Названия переопределяются конфигурацией. Если бакета нет, приложение MUST создать его при первом обращении к нему (создание идемпотентно и безопасно при одновременных запросах); отсутствие бакета при старте приложения не должно мешать запуску.

#### Scenario: Первый запуск
- **WHEN** хранилище пусто и публикуется первая квитанция
- **THEN** бакет квитанций создаётся автоматически и квитанция сохраняется

#### Scenario: Бакеты уже есть
- **WHEN** приложение запускается при существующих бакетах
- **THEN** они используются, ошибок и повторного создания нет

#### Scenario: Хранилище недоступно при старте
- **WHEN** приложение стартует, а хранилище ещё не отвечает
- **THEN** приложение запускается, а операции с файлами завершаются ошибкой, пока хранилище недоступно

#### Scenario: Бакет актов создаётся при первой загрузке
- **WHEN** бакета актов нет и загружается первый акт проверки
- **THEN** бакет создаётся автоматически, акт сохраняется

### Requirement: Подключение приложения
Приложение SHALL подключаться к хранилищу по параметрам `storage.s3.endpoint`, `storage.s3.region`, `storage.s3.access-key`, `storage.s3.secret-key`, `storage.s3.receipts-bucket` и `storage.s3.attachments-bucket`, переопределяемым переменными окружения `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_RECEIPTS_BUCKET`, `S3_ATTACHMENTS_BUCKET`. Адресация SHALL быть вида path-style (бакет в пути, а не в имени хоста). В профиле `dev` у параметров есть значения для разработки; в `prod` ключи MUST NOT иметь значений по умолчанию (см. спецификацию `runtime-profiles`).

#### Scenario: Dev без настройки
- **WHEN** приложение запущено в профиле `dev` с локальным хранилищем из Compose
- **THEN** оно подключается без дополнительных переменных окружения

#### Scenario: Свой адрес хранилища
- **WHEN** задан `S3_ENDPOINT`
- **THEN** приложение использует этот адрес

### Requirement: Ключи объектов
Ключ объекта SHALL создаваться сервером как UUID; имя файла от клиента MUST NOT входить в ключ. Ключ MUST проверяться на соответствие формату перед обращением к хранилищу. Квитанции и вложения хранятся в разных бакетах, а сопоставление «ключ → запись» находится в БД.

#### Scenario: Ключ не UUID
- **WHEN** хранилищу передаётся ключ вида `../secret` или иной, не являющийся UUID
- **THEN** операция отклоняется без обращения к хранилищу

#### Scenario: Имя клиента не попадает в ключ
- **WHEN** загружается файл с именем `../../etc/passwd.pdf`
- **THEN** ключ объекта — новый UUID, имя в нём не используется

### Requirement: Запись и целостность
Объект SHALL записываться в хранилище целиком: читатель не получает частично записанный файл. Для каждого файла система MUST вычислить и сохранить в БД размер и SHA-256. Если сохранение записи в БД не удалось, записанные в хранилище объекты MUST быть удалены; сбой удаления фиксируется в журнале и не меняет ответ клиенту. Чтение несуществующего объекта даёт «нет файла» (ответ `404` пользователю, ошибка в журнале сервера, если запись о файле в БД есть).

#### Scenario: Сбой БД после записи
- **WHEN** запись в БД не удалась после того, как файл записан в хранилище
- **THEN** объект удалён из хранилища

#### Scenario: Потерянный объект
- **WHEN** запись о файле в БД есть, а объекта в хранилище нет
- **THEN** скачивание даёт `404`, в журнале сервера ошибка, работа остальных файлов не затронута

#### Scenario: Размер и контрольная сумма
- **WHEN** файл сохранён
- **THEN** в БД лежат его размер в байтах и SHA-256, совпадающие с содержимым объекта

### Requirement: Состояние хранилища
`/api/actuator/health` SHALL учитывать состояние хранилища: когда оно отвечает и бакеты доступны, компонент `objectStorage` имеет статус `UP`, иначе `DOWN`, а общий статус сервиса `DOWN`. В профиле `prod` в ответе MUST NOT быть адресов, ключей и текстов ошибок хранилища.

#### Scenario: Хранилище работает
- **WHEN** хранилище отвечает на запросы
- **THEN** `GET /api/actuator/health` показывает `UP`

#### Scenario: Хранилище остановлено
- **WHEN** контейнер хранилища остановлен
- **THEN** `GET /api/actuator/health` показывает `DOWN`

#### Scenario: Prod не раскрывает подробности
- **WHEN** в профиле `prod` хранилище недоступно
- **THEN** в ответе здоровья нет адреса хранилища и текста ошибки

### Requirement: Перенос существующих квитанций
Если задан параметр `receipts.migration.source-path` (переменная `RECEIPTS_MIGRATION_SOURCE_PATH`) и каталог существует, приложение при старте SHALL скопировать в бакет квитанций файлы всех записей таблицы `receipts`, которых там ещё нет, под тем же ключом (`file_key`). Перенос MUST быть идемпотентным (повторный запуск ничего не дублирует и не перезаписывает), MUST NOT удалять и менять исходные файлы, MUST сверять размер и SHA-256 с записью БД и не копировать файл, не совпавший с ними (ошибка в журнале). Сбой одного файла не останавливает перенос остальных и запуск приложения. По окончании в журнал пишутся числа: перенесено, уже было, нет исходного файла, ошибок. В dev значение по умолчанию — `./data/receipts`; в Docker том со старыми файлами монтируется в бэкенд только для чтения.

#### Scenario: Перенос
- **WHEN** в БД две квитанции, их файлы лежат в каталоге-источнике, а в бакете пусто
- **THEN** после старта обе квитанции скачиваются, файлы в бакете совпадают с исходными, исходные файлы на месте

#### Scenario: Повторный старт
- **WHEN** приложение запускается снова
- **THEN** ничего не копируется повторно, в журнале «перенесено 0, уже было 2»

#### Scenario: Нет исходного файла
- **WHEN** запись квитанции есть, а файла нет ни в каталоге, ни в бакете
- **THEN** в журнале предупреждение, остальные файлы переносятся, приложение запускается

#### Scenario: Файл не совпал с записью
- **WHEN** размер или SHA-256 исходного файла не совпадают с записью БД
- **THEN** файл не копируется, в журнале ошибка, приложение запускается

#### Scenario: Источник не задан
- **WHEN** `receipts.migration.source-path` не задан или каталога нет
- **THEN** перенос не выполняется, приложение запускается
