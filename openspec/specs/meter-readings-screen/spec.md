## Purpose

Позволяет жильцу ввести и подготовить к отправке показания счётчиков горячей и холодной воды по стоякам своей квартиры на одном экране.

## Requirements

### Requirement: Шапка экрана с данными лицевого счёта
Экран SHALL показывать шапку с названием ТСЖ, навигацией («Показания» — текущий раздел, выделен основным цветом; «Заявки»), иконками уведомлений, профиля и дома, а также блоком с адресом квартиры и номером лицевого счёта. Адрес и номер лицевого счёта MUST браться из ответа API по лицевому счёту.

#### Scenario: Отображение шапки
- **WHEN** пользователь открывает экран ввода показаний, а API вернул лицевой счёт `000000000001` с адресом «ул. Тестовая, д. Тест, кв. 1»
- **THEN** в шапке видны «ТСЖ «Комфорт»», пункты навигации «Показания» и «Заявки», три иконки, адрес «ул. Тестовая, д. Тест, кв. 1» и строка «Лицевой счёт № 000000000001»

### Requirement: Заголовок периода
Экран SHALL показывать по центру заголовок «Ввод показаний» и подзаголовок с отчётным месяцем и сроком передачи показаний.

#### Scenario: Отображение периода
- **WHEN** пользователь открывает экран
- **THEN** под заголовком отображается строка вида «Август 2026 · Передайте показания до 25 числа»

### Requirement: Карточки стояков
Экран SHALL строить карточки «Стояк N» из счётчиков воды лицевого счёта, полученных из API: N-й по порядку счётчик горячей воды (`HOT`) и N-й счётчик холодной воды (`COLD`) образуют «Стояк N». Карточка SHALL содержать название стояка и два поля ввода: «Горячая вода, м³» и «Холодная вода, м³». Под каждым полем SHALL отображаться «Счётчик № …» с номером соответствующего счётчика и предыдущее показание — значение последнего показания этого счётчика с тремя знаками после запятой. Если для поля нет счётчика или у счётчика нет показаний, соответствующие строки MUST показывать прочерк.

#### Scenario: Отображение стояков
- **WHEN** API вернул счётчики «Тест 1» (`HOT`, последнее показание `245.300`) и «Тест 2» (`COLD`, последнее показание `512.100`)
- **THEN** на экране одна карточка «Стояк 1»; под полем горячей воды видны «Счётчик № Тест 1» и «Пред. показание: 245.300 м³», под полем холодной — «Счётчик № Тест 2» и «Пред. показание: 512.100 м³», поля пустые с подсказкой `0.000`

#### Scenario: Несколько пар счётчиков
- **WHEN** API вернул два счётчика горячей воды и два холодной
- **THEN** на экране две карточки «Стояк 1» и «Стояк 2», в каждой — по паре счётчиков в порядке номеров

#### Scenario: Непарный счётчик
- **WHEN** API вернул один счётчик горячей воды и ни одного холодной
- **THEN** на экране карточка «Стояк 1», у поля холодной воды в строках счётчика и предыдущего показания стоит прочерк

#### Scenario: Квартира без счётчиков
- **WHEN** API вернул пустой список счётчиков
- **THEN** на экране нет предзаполненных карточек стояков, доступна кнопка «+ Добавить стояк»

#### Scenario: Счётчик без показаний
- **WHEN** у счётчика нет показаний
- **THEN** под полем «Пред. показание» стоит прочерк, а проверка «не меньше предыдущего» для него не применяется

### Requirement: Ввод показаний
Поле ввода SHALL принимать только неотрицательные числа с точкой или запятой в качестве разделителя и не более чем тремя знаками после разделителя. Показание MUST NOT быть меньше предыдущего показания этого счётчика.

#### Scenario: Допустимое значение
- **WHEN** пользователь вводит в поле значение, не меньшее предыдущего показания, например `250.125`
- **THEN** значение принимается без сообщения об ошибке

#### Scenario: Нечисловой ввод
- **WHEN** пользователь вводит в поле буквы или отрицательное число
- **THEN** поле не принимает такой ввод или показывает ошибку, а отправка блокируется

#### Scenario: Значение меньше предыдущего
- **WHEN** пользователь вводит значение меньше предыдущего показания
- **THEN** под полем отображается сообщение, что показание не может быть меньше предыдущего, а отправка блокируется

### Requirement: Добавление стояка
Кнопка «+ Добавить стояк» SHALL добавлять в форму новую карточку стояка со следующим порядковым номером и пустыми полями.

#### Scenario: Добавление третьего стояка
- **WHEN** на экране два стояка и пользователь нажимает «+ Добавить стояк»
- **THEN** появляется карточка «Стояк 3» с пустыми полями горячей и холодной воды

### Requirement: Отправка показаний
Кнопка «Отправить показания» SHALL отправлять введённые значения в API сохранения показаний лицевого счёта, если все заполненные поля корректны и заполнено хотя бы одно поле. В запрос MUST попадать для каждого заполненного поля номер его счётчика и значение с точкой в качестве разделителя; пустые поля MUST NOT отправляться. После успешной отправки пользователь SHALL увидеть подтверждение. Во время отправки кнопка MUST быть заблокирована.

#### Scenario: Успешная отправка
- **WHEN** пользователь ввёл корректные значения хотя бы в одно поле и нажал «Отправить показания», а API ответил успехом
- **THEN** значения отправлены в API вместе с номерами счётчиков и отображается сообщение об успешной передаче показаний

#### Scenario: Пустая форма
- **WHEN** все поля пусты и пользователь нажимает «Отправить показания»
- **THEN** показания не отправляются и отображается сообщение о необходимости ввести хотя бы одно значение

#### Scenario: Есть ошибки ввода
- **WHEN** хотя бы одно поле содержит некорректное значение и пользователь нажимает «Отправить показания»
- **THEN** показания не отправляются, ошибочные поля подсвечены

#### Scenario: Заполнено одно поле из нескольких
- **WHEN** пользователь ввёл значение только в поле горячей воды и нажал «Отправить показания»
- **THEN** в API отправлено одно показание — для счётчика горячей воды этой карточки

#### Scenario: Сервер отклонил значение
- **WHEN** API отвечает ошибкой `VALUE_LESS_THAN_PREVIOUS` для счётчика
- **THEN** под полем этого счётчика отображается сообщение, что показание не может быть меньше предыдущего, введённые значения не очищаются, а «Пред. показание» обновляется актуальным

#### Scenario: Сервер отклонил запись по другим причинам
- **WHEN** API отвечает `400` с кодом `INVALID_VALUE` или `METER_NOT_FOUND` для счётчика
- **THEN** под полем этого счётчика отображается сообщение об ошибке («Введите число, не более трёх знаков после запятой» или «Счётчик не найден»)

#### Scenario: Конфликт при сохранении
- **WHEN** API отвечает `409`
- **THEN** отображается сообщение, что показания не сохранены из-за одновременного изменения и можно повторить отправку, а данные счёта перезапрашиваются

#### Scenario: Счёт не найден при отправке
- **WHEN** API отвечает `404`
- **THEN** отображается сообщение «Лицевой счёт не найден», введённые значения не очищаются

#### Scenario: Ошибка связи при отправке
- **WHEN** отправка завершается ошибкой сети или сервера
- **THEN** отображается сообщение «Не удалось отправить показания, попробуйте позже», введённые значения не очищаются

### Requirement: Сброс формы
Кнопка «Сбросить форму» SHALL очищать все введённые значения и сообщения об ошибках.

#### Scenario: Сброс введённых значений
- **WHEN** пользователь ввёл значения в несколько полей и нажал «Сбросить форму»
- **THEN** все поля пусты и сообщения об ошибках скрыты

### Requirement: Контакты для помощи
Экран SHALL показывать карточку «Нужна помощь?» с указанием должности контактного лица и телефоном.

#### Scenario: Отображение контактов
- **WHEN** пользователь открывает экран
- **THEN** внизу отображаются «Нужна помощь?», «Председатель правления ТСЖ» и телефон `+7 (999) 123-45-67`

### Requirement: Соответствие макету
Оформление экрана SHALL соответствовать макету Figma `02-meter-readings`: основной цвет `#ffb370`, фон страницы `#fffbeb`, белые карточки с рамкой `#f0f0f0`, белая шапка с нижней границей `#e8e8e8`. Основной блок с показаниями SHALL быть отцентрирован по горизонтали, а его ширина — ограничена 700px на широких экранах (отступы по бокам 40px). Экран MUST использовать только компоненты Ant Design.

#### Scenario: Широкий экран
- **WHEN** экран открыт в окне шириной 1440px
- **THEN** расположение блоков и цвета совпадают с макетом

#### Scenario: Узкий экран
- **WHEN** экран открыт в окне шириной менее 768px
- **THEN** поля ввода каждого стояка располагаются друг под другом, горизонтальной прокрутки страницы нет

### Requirement: Загрузка лицевого счёта
Экран SHALL загружать информацию о лицевом счёте с API при открытии. Номер счёта берётся из параметра адресной строки `account`; если параметра нет, в режиме разработки используется счёт по умолчанию, а в рабочей сборке экран MUST показать сообщение, что лицевой счёт не указан. Пока данные загружаются, экран SHALL показывать индикатор загрузки; содержимое экрана MUST NOT показываться до получения данных.

#### Scenario: Номер счёта в адресной строке
- **WHEN** пользователь открывает экран с адресом `/?account=000000000001`
- **THEN** экран запрашивает лицевой счёт `000000000001` и после ответа показывает его данные

#### Scenario: Загрузка
- **WHEN** запрос к API ещё не завершён
- **THEN** вместо содержимого экрана показан индикатор загрузки

#### Scenario: Счёт не найден
- **WHEN** API отвечает `404` для запрошенного номера
- **THEN** экран показывает сообщение «Лицевой счёт не найден» и не показывает форму ввода показаний

#### Scenario: Ошибка связи
- **WHEN** запрос к API завершается ошибкой сети или сервера
- **THEN** экран показывает сообщение «Не удалось загрузить данные» и не показывает форму ввода показаний

#### Scenario: Номер счёта не указан
- **WHEN** рабочая сборка открыта без параметра `account`
- **THEN** экран показывает сообщение, что лицевой счёт не указан

### Requirement: Совладельцы лицевого счёта
Экран SHALL показывать список совладельцев лицевого счёта (ФИО из ответа API) во всплывающем окне, открываемом по иконке профиля в шапке.

#### Scenario: Открытие списка совладельцев
- **WHEN** пользователь нажимает иконку профиля в шапке при двух совладельцах счёта
- **THEN** отображаются ФИО обоих совладельцев

#### Scenario: Счёт без совладельцев
- **WHEN** пользователь нажимает иконку профиля, а у счёта нет совладельцев
- **THEN** отображается сообщение «Совладельцы не указаны»

### Requirement: Обновление данных после сохранения
После успешного сохранения показаний экран SHALL заново загрузить информацию о лицевом счёте из API, очистить введённые значения и показать под полями новые «Пред. показание» — значения только что сохранённых показаний. Экран при этом MUST NOT показывать полноэкранный индикатор загрузки и MUST NOT терять карточки.

#### Scenario: Предыдущее показание обновилось
- **WHEN** у счётчика «Тест 1» было предыдущее показание `245.300`, пользователь отправил `250.125` и API сохранил его
- **THEN** под полем «Тест 1» отображается «Пред. показание: 250.125 м³», а поле пусто

#### Scenario: Повторная отправка
- **WHEN** после успешного сохранения пользователь вводит значение меньше только что сохранённого
- **THEN** под полем отображается сообщение, что показание не может быть меньше предыдущего

#### Scenario: Данные не удалось обновить
- **WHEN** показания сохранены, но повторная загрузка лицевого счёта завершилась ошибкой
- **THEN** отображается предупреждение, что показания сохранены, но данные экрана не обновились, и предложение обновить страницу

### Requirement: Поля без счётчика
Значение, введённое в поле, для которого нет счётчика (поле добавленного вручную стояка или поле у непарного счётчика), MUST блокировать отправку, а под полем SHALL отображаться сообщение «Для этого поля нет счётчика». Такие поля MUST NOT попадать в запрос.

#### Scenario: Значение в поле без счётчика
- **WHEN** пользователь добавил стояк кнопкой «+ Добавить стояк», ввёл значение в его поле и нажал «Отправить показания»
- **THEN** показания не отправляются, под полем отображается «Для этого поля нет счётчика»

#### Scenario: Пустое поле без счётчика
- **WHEN** поле без счётчика остаётся пустым
- **THEN** оно не влияет на отправку остальных полей

### Requirement: Дата проверки и статус «Просрочено»
Под полем каждого счётчика экран SHALL показывать строку «Дата проверки: ДД.ММ.ГГГГ» с датой проверки счётчика из API; если даты нет, строка MUST показывать «Дата проверки: —». Экран SHALL сравнивать дату проверки с текущей системной датой устройства пользователя (только дата, без времени): если дата проверки раньше текущей даты, рядом MUST показываться метка «Просрочено». В сам день даты проверки метка MUST NOT показываться. Метка MUST NOT показываться и для счётчика без даты проверки, и для поля без счётчика. Статус только информирует и MUST NOT блокировать ввод и отправку показаний.

#### Scenario: Срок проверки не истёк
- **WHEN** дата проверки счётчика 01.01.2028, а текущая системная дата 18.10.2026
- **THEN** под полем счётчика видна строка «Дата проверки: 01.01.2028» без метки «Просрочено»

#### Scenario: Срок проверки истёк
- **WHEN** дата проверки счётчика 17.10.2026, а текущая системная дата 18.10.2026
- **THEN** под полем счётчика видна строка «Дата проверки: 17.10.2026» и метка «Просрочено»

#### Scenario: День окончания срока
- **WHEN** дата проверки счётчика совпадает с текущей системной датой
- **THEN** метка «Просрочено» не показывается

#### Scenario: Дата проверки не задана
- **WHEN** у счётчика нет даты проверки
- **THEN** показывается «Дата проверки: —» без метки «Просрочено»

#### Scenario: Поле без счётчика
- **WHEN** для поля нет счётчика
- **THEN** строка «Дата проверки: —» без метки «Просрочено»

#### Scenario: Просрочка не мешает вводу
- **WHEN** у счётчика срок проверки истёк, а пользователь вводит корректное значение и нажимает «Отправить показания»
- **THEN** показание отправляется как обычно
