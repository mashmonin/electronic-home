## Purpose

Позволяет жильцу ввести и подготовить к отправке показания счётчиков горячей и холодной воды по отдельным карточкам счётчиков своей квартиры на одном экране.

## Requirements

### Requirement: Шапка экрана с данными лицевого счёта
Экран SHALL показывать шапку с названием ТСЖ, навигацией из пунктов «Показания», «Квитанции» и «Заявки» (пункт открытой вкладки выделен основным цветом), иконками уведомлений, профиля и дома, а также блоком с адресом квартиры и номером лицевого счёта. Адрес и номер лицевого счёта MUST браться из ответа API по лицевому счёту.

#### Scenario: Отображение шапки
- **WHEN** пользователь открывает экран ввода показаний, а API вернул лицевой счёт `000000000001` с адресом «ул. Тестовая, д. Тест, кв. 1»
- **THEN** в шапке видны «ТСЖ «Комфорт»», пункты навигации «Показания», «Квитанции» и «Заявки», три иконки, адрес «ул. Тестовая, д. Тест, кв. 1» и строка «Лицевой счёт № 000000000001», а пункт «Показания» выделен основным цветом

### Requirement: Заголовок периода
Экран MUST NOT показывать заголовок «Ввод показаний». Заголовком страницы SHALL быть подпись периода «Показания за <месяц>» по требованию «Подпись периода и статус сдачи», выровненная по левому краю.

#### Scenario: Отображение периода
- **WHEN** пользователь открывает экран
- **THEN** вверху слева отображается заголовок «Показания за <месяц>», а заголовка «Ввод показаний» и прежней строки вида «Август 2026 · Передайте показания до 25 числа» нет

### Requirement: Карточки счётчиков
Экран SHALL показывать каждый счётчик воды лицевого счёта, полученный из API, отдельной карточкой в порядке ответа API. Карточка SHALL состоять из двух частей: слева — название (номер) счётчика вверху и под ним строка с датой проверки; справа — блок показаний с полем ввода и строкой «Предыдущее показание». Подпись поля MUST зависеть от типа воды: «Горячая вода, м³» для `HOT` и «Холодная вода, м³» для `COLD`. «Предыдущее показание» — значение последнего показания счётчика с тремя знаками после запятой, а при отсутствии показаний — прочерк. Экран MUST NOT группировать счётчики в стояки и MUST NOT позволять добавлять карточки вручную.

#### Scenario: Отображение счётчиков
- **WHEN** API вернул счётчики «Тест 1» (`HOT`, последнее показание `245.300`) и «Тест 2» (`COLD`, последнее показание `512.100`)
- **THEN** на экране две отдельные карточки: в первой название «Тест 1», поле «Горячая вода, м³» и «Предыдущее показание: 245.300 м³», во второй название «Тест 2», поле «Холодная вода, м³» и «Предыдущее показание: 512.100 м³»; поля пустые с подсказкой `0.000`

#### Scenario: Расположение частей карточки
- **WHEN** экран открыт в окне шириной не менее 768px
- **THEN** в каждой карточке слева видны название счётчика и под ним дата проверки, справа от них — блок показаний

#### Scenario: Два счётчика одного типа
- **WHEN** API вернул два счётчика горячей воды
- **THEN** на экране две отдельные карточки с полями «Горячая вода, м³»

#### Scenario: Нет слов «Стояк» и кнопки добавления
- **WHEN** экран открыт с любым набором счётчиков
- **THEN** на экране нет заголовков «Стояк N» и кнопки «+ Добавить стояк»

#### Scenario: Счётчик без показаний
- **WHEN** у счётчика нет показаний
- **THEN** в блоке показаний «Предыдущее показание» заменено прочерком, а проверка «не меньше предыдущего» для него не применяется

#### Scenario: Лицевой счёт без счётчиков
- **WHEN** API вернул пустой список счётчиков
- **THEN** вместо карточек показано сообщение «Для этого лицевого счёта счётчики не найдены», кнопки «Отправить показания» и «Сбросить форму» не показываются

### Requirement: Ввод показаний
Поле ввода SHALL принимать только неотрицательные числа с точкой или запятой в качестве разделителя и не более чем тремя знаками после разделителя. Показание MUST NOT быть меньше предыдущего показания этого счётчика.

#### Scenario: Допустимое значение
- **WHEN** пользователь вводит в поле значение, не меньшее предыдущего показания, например `250.125`
- **THEN** значение принимается без сообщения об ошибке

#### Scenario: Нечисловой ввод
- **WHEN** пользователь вводит в поле буквы или отрицательное число
- **THEN** поле не принимает такой ввод или показывает ошибку, а отправка блокируется

#### Scenario: Значение меньше предыдущего
- **WHEN** пользователь вводит значение меньше предыдущего показания
- **THEN** под полем отображается сообщение, что показание не может быть меньше предыдущего, а отправка блокируется

### Requirement: Отправка показаний
Кнопка «Отправить показания» SHALL отправлять введённые значения в API сохранения показаний лицевого счёта, если все заполненные поля корректны и заполнено хотя бы одно поле. В запрос MUST попадать для каждого заполненного поля номер счётчика его карточки и значение с точкой в качестве разделителя; пустые поля MUST NOT отправляться. После успешной отправки пользователь SHALL увидеть подтверждение. Во время отправки кнопка MUST быть заблокирована.

#### Scenario: Успешная отправка
- **WHEN** пользователь ввёл корректные значения хотя бы в одно поле и нажал «Отправить показания», а API ответил успехом
- **THEN** значения отправлены в API вместе с номерами счётчиков и отображается сообщение об успешной передаче показаний

#### Scenario: Пустая форма
- **WHEN** все поля пусты и пользователь нажимает «Отправить показания»
- **THEN** показания не отправляются и отображается сообщение о необходимости ввести хотя бы одно значение

#### Scenario: Есть ошибки ввода
- **WHEN** хотя бы одно поле содержит некорректное значение и пользователь нажимает «Отправить показания»
- **THEN** показания не отправляются, ошибочные поля подсвечены

#### Scenario: Заполнено одно поле из нескольких
- **WHEN** пользователь ввёл значение только в карточке счётчика «Тест 1» и нажал «Отправить показания»
- **THEN** в API отправлено одно показание — для счётчика «Тест 1»

#### Scenario: Сервер отклонил значение
- **WHEN** API отвечает ошибкой `VALUE_LESS_THAN_PREVIOUS` для счётчика
- **THEN** под полем этого счётчика отображается сообщение, что показание не может быть меньше предыдущего, введённые значения не очищаются, а «Предыдущее показание» обновляется актуальным

#### Scenario: Сервер отклонил запись по другим причинам
- **WHEN** API отвечает `400` с кодом `INVALID_VALUE` или `METER_NOT_FOUND` для счётчика
- **THEN** под полем этого счётчика отображается сообщение об ошибке («Введите число, не более трёх знаков после запятой» или «Счётчик не найден»)

#### Scenario: Конфликт при сохранении
- **WHEN** API отвечает `409`
- **THEN** отображается сообщение, что показания не сохранены из-за одновременного изменения и можно повторить отправку, а данные счёта перезапрашиваются

#### Scenario: Счёт не найден при отправке
- **WHEN** API отвечает `404`
- **THEN** отображается сообщение «Лицевой счёт не найден», введённые значения не очищаются

#### Scenario: Ошибка связи при отправке
- **WHEN** отправка завершается ошибкой сети или сервера
- **THEN** отображается сообщение «Не удалось отправить показания, попробуйте позже», введённые значения не очищаются

### Requirement: Сброс формы
Кнопка «Сбросить форму» SHALL очищать все введённые значения и сообщения об ошибках.

#### Scenario: Сброс введённых значений
- **WHEN** пользователь ввёл значения в несколько полей и нажал «Сбросить форму»
- **THEN** все поля пусты и сообщения об ошибках скрыты

### Requirement: Контакты для помощи
Экран SHALL показывать карточку «Нужна помощь?» с указанием должности контактного лица и телефоном.

#### Scenario: Отображение контактов
- **WHEN** пользователь открывает экран
- **THEN** внизу отображаются «Нужна помощь?», «Председатель правления ТСЖ» и телефон `+7 (999) 123-45-67`

### Requirement: Соответствие макету
Оформление экрана SHALL соответствовать макету Figma `02-meter-readings`: основной цвет `#ffb370`, фон страницы `#fffbeb`, белые карточки с рамкой `#f0f0f0`, белая шапка с нижней границей `#e8e8e8`. Внутреннее устройство карточки счётчика определяется требованием «Карточки счётчиков» и по решению владельца отличается от карточки «Стояк N» макета. Основной блок с карточками SHALL быть отцентрирован по горизонтали, а его ширина — ограничена 700px на широких экранах (отступы по бокам 40px). Экран MUST использовать только компоненты Ant Design.

#### Scenario: Широкий экран
- **WHEN** экран открыт в окне шириной 1440px
- **THEN** цвета, шапка и ширина блока совпадают с макетом, а карточки счётчиков устроены как описано в «Карточки счётчиков»

#### Scenario: Узкий экран
- **WHEN** экран открыт в окне шириной менее 768px
- **THEN** в каждой карточке блок показаний располагается под названием счётчика и датой проверки, горизонтальной прокрутки страницы нет

### Requirement: Загрузка лицевого счёта
Экран SHALL открываться только после входа. После входа экран собственника и жильца SHALL определять номер лицевого счёта по ответу `GET /api/auth/me`: берётся первый номер из `accounts`, параметр адресной строки `account` игнорируется. Если у пользователя нет доступных счетов, экран MUST показать сообщение «К вашей учётной записи не привязан лицевой счёт». Экран SHALL загружать информацию о лицевом счёте с API, передавая токен. Пока данные загружаются, экран SHALL показывать индикатор загрузки; содержимое экрана MUST NOT показываться до получения данных. Для администратора лицевой счёт не загружается совсем (см. требование «Экран администратора»).

#### Scenario: Номер счёта не указан
- **WHEN** вошёл собственник счёта `000000000001`, а в адресной строке нет параметра `account`
- **THEN** экран запрашивает лицевой счёт `000000000001` из `/api/auth/me` и после ответа показывает его данные

#### Scenario: Параметр счёта игнорируется
- **WHEN** собственник открывает экран с адресом `/?account=000000000002`
- **THEN** экран запрашивает счёт из `/api/auth/me`, а не счёт из параметра

#### Scenario: Номер счёта в адресной строке
- **WHEN** администратор открывает экран с адресом `/?account=000000000002`
- **THEN** запрос `GET /api/accounts/{number}` не отправляется

#### Scenario: Загрузка
- **WHEN** запрос к API ещё не завершён
- **THEN** вместо содержимого экрана показан индикатор загрузки

#### Scenario: Счёт не найден
- **WHEN** API отвечает `404` для запрошенного номера
- **THEN** экран показывает сообщение «Лицевой счёт не найден» и не показывает форму ввода показаний

#### Scenario: Ошибка связи
- **WHEN** запрос к API завершается ошибкой сети или сервера
- **THEN** экран показывает сообщение «Не удалось загрузить данные» и не показывает форму ввода показаний

#### Scenario: Нет привязанного счёта
- **WHEN** вошёл собственник или жилец, у которого `accounts` пуст
- **THEN** экран показывает сообщение «К вашей учётной записи не привязан лицевой счёт»

### Requirement: Совладельцы лицевого счёта
Экран SHALL показывать список совладельцев лицевого счёта (ФИО из ответа API) во всплывающем окне, открываемом по иконке профиля в шапке.

#### Scenario: Открытие списка совладельцев
- **WHEN** пользователь нажимает иконку профиля в шапке при двух совладельцах счёта
- **THEN** отображаются ФИО обоих совладельцев

#### Scenario: Счёт без совладельцев
- **WHEN** пользователь нажимает иконку профиля, а у счёта нет совладельцев
- **THEN** отображается сообщение «Совладельцы не указаны»

### Requirement: Обновление данных после сохранения
После успешного сохранения показаний экран SHALL заново загрузить информацию о лицевом счёте из API, очистить введённые значения и показать в карточках новые «Предыдущее показание» — значения только что сохранённых показаний. Экран при этом MUST NOT показывать полноэкранный индикатор загрузки и MUST NOT терять карточки.

#### Scenario: Предыдущее показание обновилось
- **WHEN** у счётчика «Тест 1» было предыдущее показание `245.300`, пользователь отправил `250.125` и API сохранил его
- **THEN** в карточке «Тест 1» отображается «Предыдущее показание: 250.125 м³», а поле пусто

#### Scenario: Повторная отправка
- **WHEN** после успешного сохранения пользователь вводит значение меньше только что сохранённого
- **THEN** под полем отображается сообщение, что показание не может быть меньше предыдущего

#### Scenario: Данные не удалось обновить
- **WHEN** показания сохранены, но повторная загрузка лицевого счёта завершилась ошибкой
- **THEN** отображается предупреждение, что показания сохранены, но данные экрана не обновились, и предложение обновить страницу

### Requirement: Дата проверки и статус счётчика
В левой части карточки счётчика под его названием экран SHALL показывать строку «Дата проверки: ДД.ММ.ГГГГ» с датой проверки из API; если даты нет, строка MUST показывать «Дата проверки: —». Экран SHALL сравнивать дату проверки с текущей системной датой устройства пользователя (только дата, без времени): если дата проверки раньше текущей даты, на следующей строке под датой проверки MUST показываться метка «Просрочено». В сам день даты проверки метка MUST NOT показываться, как и для счётчика без даты проверки. Статус только информирует и MUST NOT блокировать ввод и отправку показаний.

#### Scenario: Срок проверки не истёк
- **WHEN** дата проверки счётчика 01.01.2028, а текущая системная дата 18.10.2026
- **THEN** под названием счётчика видна строка «Дата проверки: 01.01.2028» без метки «Просрочено»

#### Scenario: Срок проверки истёк
- **WHEN** дата проверки счётчика 17.10.2026, а текущая системная дата 18.10.2026
- **THEN** под названием счётчика видна строка «Дата проверки: 17.10.2026», а на следующей строке под ней — метка «Просрочено»

#### Scenario: День окончания срока
- **WHEN** дата проверки счётчика совпадает с текущей системной датой
- **THEN** метка «Просрочено» не показывается

#### Scenario: Дата проверки не задана
- **WHEN** у счётчика нет даты проверки
- **THEN** показывается «Дата проверки: —» без метки «Просрочено»

#### Scenario: Просрочка не мешает вводу
- **WHEN** у счётчика срок проверки истёк, а пользователь вводит корректное значение и нажимает «Отправить показания»
- **THEN** показание отправляется как обычно

### Requirement: Подпись периода и статус сдачи
Над карточками счётчиков экран SHALL показывать подпись «Показания за <месяц>», где месяц — название месяца, в котором заканчивается текущий период передачи из ответа API (`reading_period.end`), в именительном падеже. Под подписью экран SHALL показывать строку статуса:
- если по всем счётчикам есть показания за период (`reading_period.all_submitted`): «Показания сданы, новые можно будет отправить после <день> <месяц>», где дата — последний день периода (`reading_period.end`) с месяцем в родительном падеже;
- если часть счётчиков сдана: «Часть показаний сдана. Передайте остальные до <день> <месяц>»;
- если ничего не сдано: «Передайте показания до <день> <месяц>».

Подпись SHALL быть заголовком страницы: крупный жирный шрифт (26px), выравнивание по левому краю; строка статуса SHALL идти под ней полужирным шрифтом 15px и тоже по левому краю. Экран MUST NOT сравнивать даты сам: период и статус берутся только из ответа API.

#### Scenario: Оформление и выравнивание
- **WHEN** экран открыт с любым набором счётчиков
- **THEN** «Показания за <месяц>» показано крупным жирным шрифтом (26px), строка статуса — под ним полужирным шрифтом 15px, обе строки выровнены по левому краю, по центру страницы ничего из них нет

#### Scenario: Показания ещё не сданы
- **WHEN** API вернул период с 26 сентября по 25 октября 2026 и ни один счётчик не сдан
- **THEN** показаны «Показания за октябрь» и «Передайте показания до 25 октября»

#### Scenario: Показания сданы
- **WHEN** API вернул `all_submitted` истина для периода, заканчивающегося 25 октября
- **THEN** показаны «Показания за октябрь» и «Показания сданы, новые можно будет отправить после 25 октября»

#### Scenario: Сдана часть показаний
- **WHEN** показание есть только у одного из двух счётчиков
- **THEN** показаны «Показания за октябрь» и «Часть показаний сдана. Передайте остальные до 25 октября»

#### Scenario: Первая подача после установки
- **WHEN** пользователь впервые открывает приложение, и за текущий период показаний нет
- **THEN** экран показывает подпись текущего месяца-периода и редактируемую форму

#### Scenario: Новый период
- **WHEN** пользователь открывает приложение 26 октября после сдачи показаний 18 октября
- **THEN** API вернул период «ноябрь», поля снова доступны, подпись «Показания за ноябрь», в «Предыдущее показание» стоят значения, сданные 18 октября

#### Scenario: Пропущенный период
- **WHEN** за прошлый период показания не сдавались, а сейчас идёт следующий
- **THEN** форма относится только к текущему периоду, подпись — месяц текущего периода

### Requirement: Сданные показания не редактируются
Если API вернул у счётчика `input_locked` истина, его карточка SHALL показывать показание за текущий период (`current_period_reading.value` с тремя знаками после запятой) в недоступном для правки поле, а «Предыдущее показание» — значение, предшествовавшее сданному (`current_period_reading.previous`), либо прочерк, если его нет. Такой счётчик MUST NOT попадать в запрос на сохранение. Когда заблокированы все счётчики, кнопки «Отправить показания» и «Сбросить форму» MUST оставаться на экране, но быть недоступными (disabled); если заблокирована только часть, остальные карточки и кнопки остаются доступными. После успешного сохранения экран SHALL перезапрашивать данные и показывать сданные значения заблокированными.

#### Scenario: Карточка со сданным показанием
- **WHEN** по «Тест 1» за текущий период сдано `250.125` (предыдущее `245.300`) и `input_locked` истина
- **THEN** в карточке «Тест 1» недоступное поле содержит `250.125`, строка «Предыдущее показание: 245.300 м³»

#### Scenario: Все показания сданы
- **WHEN** у обоих счётчиков `input_locked` истина
- **THEN** кнопки «Отправить показания» и «Сбросить форму» показаны, но недоступны, все поля недоступны и содержат сданные значения

#### Scenario: Сдана часть счётчиков
- **WHEN** `input_locked` истина только у «Тест 1»
- **THEN** поле «Тест 1» недоступно, поле «Тест 2» редактируемо, кнопки показаны, в запрос попадёт только «Тест 2»

#### Scenario: После отправки
- **WHEN** пользователь отправил показания и API сохранил их
- **THEN** форма остаётся на экране, поля с отправленными значениями недоступны, подпись «Показания сданы, новые можно будет отправить после 25 октября»

#### Scenario: Сервер отклонил повторную подачу
- **WHEN** API отвечает ошибкой `ALREADY_SUBMITTED` для счётчика
- **THEN** отображается предупреждение «Показания за этот период уже сданы», данные счёта перезапрашиваются, и карточка этого счётчика показывает сданное значение заблокированным

#### Scenario: Проверка отключена
- **WHEN** API вернул `input_locked` ложь у счётчика, по которому есть показание за период
- **THEN** поле редактируемо и пусто, повторная отправка возможна

### Requirement: Пометка тестового режима
Если API вернул `reading_period.enforced` ложь, экран SHALL показывать над карточками пометку «Тестовый режим: ограничение периода передачи отключено». При истинном значении пометки быть не должно.

#### Scenario: Проверка отключена на сервере
- **WHEN** API вернул `enforced` ложь
- **THEN** над карточками видна пометка «Тестовый режим: ограничение периода передачи отключено»

#### Scenario: Проверка включена на сервере
- **WHEN** API вернул `enforced` истина
- **THEN** пометки тестового режима нет

### Requirement: Профиль и выход в шапке
Меню профиля в шапке SHALL показывать логин и роль («Администратор», «Собственник», «Жилец») вошедшего пользователя и действие «Выйти» (см. спецификацию `login-screen`); у собственника и жильца также список совладельцев счёта, у администратора совладельцев нет.

#### Scenario: Меню профиля
- **WHEN** собственник открывает меню профиля
- **THEN** видны его логин, роль, совладельцы счёта и действие «Выйти»

#### Scenario: Меню профиля администратора
- **WHEN** администратор открывает меню профиля
- **THEN** видны логин, роль «Администратор» и действие «Выйти», списка совладельцев нет

### Requirement: Экран администратора
После входа администратор SHALL видеть шапку без данных лицевого счёта: название ТСЖ, навигацию из пунктов «Выставить квитанции» (открыт, выделен основным цветом), «Все показания» и «Заявки», иконки уведомлений, профиля и дома; блока с адресом и номером лицевого счёта нет. Пунктов «Показания» и «Квитанции» у администратора нет, форма ввода показаний и список квитанций ему не показываются. Ниже шапки показывается вкладка «Выставить квитанции» (см. спецификацию `receipts`), после нажатия «Все показания» — сводка показаний по квартирам (см. спецификацию `readings-overview-screen`), после нажатия «Заявки» — вкладка заявок (см. спецификацию `requests-screen`). Экран администратора MUST NOT запрашивать `GET /api/accounts/{number}`.

#### Scenario: Шапка администратора
- **WHEN** в систему вошёл администратор
- **THEN** в шапке видны «ТСЖ «Комфорт»», пункты «Выставить квитанции», «Все показания» и «Заявки», три иконки; адреса и строки «Лицевой счёт № …» нет, пунктов «Показания» и «Квитанции» нет

#### Scenario: Нет данных счёта
- **WHEN** администратор открывает экран
- **THEN** форма ввода показаний не показывается и данные лицевого счёта не запрашиваются

### Requirement: Изменение даты проверки с актом
Рядом со строкой «Дата проверки» в карточке счётчика экран SHALL показывать кнопку редактирования («Изменить») для администратора и собственника; для жильца кнопки нет. Кнопка открывает модальное окно «Изменение срока проверки» (antd) с названием счётчика, полем выбора даты (`DatePicker`, формат ДД.ММ.ГГГГ, изначально текущая дата проверки, если она есть) и областью загрузки акта проверки (файлы `pdf`, `jpg`, `jpeg`, `png` до 10 МБ, один файл). Прикрепление акта MUST быть обязательным: кнопка «Сохранить» недоступна, пока не выбраны дата и успешно загруженный файл. Файл отправляется на `POST .../verification-act-uploads` сразу при прикреплении, с показом процесса загрузки; недопустимый тип или размер отклоняются в окне без запроса, с понятным сообщением. Удаление выбранного файла в окне снова блокирует «Сохранить»; повторное прикрепление заменяет файл (на сервер уходит новый, использованным будет последний ключ). По «Сохранить» экран отправляет `PUT .../verification-date` с датой и ключом акта (ссылкой на файл в хранилище); пока запрос идёт, кнопка заблокирована. Если ответ `applied` истинный (изменил администратор), окно закрывается, данные лицевого счёта перезагружаются, карточка показывает новую дату, а метка «Просрочено» пропадает, если срок больше не истёк. Если `applied` ложный (изменил собственник), окно закрывается, а на экране показывается уведомление «Заявка П-… создана. Новая дата проверки вступит в силу после подтверждения администратором»; дата и метка в карточке остаются прежними. При ошибке окно остаётся открытым с сообщением, введённые дата и файл сохраняются. Отмена или закрытие окна ничего не меняет.

#### Scenario: Кнопка у собственника и администратора
- **WHEN** экран открыт собственником или администратором
- **THEN** в каждой карточке рядом с датой проверки есть кнопка «Изменить»

#### Scenario: Нет кнопки у жильца
- **WHEN** экран открыт жильцом
- **THEN** кнопки изменения даты проверки нет

#### Scenario: Окно открывается
- **WHEN** пользователь нажимает «Изменить» в карточке «Тест 1» с датой 01.01.2028
- **THEN** открыто окно «Изменение срока проверки» с названием «Тест 1», датой 01.01.2028 и областью загрузки акта; «Сохранить» недоступна

#### Scenario: Без файла сохранить нельзя
- **WHEN** дата выбрана, а файл не прикреплён или ещё грузится
- **THEN** «Сохранить» недоступна

#### Scenario: Файл грузится при прикреплении
- **WHEN** пользователь прикрепляет `act.pdf`
- **THEN** сразу уходит запрос загрузки; после ответа `201` файл помечен загруженным и «Сохранить» доступна

#### Scenario: Недопустимый файл
- **WHEN** пользователь выбирает `act.exe` или файл больше 10 МБ
- **THEN** в окне видно сообщение, запрос не отправляется, файл не принят

#### Scenario: Сохранение администратором
- **WHEN** администратор выбрал дату 20.05.2030, файл загружен, нажата «Сохранить», сервер ответил `200` с `applied` истинным
- **THEN** окно закрыто, карточка показывает «Дата проверки: 20.05.2030»

#### Scenario: Сохранение собственником
- **WHEN** собственник выбрал дату 20.05.2030, файл загружен, нажата «Сохранить», сервер ответил `201` с номером заявки `П-201026-0003`
- **THEN** окно закрыто, показано уведомление с номером заявки, карточка по-прежнему показывает прежнюю дату проверки

#### Scenario: Просрочка снята
- **WHEN** у счётчика была метка «Просрочено», администратор сохранил новую дату, не раньше текущей
- **THEN** после сохранения метка «Просрочено» не показывается

#### Scenario: Ошибка сохранения
- **WHEN** сервер ответил ошибкой на `PUT`
- **THEN** окно остаётся открытым, показано сообщение, дата и файл сохранены, повторное нажатие возможно

#### Scenario: Отмена
- **WHEN** пользователь закрывает окно без сохранения
- **THEN** дата в карточке прежняя, `PUT` не отправлялся
