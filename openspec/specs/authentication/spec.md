## Purpose

Описывает вход по логину и паролю, выпуск и проверку JWT, учётные записи с ролями, их привязку к лицевым счетам и защиту API токеном.

## Requirements

### Requirement: Вход по логину и паролю
Бэкенд SHALL предоставлять эндпоинт `POST /api/auth/login`, принимающий JSON `{"login": "...", "password": "..."}`. При верных данных активной учётной записи эндпоинт SHALL вернуть `200` и JSON `{"access_token": "...", "token_type": "Bearer", "expires_in": <секунды>}`. При неверном логине, неверном пароле или отключённой учётной записи эндпоинт SHALL вернуть `401` с одинаковым телом, не позволяющим отличить причину. Логин MUST сравниваться без учёта регистра. Эндпоинт MUST быть доступен без токена.

#### Scenario: Успешный вход
- **WHEN** клиент отправляет верные логин и пароль тестовой учётной записи
- **THEN** ответ `200`, в теле непустой `access_token`, `token_type` равен `Bearer`, `expires_in` равен времени жизни токена в секундах

#### Scenario: Неверный пароль
- **WHEN** клиент отправляет существующий логин с неверным паролем
- **THEN** ответ `401`, токен не выдан

#### Scenario: Неизвестный логин
- **WHEN** клиент отправляет логин, которого нет
- **THEN** ответ `401` с тем же телом, что и при неверном пароле

#### Scenario: Отключённая учётная запись
- **WHEN** клиент отправляет верные логин и пароль отключённой учётной записи
- **THEN** ответ `401`, токен не выдан

#### Scenario: Некорректный запрос
- **WHEN** в запросе нет логина или пароля либо они пустые
- **THEN** ответ `400`, токен не выдан

#### Scenario: Регистр логина
- **WHEN** клиент отправляет логин тестовой записи в другом регистре с верным паролем
- **THEN** ответ `200`

### Requirement: Содержимое токена
Выданный токен SHALL быть подписанным JWT, содержащим стандартные claims `iss`, `sub` (идентификатор учётной записи), `iat`, `exp` и claim `roles` со списком из одной роли учётной записи (`ADMIN`, `OWNER` или `RESIDENT`). Токен MUST NOT содержать пароль, его хэш и персональные данные. Срок жизни токена SHALL задаваться конфигурацией.

#### Scenario: Роль в токене
- **WHEN** выдан токен учётной записи с ролью `OWNER`
- **THEN** его `roles` равен `["OWNER"]`, а `sub` совпадает с идентификатором учётной записи

#### Scenario: Срок жизни
- **WHEN** токен выдан, а срок его жизни истёк
- **THEN** защищённые эндпоинты отвечают на него `401`

#### Scenario: Подделанный токен
- **WHEN** клиент отправляет токен с изменённым содержимым или подписанный другим ключом
- **THEN** защищённые эндпоинты отвечают `401`

### Requirement: Текущий пользователь
Бэкенд SHALL предоставлять эндпоинт `GET /api/auth/me`, возвращающий для аутентифицированного клиента JSON `{"login": "...", "role": "...", "accounts": ["000000000001", ...]}`, где `accounts` — номера доступных лицевых счетов (для `ADMIN` — все счета) в порядке возрастания. Без валидного токена эндпоинт SHALL вернуть `401`. В ответе MUST NOT быть пароля, хэша и внутренних идентификаторов.

#### Scenario: Собственник
- **WHEN** тестовый пользователь запрашивает `GET /api/auth/me` со своим токеном
- **THEN** ответ `200`, `role` равен `OWNER`, `accounts` равен `["000000000001"]`

#### Scenario: Администратор
- **WHEN** запрос выполняет учётная запись с ролью `ADMIN`
- **THEN** `role` равен `ADMIN`, а `accounts` содержит все лицевые счета системы

#### Scenario: Без токена
- **WHEN** запрос отправлен без заголовка `Authorization`
- **THEN** ответ `401`

### Requirement: Учётные записи и роли
Система SHALL хранить учётные записи с уникальным (без учёта регистра) логином, хэшем пароля, ровно одной ролью из `ADMIN`, `OWNER`, `RESIDENT`, признаком активности и признаком `is_test`. Пароль MUST храниться только в виде необратимого хэша с солью. Учётная запись SHALL быть связана с нулём или более лицевых счетов; для `OWNER` и `RESIDENT` именно эта связь определяет доступные счета.

#### Scenario: Уникальность логина
- **WHEN** добавляется учётная запись с логином, отличающимся от существующего только регистром
- **THEN** хранилище отклоняет добавление

#### Scenario: Допустимые роли
- **WHEN** добавляется учётная запись с ролью, не входящей в `ADMIN`, `OWNER`, `RESIDENT`
- **THEN** хранилище отклоняет добавление

#### Scenario: Пароль не хранится открыто
- **WHEN** проверяется содержимое хранилища учётных записей
- **THEN** пароль в открытом виде отсутствует, хранится только хэш

### Requirement: Тестовая учётная запись
В профиле `dev` система SHALL содержать одну тестовую учётную запись с логином `owner`, ролью `OWNER`, признаком `is_test`, привязанную к лицевому счёту `000000000001`. Пароль тестовой записи MUST быть описан в документации разработки, в репозитории хранится только его хэш. В профиле `prod` тестовых и иных учётных записей по умолчанию быть не должно.

#### Scenario: Вход тестовым пользователем в dev
- **WHEN** в профиле `dev` клиент входит с логином `owner` и паролем из документации
- **THEN** вход успешен, а `GET /api/auth/me` возвращает счёт `000000000001`

#### Scenario: Прод без тестовых записей
- **WHEN** миграции применены в профиле `prod`
- **THEN** в хранилище нет записей с `is_test`, вход тестовыми данными даёт `401`

### Requirement: Защита API по умолчанию
Все эндпоинты `/api/**`, кроме `POST /api/auth/login` и публикации квитанции `PUT /api/accounts/{number}/receipts/{month}` (защищена `X-Admin-Token`), SHALL требовать валидный токен в заголовке `Authorization: Bearer <token>`. Запрос без токена или с невалидным токеном SHALL получить `401` с заголовком `WWW-Authenticate: Bearer`. `/api/actuator/health` MUST оставаться доступным без токена. Сессии на сервере создаваться не должны.

#### Scenario: Запрос без токена
- **WHEN** клиент запрашивает `GET /api/accounts/000000000001` без `Authorization`
- **THEN** ответ `401`, данных счёта в теле нет

#### Scenario: Проверка работоспособности
- **WHEN** клиент запрашивает `GET /api/actuator/health` без токена
- **THEN** ответ `200`

#### Scenario: Публикация квитанции
- **WHEN** клиент отправляет `PUT` публикации квитанции с верным `X-Admin-Token` и без JWT
- **THEN** запрос не отклоняется как неаутентифицированный и обрабатывается по правилам спецификации `receipts`

#### Scenario: Нет серверной сессии
- **WHEN** клиент успешно выполнил запрос с токеном
- **THEN** ответ не содержит `Set-Cookie`
