## Purpose

Принимает от клиентов новые показания счётчиков воды по лицевому счёту и сохраняет их в цепочке показаний счётчика, проверяя правила ввода.

## Requirements

### Requirement: Сохранение показаний
Бэкенд SHALL предоставлять эндпоинт `POST /api/accounts/{number}/readings`, принимающий JSON `{"readings": [{"meter_number": "...", "value": 250.125}, ...]}` и сохраняющий каждое показание для счётчика квартиры лицевого счёта с указанным номером. При успехе эндпоинт SHALL вернуть статус `201` и JSON `{"readings": [...]}`, где каждый элемент содержит `meter_number`, `water_type`, `value`, `reading_date` и `previous` (объект с `value` и `reading_date` либо `null`). Имена полей MUST быть в `snake_case`, технических полей хранилища в ответе MUST NOT быть.

#### Scenario: Одно показание
- **WHEN** клиент отправляет `{"readings": [{"meter_number": "Тест 1", "value": 250.125}]}` на `/api/accounts/000000000001/readings`
- **THEN** ответ `201`, в `readings` одно показание со значением `250.125`, типом воды `HOT`, текущей датой сервера и `previous` со значением `245.300`

#### Scenario: Несколько показаний за один запрос
- **WHEN** клиент отправляет показания для «Тест 1» и «Тест 2» в одном запросе
- **THEN** ответ `201`, сохранены оба показания

#### Scenario: Повторное чтение после сохранения
- **WHEN** после успешного сохранения клиент запрашивает `GET /api/accounts/000000000001`
- **THEN** первым в `readings` счётчика идёт новое показание, а его `previous` указывает на прежнее последнее показание

### Requirement: Цепочка и дата показания
Дата нового показания MUST быть текущей датой сервера и MUST NOT приниматься от клиента. Предыдущим для нового показания MUST становиться последнее существующее показание того же счётчика; у счётчика без показаний новое показание становится первым и `previous` равен `null`. Признак `is_test` нового показания MUST совпадать с признаком его счётчика.

#### Scenario: Показание поверх последнего
- **WHEN** у счётчика уже есть показания и сохраняется новое
- **THEN** новое показание ссылается на последнее прежнее как на предыдущее

#### Scenario: Первое показание счётчика
- **WHEN** сохраняется показание для счётчика, у которого показаний ещё нет
- **THEN** показание сохраняется, `previous` в ответе равен `null`

#### Scenario: Дата с клиента игнорируется
- **WHEN** клиент передаёт в запросе поле `reading_date`
- **THEN** поле игнорируется, а дата показания равна текущей дате сервера

#### Scenario: Признак тестовой записи
- **WHEN** сохраняется показание для тестового счётчика
- **THEN** сохранённое показание помечено как тестовое

### Requirement: Проверка значений
Значение показания MUST быть обязательным, неотрицательным числом не более чем с тремя знаками после запятой, вмещающимся в хранилище, и MUST NOT быть меньше значения предыдущего показания этого счётчика. Равное предыдущему значение допустимо.

#### Scenario: Значение меньше предыдущего
- **WHEN** клиент отправляет значение меньше последнего показания счётчика
- **THEN** ответ `400`, в `errors` для этого счётчика код `VALUE_LESS_THAN_PREVIOUS`, ничего не сохранено

#### Scenario: Значение равно предыдущему
- **WHEN** клиент отправляет значение, равное последнему показанию
- **THEN** показание сохраняется

#### Scenario: Недопустимое значение
- **WHEN** значение отсутствует, отрицательное, имеет больше трёх знаков после запятой или не помещается в хранилище
- **THEN** ответ `400`, в `errors` для этого счётчика код `INVALID_VALUE`, ничего не сохранено

### Requirement: Проверка запроса
Запрос MUST содержать хотя бы одно показание; каждый счётчик в запросе MUST принадлежать квартире данного лицевого счёта и MUST NOT повторяться. Нарушения SHALL приводить к ответу `400` с кодами ошибок: `EMPTY_REQUEST`, `METER_NOT_FOUND`, `DUPLICATE_METER`. Эндпоинт SHALL перечислять в `errors` все найденные ошибки по всем показаниям запроса, а не только первую.

#### Scenario: Пустой запрос
- **WHEN** клиент отправляет пустой список `readings`
- **THEN** ответ `400` с кодом `EMPTY_REQUEST`

#### Scenario: Чужой или неизвестный счётчик
- **WHEN** указан номер счётчика, которого нет у квартиры этого счёта
- **THEN** ответ `400`, в `errors` для этого номера код `METER_NOT_FOUND`, ничего не сохранено

#### Scenario: Повтор счётчика в запросе
- **WHEN** один и тот же номер счётчика указан дважды
- **THEN** ответ `400`, в `errors` для этого номера код `DUPLICATE_METER`, ничего не сохранено

#### Scenario: Несколько ошибок
- **WHEN** в запросе одно показание меньше предыдущего, а другое для неизвестного счётчика
- **THEN** в `errors` перечислены обе ошибки с номерами счётчиков и кодами

### Requirement: Атомарность
Показания одного запроса SHALL сохраняться одной транзакцией: если хотя бы одно показание недопустимо, не сохраняется ни одно.

#### Scenario: Одно из показаний недопустимо
- **WHEN** в запросе из двух показаний второе меньше предыдущего
- **THEN** ответ `400`, ни первое, ни второе показание не сохранены

### Requirement: Отсутствующий счёт и конфликты
Если лицевого счёта нет, эндпоинт SHALL вернуть `404`. Если сохранение нарушает ограничения БД (например, при гонке запросов), эндпоинт SHALL вернуть `409` и не сохранять показания запроса. Параллельные запросы по одному счётчику SHALL обрабатываться последовательно, цепочка показаний MUST оставаться линейной.

#### Scenario: Неизвестный счёт
- **WHEN** клиент отправляет показания на `/api/accounts/999999999999/readings`
- **THEN** ответ `404`

#### Scenario: Одновременные запросы
- **WHEN** два запроса одновременно сохраняют допустимые показания для одного счётчика
- **THEN** оба сохраняются друг за другом, цепочка показаний счётчика остаётся линейной, ответов `5xx` нет
