## Context

Фронтенд — React 19 + TypeScript + Vite, только Ant Design; сейчас `App.tsx` показывает шапку и `HealthStatus`. Тесты — vitest + Testing Library. Источник дизайна — Figma `communal-services`, фрейм `02-meter-readings` (node `3:26`, 1440×900). Токены из макета: основной `#ffb370`, фон `#fffbeb`, текст `#262626`/`#595959`/`#8c8c8c`, плейсхолдер `#bfbfbf`, рамки `#d9d9d9`/`#f0f0f0`/`#e8e8e8`; шрифты 26/15/14/13/11px. Бэкенд API для показаний, адресов и квартир отсутствует (см. proposal.md).

## Goals / Non-Goals

**Goals:**
- Воплотить фрейм `02-meter-readings` на Ant Design с валидацией ввода, добавлением стояка, отправкой и сбросом.
- Изолировать источник данных так, чтобы позже заменить заглушку на REST-клиент без правки компонентов.

**Non-Goals:**
- Фрейм `01-auth`, вход, маршрутизация, защита страницы.
- Бэкенд, Liquibase-миграции, реальная отправка показаний.
- Расчёты начислений и история показаний.

## Decisions

- **Данные через слой `readingsApi` с заглушкой.** Компоненты получают данные и вызывают `submitReadings()` из модуля `api/readingsApi.ts`, который сейчас возвращает моковые данные (две квартиры, два стояка, значения из макета) и «успешно» разрешает промис с небольшой задержкой. Альтернатива — жёстко прописать данные в компонентах: проще, но потребует переписывания при появлении API.
- **Тема через `ConfigProvider`.** Токены `colorPrimary: #ffb370`, `colorBgLayout: #fffbeb`, радиусы и шрифты задаются в одном месте (`theme.ts`), а не inline-стилями. Альтернатива — CSS-файл с переопределениями antd: расходится с правилом «только antd» и хуже поддерживается.
- **Форма на `Form` из antd.** Поля — `Form.Item` + `Input` (`inputMode="decimal"`), правила валидации через `rules` (формат до 3 знаков, ≥ предыдущего показания). Запятая нормализуется в точку. `InputNumber` не используем: он плохо работает с запятой и пустым состоянием. Альтернатива — собственное состояние: больше кода без выигрыша.
- **Структура компонентов:** `MeterReadingsPage` (композиция), `AppHeader` (название, навигация, иконки, блок адреса с лицевым счётом), `RiserCard`, `ReadingField`, `ContactCard`. Динамические стояки — `Form.List`.
- **Макет и адаптивность.** Основной блок — `max-width: 700px`, отступ 40px (на узком экране 16px); поля стояка — `Row/Col` (`xs=24`, `md=12`). Шапка по макету: слева название ТСЖ и навигация, справа иконки и блок «адрес + лицевой счёт»; блок адреса открывает `Dropdown` выбора квартиры; на узких экранах элементы переносятся. Навигация и иконки пока не интерактивны (маршрутов нет). Иконки — из `@ant-design/icons` (входит в зависимости antd).
- **`HealthStatus` убирается со страницы** (в макете его нет); требование «Индикация состояния в интерфейсе» удаляется дельта-спекой `platform-health`. Компонент `HealthStatus` и его тест остаются в коде неиспользуемыми.
- **Подтверждения** — `message` из antd; в макете состояний успеха/ошибки нет, поэтому используются стандартные компоненты antd.

## Risks / Trade-offs

- [Макет — статичный кадр, нет состояний ошибки, загрузки, пустых данных] → стандартные состояния antd, зафиксированы в спеке; при появлении макетов правятся отдельным изменением.
- [Моковая отправка создаёт впечатление, что данные сохранены] → заглушка явно помечена в коде и в `tasks.md`; реальный API — отдельное изменение.
- [Валидация «не меньше предыдущего» может быть неверна при замене счётчика] → осознанное допущение для первой версии; правило вынесено в отдельную функцию.
- [Точное воспроизведение 1440px и цветов из макета vs. адаптивность] → сверка по ключевым размерам на 1440px, на узких экранах допустимо отличие по раскладке.
