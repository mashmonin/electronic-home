## Context

См. proposal.md. Данные берутся из листа «Лист1» книги Excel: колонка A — номер квартиры (только у первой строки квартиры), C — ХВ/ГВ, D — номер счётчика, колонки FL–GG (168–189) — накопительные показания за январь 2025 – октябрь 2026. Ячейки содержат десятичную запятую, а иногда «показание/расход». Таблицы `addresses` (уникально по улице, дому и квартире), `water_meters` (уникально по адресу и номеру) и `meter_readings` (одно показание без предыдущего на счётчик, предыдущее показание того же счётчика) уже существуют.

## Decisions

1. **SQL-файл, сгенерированный из таблицы.** Одноразовый скрипт читает лист (xlsx — это zip с XML, внешние библиотеки не нужны) и пишет `020-import-readings-2025-2026.sql`; Liquibase выполняет его через `sqlFile` с `splitStatements: false` (внутри `DO $$ … $$`). Данные в файле — значения `VALUES`, а не вызовы скрипта, поэтому миграция воспроизводима и не зависит от таблицы Excel.
2. **Три шага.** `INSERT` квартир (адрес берётся, если уже есть), `INSERT` счётчиков (`WHERE NOT EXISTS` по адресу и номеру), затем блок `DO` с циклом по показаниям в порядке «счётчик, дата»: каждое показание вставляется сразу с `previous_reading_id`, равным предыдущему вставленному или уже существующему последнему показанию счётчика. Массовая вставка без цепочки невозможна: индекс допускает только одно показание без предыдущего на счётчик.
3. **Идемпотентность.** Показание не вставляется, если у счётчика уже есть показание на эту дату.
4. **Временный адрес.** «ул. Тестовая, д. Дом» вместо тестового дома «Тест»: интеграционные тесты создают свои квартиры 90–100 на доме «Тест», и общий адрес давал бы конфликты уникальности. Настоящий адрес позже меняется одним `UPDATE` по улице и дому.
5. **Дата показания.** В таблице нет дат; 20-е число лежит внутри периода своего месяца при любом дне закрытия не меньше 20 и не уходит в будущее для октября 2026. Значение — константа генератора.
6. **Откат.** Удаляются показания и счётчики с `is_test = false` на этом адресе, затем адрес без счётчиков.

## Risks / Trade-offs

- [Реальные данные есть и в dev, и в prod] → по решению пользователя; помечены `is_test = false`.
- [Показания, уменьшающиеся при замене счётчика] → переносятся как в таблице (117 мест, список в отчёте генератора); приложение при подаче новых показаний сравнивает с последним показанием.
- [Данные в тестах] → интеграционные тесты видят дополнительные записи; проверки «в prod нет данных» заменены проверкой «нет тестовых записей».
- [Расход, пересчитанный из данных таблицы] → не переносится, расход считается как разность показаний.
