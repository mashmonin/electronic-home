## Context

В БД есть `addresses` (адрес = квартира), `accounts`, `owners` и связки; во всех таблицах есть `is_test`. Миграции Liquibase лежат в `db/changelog/changes/001…003`, тестовые данные грузятся changeSet'ами с `context: dev` (в `application-dev.yml` — `contexts: dev`, в `application-prod.yml` — `prod`). Интеграционные тесты — Testcontainers (`postgres:16`, профиль `dev`). Решения владельца: у квартиры много счётчиков воды, тип — горячая/холодная, у счётчика много показаний, в показании «предыдущий» — это ссылка на предыдущее показание. Мотивация — в proposal.md, требования — в спеке.

## Goals / Non-Goals

**Goals:**
- Таблицы `water_meters` и `meter_readings` с целостностью, выраженной в БД (FK, CHECK, UNIQUE).
- Модель, из которой «предыдущее показание» выводится ссылкой, без дублирования значения.
- Тестовые данные для `dev`, отдельно от структуры.

**Non-Goals:**
- API, JPA-сущности, перевод фронтенда со стояков-заглушек, ввод новых показаний.
- Счётчики других ресурсов (электричество, газ), тарифы, стояки, поверка, модель счётчика.
- Проверка, что значение не меньше предыдущего (правило остаётся на уровне приложения).

## Decisions

- **Схема:**
  - `water_meters(id, address_id, water_type, number, is_test)`: `address_id` `NOT NULL` → FK на `addresses`; `water_type varchar(8) NOT NULL` с `CHECK (water_type IN ('HOT','COLD'))`; `number varchar(64) NOT NULL`; `UNIQUE(address_id, number)`; индекс по `address_id` покрывается уникальным ограничением.
  - `meter_readings(id, meter_id, value, reading_date, previous_reading_id, is_test)`: `meter_id` `NOT NULL` → FK на `water_meters`; `value numeric(12,3) NOT NULL` с `CHECK (value >= 0)`; `reading_date date NOT NULL`; `previous_reading_id bigint NULL`.
  - `is_test boolean NOT NULL DEFAULT false` в обеих таблицах (как в миграции 002).
- **«Предыдущий» — ссылка `previous_reading_id`, а не копия значения.** Выбор владельца. Предыдущее значение берётся соединением с предыдущей записью; дублирования и расхождений нет. Альтернатива — колонка `previous_value`: проще читать, но значение можно записать неверно.
- **Предыдущее показание принадлежит тому же счётчику — составной FK:** `UNIQUE(id, meter_id)` в `meter_readings` и `FOREIGN KEY (previous_reading_id, meter_id) REFERENCES meter_readings(id, meter_id)`. При `NULL` в `previous_reading_id` проверка не срабатывает (`MATCH SIMPLE`), нужные случаи покрыты `NOT NULL` на `meter_id`.
- **Линейная цепочка:** `UNIQUE(previous_reading_id)` (одно показание — предыдущее максимум для одного следующего; несколько `NULL` допускаются) и частичный уникальный индекс `UNIQUE(meter_id) WHERE previous_reading_id IS NULL` (одно первое показание на счётчик). Запрет ссылки на себя — `CHECK (previous_reading_id <> id)`.
- **Тип воды — `varchar` + `CHECK`, а не enum PostgreSQL:** добавление значений не требует `ALTER TYPE`, значения читаются как строки в JPA без отдельного маппинга. Альтернатива — boolean `is_hot`: менее читаем и не расширяется.
- **Удаление без каскада (`RESTRICT`)**, как в остальной модели: адрес со счётчиками, счётчик с показаниями и показание, на которое ссылаются, удалить нельзя.
- **Дата показания — `date`**, а не `timestamp`: передача показаний происходит по дням; точное время не нужно. Если понадобится, добавляется колонкой.
- **Миграции:** `004-create-meter-tables.yaml` (структура) и `005-seed-test-meters.yaml` (сид, `context: dev`), подключаются в master. Сид использует подзапросы по адресу, номеру счётчика и значению показания, а не зашитые `id`.
- **Тестовые данные:** на кв. 1 тестового адреса — «Тест 1» (`HOT`): `230.000` (2026-08-25, без предыдущего), `245.300` (2026-09-25, предыдущее — первое); «Тест 2» (`COLD`): `498.500` и `512.100` с теми же датами. Значения `245.300` и `512.100` совпадают с «предыдущими» показаниями на экране-заглушке. Все записи `is_test = true`; откат сида — удаление строк с `is_test` в порядке «показания → счётчики».
- **Тесты:** (1) схема — каждый сценарий спеки на Testcontainers через JDBC; (2) `dev` — сид существует, цепочка корректна, всё `is_test`; (3) `contexts=prod` — таблицы пусты. `HousingSchemaIT` очищает таблицы через `TRUNCATE … CASCADE`, поэтому новые таблицы ему не мешают (список в `TRUNCATE` дополняется при необходимости).

## Risks / Trade-offs

- [Цепочку «предыдущих» можно разорвать или зациклить обновлением записей] → ограничения запрещают ветвление, ссылки на себя и чужой счётчик; циклы при вставке невозможны (ссылаться можно только на существующую строку), при `UPDATE` проверяются на уровне приложения.
- [Значение показания не проверяется относительно предыдущего (например, меньше предыдущего)] → правило «не меньше предыдущего» реализуется на уровне приложения вместе с API ввода.
- [Номер уникален только в пределах квартиры; одинаковые заводские номера в разных квартирах допустимы] → осознанно: заводские номера разных производителей могут совпасть; ужесточается отдельной миграцией при необходимости.
- [Тип воды `varchar` допускает только `HOT` и `COLD` через CHECK] → новые типы потребуют миграции, что соответствует правилу «схема только миграциями».
- [Тестовые счётчики с `is_test` попадут в выборки настоящих данных] → будущий API должен отбирать `is_test = false` в prod; в prod сид не выполняется.
- [Сид с поиском по значению показания в подзапросе чувствителен к дублям] → значения в сиде уникальны на счётчик; при ручном добавлении дублей в dev подзапрос вернёт ошибку, что видно сразу.
