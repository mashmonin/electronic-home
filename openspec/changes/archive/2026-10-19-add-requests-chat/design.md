## Context

Бэкенд — Spring Boot 4 (MVC, `JdbcClient` для простых чтений, Liquibase), вход по JWT, роли `ADMIN`/`OWNER`/`RESIDENT` проверяются `@PreAuthorize`. Фронтенд — React + antd без роутера: вкладки задаются `tabs.ts` (`allowedTab`), адрес хранит `tab` (и `account`), `apiFetch` добавляет токен и завершает сессию при `401`. Пункт «Заявки» в шапке сейчас неактивен. Нагрузка небольшая (один дом). Мотивация и состав изменений — в `proposal.md`, требования — в спецификациях.

## Goals / Non-Goals

**Goals:**
- Чат по заявке между собственником и администрацией; администратор видит все заявки и выбирает любую.
- Доступ определяется на сервере; интерфейс — удобство.
- Простота эксплуатации: без новых инфраструктурных компонентов.

**Non-Goals:**
- WebSocket/SSE, push и почтовые уведомления, счётчики непрочитанного.
- Вложения, редактирование и удаление сообщений, поиск, пагинация.
- Назначение ответственного администратора, закрытие заявок и любые статусы, доступ жильца.

## Decisions

### 1. Модель данных: две таблицы
`requests(id, account_id → accounts, author_id → users, number varchar(24) UNIQUE, created_at, last_message_at, is_test)` и `request_messages(id, request_id → requests ON DELETE CASCADE, author_id → users, body varchar(2000), created_at, is_test)`, `CHECK (length(btrim(...)) > 0)` для номера и текста. Индексы: `requests(author_id, last_message_at DESC)`, `requests(status, last_message_at DESC)`, `request_messages(request_id, id)`. `last_message_at` хранится в самой заявке (обновляется при каждом сообщении в той же транзакции): список сортируется без соединения с сообщениями. Автор заявки — учётная запись собственника, а не лицевой счёт: «заявки собственника» — это заявки этого человека; счёт нужен для отображения квартиры администратору. Вне миграций пользователей с заявками удалять нельзя (внешний ключ без каскада) — тесты, создающие таких пользователей, чистят заявки сами.
*Альтернатива:* одна таблица сообщений с «первым сообщением» как заявкой — усложняет список.

### 2. API: ресурсы, а не события
`GET/POST /api/requests`, `GET/PATCH /api/requests/{id}`, `GET/POST /api/requests/{id}/messages`. Новые сообщения читаются запросом `?after=<id>`: идентификатор растёт монотонно, поэтому курсор по `id` достаточен и дешевле метки времени. Список ограничен 200 заявками, сообщения — 500 последними (простая защита от разрастания ответа, пагинация вне рамок). Формат — `snake_case`, без `is_test`, как у остальных ответов.

### 3. Права: `@PreAuthorize` на методы, фильтр в SQL
Ролевая проверка — `@PreAuthorize("hasAnyRole('OWNER','ADMIN')")` (создание заявки — `OWNER`). Принадлежность заявки проверяет сервис одним запросом: `WHERE id = :id AND (:admin OR author_id = :userId)`. Чужая и несуществующая заявки для собственника дают одинаковый `404`, чтобы нельзя было перебирать номера; это сознательное отличие от лицевых счетов (там `403`), потому что идентификатор заявки — сквозной номер, а не пользовательский ввод. Пользователь берётся из токена (`sub`), клиентские значения не используются. ### 4. Опрос вместо WebSocket
Чат обновляется периодическими запросами: список раз в 15 с, открытый чат раз в 5 с, `?after=<последний id>` (ответ пустой почти всегда — несколько байт). Для одного дома нагрузка ничтожна (сотни запросов в минуту при полной посещаемости), а WebSocket потребовал бы аутентификации рукопожатия, sticky-проксирования в nginx, обработки обрывов и отдельных тестов. Опрос стоит поверх существующего `apiFetch`, сессия завершается по `401` как обычно. Опрос выключается при скрытой странице (`document.hidden`) и при уходе с вкладки. Переход на SSE позже не меняет контракты чтения.
*Риск:* задержка до 5 с — приемлема для обращений в ТСЖ.

### 5. Фронтенд: структура и состояние
`requests/` — `requestsApi.ts` (функции без исключений, результат — размеченный union, как у `receiptsApi`), `RequestsTab.tsx` (две панели, выбранный идентификатор, фильтр), `RequestList.tsx`, `ChatPanel.tsx` (шапка, лента, поле ввода), `NewRequestModal.tsx`, `usePolling.ts` (интервал + проверка видимости страницы + отмена). Список и сообщения лежат в состоянии компонентов (без внешнего хранилища). Фоновое обновление сливает ответ в состояние без индикатора загрузки: сообщения добавляются по `after`, список заменяется целиком, поле ввода — отдельное состояние и обновлением не затрагивается. Прокрутка вниз — только если лента была у нижнего края в момент прихода сообщений (иначе пользователь читает старое).
Вёрстка: `Grid.useBreakpoint().md` — на широком экране `Flex` с двумя колонками (список `~33%`, чат остальное, высота по экрану, прокрутка внутри колонок), на узком показывается одна колонка: список либо чат с кнопкой «К списку». Компоненты — antd: `List`, `Segmented`, `Tag`, `Input.TextArea`, `Modal`, `Form`, `Button`, `Alert`, `Empty`.

### 6. Адрес
`tabs.ts`: `Tab` получает `requests`; `tabFromSearch` знает `receipts` и `requests`; `allowedTab`: `RESIDENT` → `readings`, `OWNER` — как запрошено (кроме `upload`), `ADMIN` — `requests` либо `upload` (по умолчанию). Выбранная заявка — параметр `request`; `writeRequest(id | null)` правит адрес так же, как `writeTab`, без новых записей в истории. Для администратора вкладка по умолчанию остаётся «Выставить квитанции» (поведение прежнего изменения), «Заявки» открывается по клику или ссылке.

### 7. Администраторская страница
`AdminScreen` теперь переключается между `UploadReceiptTab` и `RequestsTab` по вкладке; шапка остаётся без данных лицевого счёта. `AppHeader` рисует пункты по ролям: `OWNER` — «Показания», «Квитанции», «Заявки»; `ADMIN` — «Выставить квитанции», «Заявки»; `RESIDENT` — «Показания»; неактивный «Заявки» исчезает.

### 8. Тестовые данные
Миграция `013` (контекст `dev`) создаёт тестовую заявку собственника `owner` по счёту `000000000001` и два сообщения (собственника и `admin`), все с `is_test`. Откат удаляет строки с `is_test`. Если `admin` в `dev` создан вручную, миграции `011`/`013` его используют по логину; если его нет (редкий случай в `dev`), сообщение администратора не вставляется.

### 9. Тесты
Бэкенд: интеграционные тесты на Testcontainers — права по ролям и автору (`404` для чужой, `403` для жильца, `401` без токена), создание и валидация, `after`, порядок списка (заявки без ответа сверху, самые давно ожидающие выше), поиск по номеру, лимит списка. Фронтенд: тесты панелей со стабом `fetch` и подменой таймеров (`vi.useFakeTimers`) для опроса; тесты адаптивности через подмену `matchMedia`. Тесты не используют `getByRole` в циклах ожидания без нужды — набор должен оставаться быстрым (сейчас ~17 с).

### 10. Номер заявки
Формат `О-ддммгг-NNNN`. Порядковая часть берётся из последовательности PostgreSQL `request_number_seq` (`nextval`) — она сквозная, потокобезопасная и не требует блокировки таблицы; повторное использование номера исключено, пропуски возможны только при откате транзакции создания (допустимо). Дата — `LocalDate.now(clock)` в часовом поясе приложения, формат `ddMMyy`; букву `О` пишем кириллической константой. Номер собирает сервис в Java (дата и формат под тестом с управляемыми часами), в БД он хранится готовой строкой с уникальным ограничением. Заполнение `NNNN`: `%04d`, после 9999 число просто становится длиннее. Темы у заявки нет: колонка `subject` удаляется, в ответах её заменяет `number`, клиентское поле темы игнорируется (Jackson не падает на неизвестных полях).
Так как миграция `012` уже применена в окружениях разработки (изменять её нельзя — контрольная сумма Liquibase), номер вводит новая миграция `014`: создаёт последовательность, добавляет колонку, заполняет номера существующим заявкам по порядку `id` (дата — дата создания в часовом поясе сессии БД, совпадающем с поясом приложения) и снимает колонку темы вместе с её ограничением.
*Альтернативы:* счётчик по дням в таблице с блокировкой — сложнее и не нужен, раз нумерация выбрана сквозной; генерировать номер на клиенте — нельзя, не уникален.

### 11. Закрытия нет, статус убран
Заявки не закрываются и не открываются: колонка `status`, её ограничение, индекс по статусу, эндпоинт `PATCH /api/requests/{id}`, ответ `409` на запись и кнопки интерфейса удаляются. Так как миграции `012`–`014` уже применены, колонку снимает новая миграция `015` (при откате возвращается `status` со значением `OPEN`). Поле `status` пропадает из ответов; вместо него в элементе списка появляется `awaiting_reply`.

### 12. Заявка без ответа, порядок списка и поиск
*Заявка без ответа* — та, чьё последнее сообщение написал собственник. Порядок считает сервер одним запросом, чтобы клиент не дублировал правило и предел в 200 заявок применялся к уже упорядоченному списку:
- сначала заявки без ответа (`last_role = 'OWNER'`), среди них по возрастанию *времени ожидания* — времени первого сообщения после последнего ответа администратора (если ответов не было, то первого сообщения заявки); дописка собственника не сбрасывает ожидание и не отодвигает заявку;
- затем остальные по `last_message_at` от новых к старым, при равенстве по `id` от новых к старым.
Время ожидания считается подзапросом по сообщениям заявки (`min(created_at)` сообщений новее последнего сообщения администратора) внутри уже существующего `LATERAL` последнего сообщения. Для одного дома это десятки-сотни заявок, и отдельная денормализованная колонка не нужна (если список вырастет, ожидание можно будет хранить в заявке и обновлять в той же транзакции, что и `last_message_at`).
Поиск — параметр `q`: сервис нормализует фрагмент (`strip`, верхний регистр, латинская `O` → кириллическая `О`), пустой превращается в «без поиска»; SQL — `position(:q IN r.number) > 0`, то есть совпадение в любом месте номера без шаблонов `LIKE` (символы `%` и `_` в запросе безопасны). Поиск идёт на сервере, а не в браузере: в списке не больше 200 заявок, поэтому найти старую заявку по номеру иначе нельзя. Права остаются в том же `WHERE`, что и у списка. Поле поиска в интерфейсе применяет `q` с задержкой 300 мс (debounce), отменяя устаревшие ответы, и очищается при создании заявки; фоновый опрос списка использует текущий `q`.
Выделение — метка «Ждёт ответа» (`Tag`), цветная полоса слева и тёплый фон строки; выбранная строка получает ещё и более тёмный фон.
*Альтернативы:* сортировать на клиенте — ломает предел и поиск; считать «без ответа» как «администратор не отвечал ни разу» — отвергнуто по решению заказчика.

## Risks / Trade-offs

- [Опрос создаёт фоновый трафик] → короткие ответы, остановка при скрытой странице; при росте — SSE, контракты чтения не меняются.
- [Задержка до 5 с между сообщениями] → допустимо для обращений в ТСЖ; обновление происходит и сразу после своей отправки.
- [Пропуски в нумерации после отката создания] → допустимы; номер не переиспользуется.
- [Рост таблицы сообщений] → индекс по `(request_id, id)`, лимит ответа; архивация — вне рамок.
- [Собственники с несколькими счетами] → заявка привязана к одному счёту при создании; окно создания спрашивает квартиру, если счетов больше одного.
- [Удаление пользователя с заявками невозможно] → намеренно: переписка не должна исчезать молча; процедура удаления пользователей в проекте пока не определена.
- [Администратор видит всё и может писать от имени «Администрации»] → автор сообщения хранится (логин администратора), собственнику показывается обобщённо.
- [Параметр `request` в адресе раскрывает идентификатор] → доступ всё равно проверяется сервером (`404` для чужих).

## Migration Plan

1. Миграции `012` (таблицы) и `013` (тестовая заявка в `dev`) применяются при старте; в `prod` таблицы пусты.
2. Бэкенд и фронтенд выкладываются вместе. Новых переменных окружения и правок nginx нет.
3. Откат: предыдущие образы; таблицы остаются и ничему не мешают.

## Open Questions

- Нужны ли непрочитанные счётчики и уведомления на почту (при росте числа заявок) — отдельное изменение, на текущие спеки и задачи не влияет.
- Сколько администраторов будут отвечать и нужно ли показывать, кто именно: сейчас собственник видит «Администрация».
