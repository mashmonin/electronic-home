## Why

Экран ввода показаний уже показывает счётчики и предыдущие показания из БД, но «Отправить показания» остаётся заглушкой: новые значения нигде не сохраняются. Нужны API и сервисная логика, которые записывают показания в `meter_readings` с правильной цепочкой «предыдущее».

## What Changes

- Новый эндпоинт `POST /api/accounts/{number}/readings`: принимает список показаний (номер счётчика и значение) по счетам квартиры лицевого счёта и сохраняет их одной транзакцией («всё или ничего»).
- Сервисная логика:
  - дата показания — текущая дата сервера;
  - предыдущее показание нового — последнее существующее показание того же счётчика (у первого показания его нет);
  - значение должно быть неотрицательным, не более трёх знаков после запятой, не меньше предыдущего;
  - счётчик должен принадлежать квартире этого лицевого счёта, один счётчик не может повторяться в запросе;
  - `is_test` нового показания наследуется от счётчика;
  - параллельные запросы по одному счётчику выполняются последовательно (блокировка счётчика), БД остаётся последней защитой.
- Ответ `201` со списком сохранённых показаний; при ошибках — `400` со списком кодов ошибок по счётчикам; неизвестный счёт — `404`; конфликт на ограничениях БД — `409`.
- JPA-сущности счётчиков и показаний получают возможность создания записей (идентификатор из БД, `is_test`).
- Эндпоинт доступен во всех профилях без авторизации (решение владельца; риск описан в design.md).
- Фронтенд не меняется: подключение «Отправить показания» к API — отдельное изменение.

## Impact

- `backend/src/main/java/com/example/electronichome/account/`: изменения в `WaterMeterEntity`, `MeterReadingEntity`, `WaterMeterRepository`; новые `MeterReadingRepository`, `ReadingService`, `ReadingValidation`, контроллер и DTO запроса/ответа; бин `Clock`.

- БД, миграции, фронтенд, nginx, зависимости не меняются.
