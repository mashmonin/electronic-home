## Context

Таблицы `water_meters` и `meter_readings` (цепочка `previous_reading_id`, составной FK, `UNIQUE(previous_reading_id)`, один «первый» на счётчик) уже есть. Чтение реализовано: сущности `WaterMeterEntity`, `MeterReadingEntity` и `AccountService` в пакете `account` (read-only, без идентификаторов-генераторов). Зависимости не включают Bean Validation. Профили `dev`/`prod` обязательны; авторизации нет. Решение владельца: эндпоинт работает во всех профилях без авторизации. Мотивация — в proposal.md, контракт — в спеке `meter-readings-api`.

## Goals / Non-Goals

**Goals:**
- Записывать новые показания с правильной цепочкой, датой и `is_test`, все-или-ничего.
- Возвращать понятные ошибки по каждому счётчику.
- Безопасно переживать параллельные запросы.

**Non-Goals:**
- Подключение фронтенда («Отправить показания» остаётся заглушкой).
- Авторизация и проверка, что вызывающий — совладелец счёта.
- Правка и удаление показаний, ввод показаний задним числом, ограничения на периоды передачи (до 25 числа).
- Новые миграции.

## Decisions

- **Ресурс — подресурс лицевого счёта: `POST /api/accounts/{number}/readings`.** Согласуется с `GET /api/accounts/{number}`; счёт задаёт квартиру, а счётчики внутри квартиры однозначно определяются номером (`UNIQUE(address_id, number)`). Тело — пакет показаний, потому что экран отправляет все поля одним действием. Альтернатива `POST /api/meters/{id}/readings`: требует отдавать клиенту внутренние идентификаторы, которые мы сознательно не раскрываем.
- **Дату ставит сервер:** `LocalDate.now(clock)`, `Clock` — бин приложения (`Clock.systemDefaultZone()`), в тестах подменяется фиксированным. Дата с клиента игнорируется: клиент не должен задним числом перестраивать историю.
- **Предыдущее показание** — последнее по `(reading_date, id)` у того же счётчика (то же правило сортировки, что при чтении, поэтому экран и запись согласованы). Запрос: `MeterReadingRepository.findFirstByMeterOrderByReadingDateDescIdDesc`.
- **Проверки в коде, без новой зависимости Bean Validation:** сервис всё равно должен собрать все ошибки списком, чего `@Valid` не даёт. Правила значения — в классе `ReadingValidation` (чистые функции, покрыты юнит-тестом): не `null`, `>= 0`, после `stripTrailingZeros` масштаб `<= 3`, число целых разрядов `<= 9` (по `numeric(12,3)`), не меньше предыдущего.
- **Ошибки:** исключение `InvalidReadingsException(List<ReadingError>)` → ответ `400` `{"errors": [{"meter_number": "...", "code": "..."}]}`; для `EMPTY_REQUEST` `meter_number` равен `null`. Коды: `EMPTY_REQUEST`, `METER_NOT_FOUND`, `DUPLICATE_METER`, `INVALID_VALUE`, `VALUE_LESS_THAN_PREVIOUS`. Некорректный JSON и тип поля — стандартный `400` Spring. Обработчик — `@ExceptionHandler` в контроллере записи, чтобы не менять поведение остальных эндпоинтов.
- **Транзакция и блокировка:** метод сервиса `@Transactional`. Счётчики запроса блокируются `PESSIMISTIC_WRITE` одним запросом `ORDER BY id` (единый порядок блокировок исключает взаимные блокировки), после чего читается последнее показание и вставляется новое. Так параллельные запросы по одному счётчику идут друг за другом и каждый видит актуальное «последнее». Альтернатива — оптимистичный ретрай по нарушению `UNIQUE(previous_reading_id)`: сложнее и даёт ложные 409.
- **Страховка БД и `409`:** при `DataIntegrityViolationException` (например, ручное вмешательство в данные) возвращается `409` без побочных эффектов (транзакция откатывается).
- **JPA для записи:** `MeterReadingEntity` получает `@GeneratedValue(strategy = IDENTITY)`, поле `isTest` (`is_test`), публичный фабричный метод/конструктор `(meter, value, readingDate, previousReading, isTest)`. `WaterMeterEntity` получает чтение `is_test`. Остальные сущности не меняются. Вставка допустима, потому что `ddl-auto: validate` проверяет только схему.
- **Структура кода (пакет `account`):** `ReadingController` (`POST`), `ReadingService`, `ReadingValidation`, `ReadingsRequest`/`ReadingsResponse` (records, `@JsonProperty` для `meter_number`, `water_type`, `reading_date`), `InvalidReadingsException`, `MeterReadingRepository`, метод блокировки в `WaterMeterRepository`. Бин `Clock` — в конфигурации приложения.
- **Ответ** строится из сохранённых сущностей (`previous` — из ссылки), порядок элементов — как в запросе.
- **Тесты:** `ReadingsApiIT` (Testcontainers, `dev`, фиксированный `Clock`): сценарии спеки, включая атомарность, ошибки списком, `is_test`, чтение после записи и параллельные запросы (несколько потоков, равные значения, итоговая цепочка линейна); юнит-тест `ReadingValidationTest`. Данные, созданные тестами, удаляются, чтобы не влиять на другие тесты (общий сид).

## Risks / Trade-offs

- [Запись без авторизации: любой клиент сможет добавить показание любому счёту, в том числе в prod] → осознанное решение владельца; до появления реальных данных в prod обязательна авторизация и проверка, что вызывающий — совладелец счёта. Показания нельзя править или удалять через API, поэтому ошибочную запись придётся исправлять в БД.
- [Показание «за сегодня» после показания с более поздней датой (ручные данные) нарушит хронологию цепочки] → предыдущее выбирается по тем же `(reading_date, id)`; проверки «дата не меньше предыдущей» нет, в нормальных условиях дата сервера не убывает.
- [Блокировка счётчика сериализует запросы по одному счётчику] → допустимо: запись редкая и короткая.
- [`Clock` с системной зоной: «сегодня» зависит от часового пояса сервера] → дата считается по часовому поясу сервера; для одного дома приемлемо, зона задаётся окружением.
- [Правила вроде «не чаще раза в день» и «до 25 числа» не проверяются] → вне рамок; в спеке не заявлены.
- [Ответ `409` при нарушении ограничений скрывает причину] → причина пишется в лог сервера, клиенту отдаётся только статус.
