## Context

См. proposal.md. Сейчас `RequestStatus` — `ACCEPTED → IN_PROGRESS → DONE → CLOSED`; `RequestService.changeStatus` двигает на шаг вперёд, а `addMessage` запрещает писать только в `CLOSED`. Переход `ACCEPTED → IN_PROGRESS` заявки `VERIFICATION` применяет акт проверки через `VerificationApplier`. Поле `kind` уже есть в БД и ответах. Сообщения пишутся через `RequestRepository.insertMessage` (JDBC), вложения через `AttachmentStorage` (вне транзакции, откат удаляет объекты).

## Goals / Non-Goals

**Goals:**
- Сервер сам решает, кто и когда может писать (по роли и статусу); фронтенд только отражает это.
- Возврат в работу и сообщение — одна транзакция.

**Non-Goals:**
- Новые роли и доступ жильцов; изменение логики акта проверки.

## Decisions

1. **Удаление `CLOSED`.** Миграция `019`: `UPDATE requests SET status = 'DONE' WHERE status = 'CLOSED'`, замена CHECK на три значения (rollback возвращает прежний CHECK). Enum `RequestStatus` теряет `CLOSED`; `next()` возвращает `IN_PROGRESS` и `DONE`, из `DONE` — `null`. Запрос `{"status":"CLOSED"}` — `400`, как неизвестное значение.
2. **Запись в чат.** Таблица прав в `RequestService.addMessage`: автор (OWNER) — `ACCEPTED`, `IN_PROGRESS`; ADMIN — только `IN_PROGRESS`; `DONE` — никто, иначе `409`. Одна функция `canWrite(role, status)`, используемая и в `reopen` (там проверяется `DONE`).
3. **Автосообщение при «Выполнено».** `changeStatus` при `IN_PROGRESS → DONE` в той же транзакции вставляет сообщение от администратора с константным текстом через `insertMessage` (обновляет `last_message_at`). Условный `UPDATE ... WHERE status = :from` остаётся защитой от гонки; сбой вставки откатывает статус.
4. **Возврат: `POST /api/requests/{id}/reopen`.** JSON и multipart, как сообщения; `@PreAuthorize("hasRole('OWNER')")`, чужая заявка — `404`, не `DONE` — `409`, пустой текст — `400`. Реализация: файлы сохраняются до транзакции (`attachments.store`), затем транзакция: условный `UPDATE status DONE → IN_PROGRESS` (0 строк → `409`), `insertMessage`, вложения; ответ `{request, message}`; при исключении вложения удаляются (по образцу `addMessage`).
5. **`awaiting_reply`.** Условие `status <> 'DONE'` вместо `'CLOSED'` в SQL списка и в `toItem`.
6. **Метки типа на фронтенде не показываются.** Тип приходит в `kind` и используется только для логики (название кнопки «Подтвердить», пояснение для администратора); `RequestList` и `ChatPanel` рядом со статусом ничего не добавляют.
7. **Панель ввода (`ChatPanel`).** Вычисляется `mode`: `write` (поле доступно), `adminWaits` (admin и `ACCEPTED` — поле заблокировано, пояснение «Чтобы писать в чат, возьмите заявку в работу / подтвердите заявку»), `done` (панель «Заявка выполнена»; у владельца ещё кнопка «Вернуть в работу»), `returning` (локальное состояние после нажатия: поле доступно, кнопка отправки «Вернуть в работу» вызывает `reopenRequest`, есть «Отмена»). Статус меняется только по ответу сервера.
8. **Тесты.** Тест, где администратор пишет в `ACCEPTED` или в `DONE`, и тест «собственник пишет в `DONE`» становятся ожиданием `409`; цепочки статусов сокращаются до `IN_PROGRESS → DONE`.

9. **Порядок и страницы.** `ORDER BY CASE status WHEN 'ACCEPTED' THEN 0 WHEN 'IN_PROGRESS' THEN 1 ELSE 2 END, created_at, id` и `LIMIT 5 OFFSET (page-1)*5` в `RequestRepository.list`; отдельный `count` по тем же условиям даёт `total`. Подзапрос времени ожидания ответа удалён, `awaiting_reply` остаётся флагом для выделения. Размер страницы фиксирован (5), `page` валидируется (`400`). Альтернатива — страницы на клиенте — отвергнута: список мог бы быть больше, чем клиент забирает за раз.
10. **Фронтенд.** `RequestsTab` хранит `page`, `fetchRequests(query, page)` возвращает `total`/`pageSize`; `Pagination` antd показывается при `total > pageSize`; новый поиск и создание заявки сбрасывают страницу на 1, пустая страница после обновления сдвигает на последнюю. Тег «Ждёт ответа» убран из `RequestList`.

## Risks / Trade-offs

- [Администратор не может ответить, не взяв заявку в работу] → намеренно по запросу; интерфейс поясняет причину.
- [Выполненная заявка с сообщением собственника после миграции из закрытых] → `awaiting_reply` ложен при `DONE`.
- [Возврат в работу не отменяет применённую дату проверки] → принятое допущение, за рамками изменения.

## Migration Plan

Применить миграцию `019`; данные сохраняются (`CLOSED → DONE`). Откат: вернуть CHECK с `CLOSED`; статусы `DONE` остаются как есть.
