## Purpose

Описывает загрузку собственников, лицевых счетов и учётных записей из ведомости начислений, чтобы у каждого собственника дома был лицевой счёт и вход в сервис.

## ADDED Requirements

### Requirement: Источник и состав загружаемых данных
Из ведомости начислений SHALL использоваться только номер лицевого счёта, ФИО собственника и номер квартиры. Остальные сведения файла (суммы долгов, оплат и начислений, площади, тарифы, показания, реквизиты ТСЖ) MUST NOT попадать в базу, в репозиторий и в выходные файлы импорта. Перед загрузкой файл проверяется на чувствительные данные (паспорт, СНИЛС, e-mail, телефоны, даты рождения); найденные сведения вне состава загрузки останавливают подготовку до решения человека.

#### Scenario: Проверка файла
- **WHEN** запускается подготовка данных
- **THEN** файл проверяется на паспорта, СНИЛС, e-mail, личные телефоны и даты рождения, а найденное сообщается без вывода значений

#### Scenario: Лишние сведения
- **WHEN** в ведомости есть суммы долга и оплаты
- **THEN** ни в базе, ни в `data/`, ни в репозитории этих сумм нет

### Requirement: Собственники и лицевые счета
Для каждой квартиры 1–138, у которой собственник физическое лицо, миграция SHALL создать собственника (`owners.full_name` — ФИО из файла), лицевой счёт (`accounts.number` — номер л/с, дополненный нулями слева до 12 знаков, как у существующих счетов) и связать счёт и собственника с уже существующей квартирой «ул. Тестовая, Дом, <квартира>» (`account_owners`, `address_owners`). Новые адреса не создаются. Миграция MUST быть повторяемой: уже существующие счета, собственники и связи пропускаются без ошибки и без дублей.

#### Scenario: Загрузка квартиры
- **WHEN** в ведомости л/с №5 принадлежит физическому лицу, а квартира 5 уже есть
- **THEN** создан собственник с этим ФИО, счёт `000000000005`, и оба связаны с квартирой 5

#### Scenario: Повторный запуск
- **WHEN** миграция выполняется на базе, где счёт `000000000005` уже есть
- **THEN** ошибки нет, второго счёта, собственника и связей не появляется

#### Scenario: Нет квартиры
- **WHEN** для л/с нет квартиры в базе
- **THEN** миграция останавливается с понятной ошибкой и ничего не записывает частично

### Requirement: Пропуск организаций и офисов
Лицевые счета организаций (ПАО, ООО и т. п. в поле плательщика) и офисов (адрес «Оф. N») SHALL быть пропущены: для них не создаются собственник, счёт, учётная запись и связи. Пропущенные л/с перечисляются в отчёте подготовки.

#### Scenario: Организация
- **WHEN** плательщик л/с — организация
- **THEN** для этого л/с ничего не создаётся, л/с указан в отчёте как пропущенный

#### Scenario: Офис
- **WHEN** адрес л/с содержит «Оф.»
- **THEN** л/с пропущен и указан в отчёте

### Requirement: Учётные записи собственников
Каждому собственнику SHALL создаваться одна учётная запись с ролью `OWNER`, включённая (`enabled`), привязанная ко всем его лицевым счетам (`user_accounts`). Логин — строчными латинскими буквами: первая буква имени + первая буква отчества + фамилия, например «Шмонин Андрей Александрович» → `aashmonin`. Транслитерация: `ё`→`e`, `й`→`y`, `ы`→`y`, `х`→`kh`, `ц`→`ts`, `ч`→`ch`, `ш`→`sh`, `щ`→`shch`, `ж`→`zh`, `ю`→`yu`, `я`→`ya`, `ъ` и `ь` опускаются, остальные буквы — по соответствию. Собственники с одинаковым ФИО считаются одним человеком и получают одну учётную запись; если логины разных людей совпали, подготовка останавливается и просит решения. Существующие логины (без учёта регистра) не изменяются.

#### Scenario: Логин по маске
- **WHEN** собственник «Шмонин Андрей Александрович»
- **THEN** логин `aashmonin`, роль `OWNER`

#### Scenario: Несколько счетов
- **WHEN** одно ФИО указано у трёх лицевых счетов
- **THEN** создана одна учётная запись, привязанная к трём счетам

#### Scenario: Совпавшие логины разных людей
- **WHEN** у двух людей с разным ФИО получается один логин
- **THEN** подготовка останавливается с сообщением, миграция не создаётся

#### Scenario: Логин уже занят
- **WHEN** пользователь с таким логином уже есть
- **THEN** он не меняется, его пароль не сбрасывается

### Requirement: Транспортные пароли
Каждой создаваемой учётной записи SHALL выдаваться случайный транспортный пароль из не менее чем 12 знаков (буквы разных регистров и цифры, без похожих знаков `0/O`, `1/l/I`), созданный криптостойким генератором. В базе хранится только BCrypt-хеш. Открытые пароли MUST NOT попадать в git, в миграцию и в журналы; они записываются один раз в локальный файл `data/` (логин, пароль, номера л/с) для передачи собственникам. Принудительной смены пароля при первом входе нет.

#### Scenario: Пароль выдан
- **WHEN** подготовка завершена
- **THEN** у каждой учётной записи есть случайный пароль в локальном файле и его BCrypt-хеш в SQL миграции, открытых паролей в SQL нет

#### Scenario: Вход
- **WHEN** собственник вводит выданные логин и транспортный пароль
- **THEN** вход выполняется как обычный вход `OWNER`, и он видит только свои счета

### Requirement: Персональные данные вне репозитория
В git SHALL храниться только changeset Liquibase и скрипт-генератор без ФИО, логинов, паролей и хешей. SQL с данными собственников и файл с открытыми паролями создаются в каталоге `data/` (в `.gitignore`) и подключаются при развёртывании. Без этого файла и без включённого контекста импорта обычные запуски (`dev`, `prod`, тесты) миграцию не выполняют и не падают.

#### Scenario: Репозиторий
- **WHEN** проверяется дифф коммита с миграцией
- **THEN** в нём нет ФИО собственников, логинов, паролей и хешей

#### Scenario: Обычный запуск
- **WHEN** приложение запускается без контекста импорта
- **THEN** changeset импорта не выполняется, ошибок нет
