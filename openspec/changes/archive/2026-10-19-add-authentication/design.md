## Context

Бэкенд — один Spring Boot 4 сервис (Java 21, Spring MVC, JPA, Liquibase), фронтенд — React + antd без роутера, за nginx с TLS. Сейчас безопасности нет: контроллеры `account`/`receipt` принимают номер счёта из пути и доверяют ему. Единственная защита — `X-Admin-Token` на публикации квитанций. Нагрузка: небольшой дом, порядка 150 одновременных пользователей. Мотивация и состав изменений — в `proposal.md`, требования — в спецификациях.

## Goals / Non-Goals

**Goals:**
- Вход по логину и паролю, stateless-аутентификация по JWT, роли `ADMIN`/`OWNER`/`RESIDENT` и проверка доступа к лицевому счёту на сервере.
- Токен и роли в формате, который не придётся ломать при переходе на внешний OIDC-провайдер.
- Минимальная правка существующих контроллеров и тестов.

**Non-Goals:**
- Собственный OIDC-провайдер, Authorization Code flow, SSO, refresh-токены, отзыв токенов.
- Самообслуживание пользователей (регистрация, сброс пароля, смена пароля) и админка пользователей.
- Защита от перебора паролей (rate limit, блокировки) — отдельное изменение.
- Перевод публикации квитанций с `X-Admin-Token` на роль `ADMIN`.

## Decisions

### 1. Один сервис, без отдельного сервиса авторизации
Авторизация живёт в том же бэкенде отдельным пакетом `auth`. Для 150 одновременных пользователей и одной БД отдельный сервис добавил бы контейнер, сетевой вызов на каждый запрос (или кэш токенов), второй деплой и рассинхронизацию схемы, ничего не давая по нагрузке: проверка HS256-подписи занимает микросекунды, BCrypt на входе — десятки миллисекунд и нужен только при логине.
*Альтернатива:* Keycloak/иной IdP. Отвергнуто сейчас как избыточное, но дверь оставлена открытой (решение 2).

### 2. Собственные JWT, совместимые с OIDC, а не полноценный OIDC
OIDC — это протокол между клиентом и провайдером (discovery, authorization code, `id_token`, JWKS). Без внешнего провайдера реализовывать его самим не нужно: форма входа остаётся нашей, `POST /api/auth/login` отдаёт access-токен. Токены делаем в «OIDC-стиле»: стандартные claims `iss`, `sub`, `iat`, `exp`, роли в claim `roles`. Бэкенд при этом использует `spring-boot-starter-oauth2-resource-server` — стандартный путь проверки Bearer JWT. Если позже появится Keycloak, меняются только источник токена (`issuer-uri` / JWKS вместо локального ключа) и конвертер claim → роли; контроллеры, правила доступа и фронтенд (кроме экрана входа) остаются прежними.
*Альтернатива:* самописный фильтр с JJWT. Отвергнуто: больше собственного security-кода и нет пути к IdP.

### 3. HS256 с общим секретом
Выпускает и проверяет токен один и тот же процесс, поэтому симметричный ключ проще пары RSA (нет хранения и ротации ключевых пар). Секрет — `auth.jwt.secret` из окружения (`JWT_SECRET`), ≥ 32 байт; в `prod` без значения по умолчанию, проверка длины при старте (`@Validated` свойства или fail-fast бин по образцу `ProfileGuard`). Кодировщик/декодировщик — `NimbusJwtEncoder`/`NimbusJwtDecoder`. При появлении второго потребителя токенов — переход на RS256 + JWKS.

### 4. Модель данных: роль в записи пользователя, счета — связью
Миграция `009`: таблица `users(id, login, password_hash, role, enabled, is_test)` с `CHECK role IN ('ADMIN','OWNER','RESIDENT')` и уникальным индексом по `lower(login)`; таблица `user_accounts(user_id, account_id, is_test)` с уникальной парой. Одна роль на запись — этого требует текущая постановка («смаппить учётную запись с ролью»); отдельная таблица ролей даёт гибкость, которой пока нет. `ADMIN` не нуждается в `user_accounts`: получает все счета. Миграция `010` (контекст `dev`) добавляет пользователя `owner` с BCrypt-хэшем и привязкой к счёту `000000000001`, откат — `DELETE ... WHERE is_test`, по образцу `003-seed-test-data`. Пароль тестовой записи фиксируется в README (хэш в репозитории — только хэш). Связь с `owners` (совладельцы счёта, для отображения ФИО) не вводим: это разные сущности — человек из договора и учётная запись для входа.

### 5. Роли → полномочия на сервере
`JwtAuthenticationConverter` превращает claim `roles` в `GrantedAuthority` `ROLE_ADMIN`/`ROLE_OWNER`/`ROLE_RESIDENT`. Доступ к счёту проверяет бин `AccountAccess` (`canAccess(authentication, number)`), вызываемый из `@PreAuthorize` на методах контроллеров (`@EnableMethodSecurity`):
- `ADMIN` — всегда `true`;
- `OWNER`/`RESIDENT` — номер счёта входит в список привязанных (запрос в БД по `sub`, один небольшой запрос на вызов);
- квитанции дополнительно `hasAnyRole('ADMIN','OWNER')`.

`@PreAuthorize` срабатывает до тела метода и раньше поиска счёта, что даёт требуемый порядок «401 → 403 → 404» и единое `403` для чужих и несуществующих счетов у `OWNER`/`RESIDENT`. Права не кладутся в токен списком счетов: токен остаётся коротким, а изменение привязки действует сразу.
*Альтернатива:* URL-правила в `SecurityFilterChain` — не умеют сверять переменную пути со связью в БД без самописных matcher'ов.

### 6. Цепочка безопасности
`SecurityFilterChain`: `csrf` отключён (нет cookie-сессий, только Bearer), `sessionCreationPolicy(STATELESS)`, `cors` включён. Правила: `POST /api/auth/login`, `GET /api/actuator/health` и `PUT /api/accounts/*/receipts/*` — `permitAll` (последняя по-прежнему проверяет `X-Admin-Token` в сервисе); остальное `/api/**` — `authenticated`. 401 формирует стандартный `BearerTokenAuthenticationEntryPoint` (с `WWW-Authenticate`), 403 — пустым телом. В `prod` включён `server.error.include-*: never`, дополнительных деталей не раскрываем. `DevCorsConfig` остаётся; заголовок `Authorization` разрешён по умолчанию (`allowedHeaders` не ограничены), поэтому правка сводится к проверке.

### 7. Логин
`AuthService` ищет пользователя по `lower(login)`, сверяет пароль `BCryptPasswordEncoder` (стоимость по умолчанию). Для неизвестного логина всё равно выполняется сравнение с фиктивным хэшем, чтобы время ответа не выдавало существование логина. Любой отказ — одинаковый `401` без тела причин. Срок жизни токена — `auth.jwt.ttl` (по умолчанию 8 часов: рабочий день без перелогина; refresh-токены не нужны для такого приложения).

### 8. Фронтенд: токен в `sessionStorage`
Модуль `auth/session.ts` хранит токен в `sessionStorage`, `auth/AuthProvider` (React-контекст) держит состояние `anonymous | authenticated(me)`. Общая функция `apiFetch` добавляет `Authorization` и при `401` (кроме входа) вызывает сброс сессии с сообщением «Сессия истекла…». `fetchAccount`, `readingsApi`, `receiptsApi` переходят на `apiFetch`. Скачивание квитанции сейчас сделано ссылкой `<a href download>` (`ReceiptsTab`), которая не несёт заголовок `Authorization`, поэтому оно переводится на `apiFetch` → blob → временная ссылка `URL.createObjectURL`. Роутер не добавляем: условный рендер `LoginPage` / `MeterReadingsPage` в `App`.
*Альтернатива:* HttpOnly cookie с токеном — устойчивее к краже через XSS, но требует CSRF-защиты и усложняет CORS в dev; для текущего размера системы и при отсутствии стороннего JS выбран `sessionStorage` (живёт только в вкладке, не уходит в `localStorage`). Решение пересматривается при появлении внешних скриптов.

### 9. Тесты
Бэкенд: `TestTokens` (хелпер, выпускающий токен нужной роли через тот же `JwtEncoder`) и создание пользователей в IT-тестах; существующие IT переводятся на аутентифицированные запросы, добавляются `AuthApiIT` (вход, `me`, истёкший/поддельный токен), `AccessControlIT` (матрица ролей, порядок 401/403/404, `X-Admin-Token` без JWT), `UserSchemaIT` (ограничения). Фронтенд: vitest — форма входа, обработка `401`, выход, скрытие вкладки для `RESIDENT`.

## Risks / Trade-offs

- [Кража токена через XSS из `sessionStorage`] → нет сторонних скриптов, токен живёт 8 часов и только во вкладке; в планах — CSP и/или переход на HttpOnly cookie.
- [Нет отзыва токенов: отключённого пользователя токен действует до `exp`] → короткий TTL; при проверке доступа к счёту можно дополнительно читать `enabled` (одним запросом вместе со связью) — делаем это в `AccountAccess`, чтобы отключение действовало сразу.
- [Перебор паролей] → не входит в изменение; nginx `limit_req` на `/api/auth/login` — первый кандидат следующей итерации.
- [Утечка или слабость `JWT_SECRET`] → fail-fast на длину ≥ 32 байт, секрет только из окружения, не в репозитории.
- [BREAKING для существующих клиентов API] → фронтенд обновляется вместе с бэкендом; публикация квитанций скриптами не затронута.
- [`403` вместо `404` для чужих счетов у `OWNER`/`RESIDENT` скрывает опечатки в номере] → осознанный компромисс ради невозможности перебора номеров.

## Migration Plan

1. Добавить миграции `009`–`010`; в `dev` тестовый пользователь появится сам, в `prod` таблицы пусты.
2. Задать `JWT_SECRET` в окружении prod (`docker-compose.prod.yml`) до выкладки: без него приложение не стартует.
3. Выкатить бэкенд и фронтенд одновременно (один `docker compose up`).
4. До появления интерфейса управления пользователей первые учётные записи в `prod` создаются вручную SQL-скриптом с BCrypt-хэшем (процедуру описать в README).
5. Откат: вернуть предыдущий образ; таблицы `users`/`user_accounts` остаются и ничему не мешают.
