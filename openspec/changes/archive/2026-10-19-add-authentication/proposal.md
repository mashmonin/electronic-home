## Why

Сейчас API полностью открыт: любой, кто знает номер лицевого счёта, видит данные квартиры, подаёт показания и скачивает квитанции. Нужны аутентификация по логину и паролю и роли (администратор, собственник, жилец), чтобы каждый пользователь получал только свои полномочия. Без этого сервис нельзя выводить в прод.

## What Changes

- Бэкенд получает Spring Security: stateless-режим, аутентификация по JWT (Bearer), пароли в BCrypt.
- Новые эндпоинты: `POST /api/auth/login` (логин + пароль → JWT) и `GET /api/auth/me` (текущий пользователь, роль, доступные лицевые счета).
- Три роли: `ADMIN` (администратор), `OWNER` (собственник), `RESIDENT` (жилец). Роль учётной записи попадает в JWT как claim `roles`, и по нему выдаются полномочия.
- Учётная запись привязывается к лицевым счетам; собственник и жилец видят и меняют данные только своих счетов, администратор — любых.
- Одна тестовая учётная запись (только профиль `dev`, собственник счёта `000000000001`); в `prod` пользователей по умолчанию нет.
- Фронтенд: форма входа (логин и пароль, Ant Design), хранение токена, выход, перенаправление на форму при `401`; номер счёта берётся из `/api/auth/me`, а не из URL.
- **BREAKING**: `GET /api/accounts/{number}`, `POST /api/accounts/{number}/readings`, `GET /api/accounts/{number}/receipts[/{month}]` без токена отвечают `401`. Эндпоинт публикации квитанций по-прежнему защищён `X-Admin-Token` и работает без JWT. `/api/actuator/health` остаётся открытым.
- Отдельный сервис авторизации и внешний OIDC-провайдер не вводятся (см. design.md); токены выпускает сам бэкенд в формате, совместимом с OIDC (стандартные claims), чтобы позже заменить его на Keycloak без переделки API.

## Capabilities

### New Capabilities
- `authentication`: вход по логину и паролю, выпуск и проверка JWT, эндпоинты `/api/auth/login` и `/api/auth/me`, модель учётных записей, ролей и привязки к лицевым счетам, тестовая учётная запись.
- `authorization`: роли `ADMIN`/`OWNER`/`RESIDENT`, матрица полномочий на эндпоинты API и проверка доступа к лицевому счёту.
- `login-screen`: форма входа на фронтенде, хранение сессии, выход, обработка `401`.

### Modified Capabilities
- `account-info-api`: эндпоинт требует аутентификации и доступа к счёту (`401`/`403`).
- `meter-readings-api`: сохранение показаний требует аутентификации и доступа к счёту; жилец может подавать показания.
- `receipts`: список и скачивание требуют аутентификации и доступа к счёту; жильцу недоступны; публикация по `X-Admin-Token` не меняется.
- `meter-readings-screen`: экран открывается только после входа, счёт определяется по учётной записи, в шапке появляется выход.
- `runtime-profiles`: секрет подписи JWT обязателен в `prod` (без значения по умолчанию), в `dev` задан по умолчанию.

## Impact

- Backend: зависимости `spring-boot-starter-security`, `spring-boot-starter-oauth2-resource-server`; пакет `auth` (контроллер, сервис выпуска токена, сущности пользователей), `SecurityConfig`; Liquibase-миграции `009`–`010` (таблицы `users`, `user_accounts`, сид тестового пользователя в контексте `dev`); конфигурация `auth.jwt.*` в `application*.yml`; обновление `DevCorsConfig` (заголовок `Authorization`).
- Существующие интеграционные тесты (`AccountApiIT`, `ReadingsApiIT`, `ReceiptsApiIT` и др.) нужно перевести на аутентифицированные запросы.
- Frontend: экран входа, модуль сессии, обёртка над `fetch` с заголовком `Authorization`, правки `MeterReadingsPage`/`AppHeader`, тесты.
- Infra: переменная окружения `JWT_SECRET` в `docker-compose.prod.yml`; nginx менять не требуется (заголовок `Authorization` проксируется по умолчанию).
- Вне рамок: регистрация и восстановление пароля, управление пользователями через UI/API, refresh-токены, ограничение частоты попыток входа, внешний OIDC-провайдер, перевод публикации квитанций на роль `ADMIN`.
