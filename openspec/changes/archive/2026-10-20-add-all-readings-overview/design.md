## Context

См. proposal.md. Показания лежат в `meter_readings` (значение, дата, ссылка на предыдущее показание того же счётчика), счётчики — в `water_meters` (адрес, тип воды), квартиры — в `accounts` + `addresses`. Период передачи считает `ReadingPeriod.containing(date, closingDay)` (по умолчанию день закрытия 25; период называется по месяцу окончания). Администратор уже имеет вкладки «Выставить квитанции» и «Заявки»: вкладка — значение `Tab` в `tabs.ts`, адрес `?tab=…`. Вкладка квитанций уже сделана как антд-`Collapse`. Остальные модули без миграций читают БД через `JdbcClient` (`AccountListController`).

## Goals / Non-Goals

**Goals:**
- Администратор за пару кликов видит, кто за месяц сдал показания, а кто нет, и сами значения.
- Нагрузка пропорциональна открытому месяцу, а не всей истории.

**Non-Goals:**
- Редактирование показаний, выгрузка, фильтры по статусу сдачи, графики, постраничность, другие услуги.

## Decisions

1. **Аккордеон «месяц → квартира» (по выбору пользователя), а не таблица с фильтрами.** Единый стиль с вкладкой квитанций; внешний `Collapse` — месяцы, внутри панели месяца — вложенный `Collapse` квартир. Альтернатива (одна таблица с быстрыми фильтрами) удобнее для сравнения, но выбрана не была.
2. **Два эндпоинта, данные месяца — лениво.** `GET /api/readings/periods` отдаёт список месяцев (без значений), `GET /api/readings?month=` — квартиры одного месяца. Так первый экран лёгкий, а значения грузятся при раскрытии (и кэшируются в состоянии вкладки). Альтернатива «одним запросом всё за все месяцы» растёт с историей.
3. **Месяц = период передачи.** `month` (`ГГГГ-ММ`) — месяц окончания периода; границы считает `ReadingPeriod` (конец = `month` + день закрытия, начало = конец минус месяц плюс день). Для списка месяцев в SQL: `CASE WHEN extract(day FROM reading_date) <= :closing THEN date_trunc('month', reading_date) ELSE date_trunc('month', reading_date) + interval '1 month' END`, плюс текущий период (по `Clock`); дубли убираются, сортировка по убыванию. Месяц позже текущего периода — `400`.
4. **Запрос месяца.** Один SQL: квартиры (`accounts` + `addresses`) × счётчики (`water_meters` по адресу) `LEFT JOIN LATERAL` на последнее показание счётчика в границах периода (`reading_date BETWEEN :start AND :end ORDER BY reading_date DESC, id DESC LIMIT 1`) и `LEFT JOIN` на предыдущее показание (`previous_reading_id`). Расход считается в сервисе как разность значений (`BigDecimal`, 3 знака). Группировка в квартиры и счётчики — в сервисе; квартиры без счётчиков не попадают в выборку (INNER JOIN со счётчиками). Сортировка квартир: числовой префикс номера (`NULLIF(regexp_replace(apartment, '\D', '', 'g'), '')::int`), затем строка, затем номер счёта; счётчиков — по номеру. Индекс `idx_meter_readings_meter_date` подходит.
5. **Права.** `@PreAuthorize("hasRole('ADMIN')")` на контроллере `ReadingsOverviewController` (путь `/api/readings`, не пересекается с `POST /api/accounts/{number}/readings`).
6. **Фронтенд.** `Tab` получает значение `'all-readings'` (адрес `?tab=all-readings`); `allowedTab` для ADMIN допускает `upload`, `all-readings`, `requests`; остальные роли такой вкладки не открывают. `AppHeader` показывает пункт «Все показания» только администратору. Компонент `AllReadingsTab`: загрузка месяцев, `Collapse` месяцев, `MonthPanel` (ленивая загрузка и кэш по месяцу, повтор при ошибке), `Collapse` квартир с метками `Tag` (зелёная/жёлтая/красная) и `Table` счётчиков; поиск фильтрует квартиры на клиенте. Названия месяцев — `toLocaleString('ru-RU', { month: 'long', year: 'numeric' })` с заглавной буквой без суффикса « г.» — или собственная таблица названий, чтобы не зависеть от локали окружения тестов.
7. **Тестовые данные.** Dev-сид уже содержит счётчики «Тест 1/2» с показаниями на квартире 1; интеграционные тесты создают свои квартиры, счётчики и показания и чистят их.

## Risks / Trade-offs

- [Много квартир в одном месяце, длинный ответ] → дом один (десятки квартир), постраничность вне рамок; при росте — добавить фильтры или пагинацию.
- [Показание, поданное в день закрытия, относится к текущему месяцу] → границы периода едины с экраном собственника (тесты на граничные даты).
- [Несколько показаний за месяц] → берётся последнее; правило повторной подачи запрещает такое, но данные могли попасть миграциями.
- [Квартиры с одинаковым номером в разных домах/улицах] → в системе один дом; сортировка использует номер лицевого счёта как запасной ключ.

## Migration Plan

Миграции не нужны. Откат — удалить эндпоинты и вкладку.
