## Context

См. proposal.md. Сейчас `water_meters.verification_date` — nullable `date`, пишется только миграциями; `WaterMeterEntity` без сеттеров. S3-хранилище (SeaweedFS) уже есть: `ObjectStore`, `ObjectKeys` (ключи — UUID сервера), `SpooledUpload` (чтение в temp-файл с лимитом, размер и SHA-256), `StorageExceptionHandler`. Спека `object-storage` запрещает публичные и предподписанные ссылки, поэтому «ссылка на файл», которую фронтенд отправляет в запросе изменения срока, — это ключ объекта, выданный сервером при загрузке, а не URL хранилища. Права доступа — `@PreAuthorize` + `@accountAccess.canAccess`; роль RESIDENT нужно исключать явно (как в квитанциях).

## Goals / Non-Goals

**Goals:**
- Двухшаговый поток: загрузка файла в S3 при прикреплении → изменение даты со ссылкой на файл, атомарное в БД.
- Мягкое удаление предыдущего акта через `is_archive`, не более одного действующего акта у счётчика (гарантия на уровне БД).
- Не оставлять мусор в S3 от загрузок, которые не довели до сохранения.

**Non-Goals:**
- Просмотр/скачивание актов вне чата и история в интерфейсе; физическое удаление архивных объектов.
- Откат статуса назад и отклонение заявки о проверке; уведомления по почте.
- Изменение остальных полей счётчика.

## Decisions

1. **Два эндпоинта, а не один multipart.** Загрузка `POST .../verification-act-uploads` кладёт файл в S3 и возвращает `file_key`; `PUT .../verification-date` принимает JSON с датой и `act_file_key`. Так соответствует требованию «закинуть в S3 при прикреплении, ссылку отправить в запросе». Альтернатива (один multipart `PUT`) проще и не оставляет сирот, но не даёт загрузки при прикреплении и прогресса в окне; отвергнута по запросу.
2. **Промежуточная таблица `meter_act_uploads`** (`object_key` PK, `meter_id`, `user_id`, `file_name`, `content_type`, `size_bytes`, `sha256`, `created_at`, `is_test`). Загрузка пишет объект в S3, затем строку; при сбое записи объект удаляется. Изменение срока в одной транзакции: блокирует счётчик (`SELECT ... FOR UPDATE` по строке `water_meters`), находит и удаляет строку загрузки (проверяя счётчик, пользователя, срок 24 часа), архивирует действующий акт, вставляет новый, обновляет дату. Это закрывает повторное использование ключа и подмену ключа чужого акта. Альтернатива — класть загрузки сразу в `meter_verification_acts`; отвергнута, чтобы в основной таблице не было «неподтверждённых» записей и ключа `is_archive` из трёх состояний.
3. **Таблица `meter_verification_acts`**: `id`, `meter_id` FK → `water_meters` (cascade), `object_key varchar(36)` unique, `file_name`, `content_type`, `size_bytes` (>0), `sha256`, `verification_date date not null`, `created_at timestamptz`, `created_by` (id пользователя), `is_archive boolean not null default false`, `is_test`. Частичный уникальный индекс `uq_meter_acts_active ON (meter_id) WHERE NOT is_archive` гарантирует один действующий акт. Миграция `017-create-meter-verification-acts.yaml` (+ include в master, rollback — drop таблиц).
4. **Мягкое удаление в одной транзакции:** сначала `UPDATE ... SET is_archive = true WHERE meter_id = ? AND NOT is_archive`, затем вставка нового (порядок важен из-за частичного индекса). Объекты S3 архивных актов не удаляются.
5. **Бакет актов** — отдельный (`storage.s3.meter-acts-bucket`, `S3_METER_ACTS_BUCKET`), чтобы не смешивать с чатами и квитанциями; создаётся лениво, как остальные (`ensureBucket`).
6. **Проверка файла:** извлечь из `request.AttachmentTypes` проверку «расширение → тип + сигнатура» в общий класс пакета `storage` (с параметром разрешённого набора расширений); для актов набор `pdf, jpg, jpeg, png`, лимит 10 МБ (`SpooledUpload`). Имя файла — через ту же очистку, что у вложений.
7. **Права:** `@PreAuthorize("hasAnyRole('ADMIN','OWNER') and @accountAccess.canAccess(authentication, #number)")`. Счётчик ищется по `(number счёта, meterNumber)`, иначе `404`.
8. **Очистка:** `@Scheduled(fixedDelay = 1h)` удаляет загрузки старше 24 часов: для каждой — `ObjectStore.delete`, затем строка; ошибка одной не прерывает остальные (лог). Требуется `@EnableScheduling` (если ещё не включён). Используется `Clock` для проверки сроков (тестируемость).
9. **Изменяемая дата:** у `WaterMeterEntity` появляется метод смены даты, доступный только сервису; JPA-репозиторий получает блокирующий поиск `findForUpdate`.
10. **Фронтенд:** компонент `VerificationDateModal` (antd `Modal`, `DatePicker` с `dayjs`, `Upload` с `beforeUpload`/`customRequest` на загрузку в `apiFetch`-обёртке), состояние «файл → file_key», кнопка «Сохранить» активна при дате и загруженном файле. После `PUT` вызывается уже существующая перезагрузка данных счёта. Кнопка «Изменить» показывается по роли из контекста авторизации. Если `dayjs` ещё нет в зависимостях (antd тянет его сам) — используется как есть.

11. **Черновик вместо немедленного применения (для собственника).** `PUT verification-date` для OWNER в одной транзакции: потребляет загрузку, создаёт `meter_verification_acts` с `is_draft = true`, `verification_date` (дата хранится в акте), `request_id`, и вызывает `RequestService.createVerificationRequest(...)` (заявка вида `VERIFICATION`, первое сообщение «Добрый день! Выполнил проверку счетчика №{number}», вложение). Для ADMIN: без заявки, акт сразу действующий (`is_draft = false`) через тот же метод «применить акт». Метод применения один и вызывается из обоих мест — «блокировка счётчика → архив действующего → снять `is_draft` → обновить дату». Альтернатива — хранить черновик без отдельного признака и применять по статусу заявки; отвергнута по запросу (явная метка `is_draft`).
12. **Индексы:** частичный уникальный индекс по `meter_id` для `NOT is_draft AND NOT is_archive`; черновиков может быть много.
13. **Копирование акта в бакет вложений:** `ObjectStore.open` из бакета актов → `put` в бакет вложений под новым UUID, запись в `request_attachments` (имя, тип, размер, SHA-256 с акта). Копирование делается до коммита; при откате транзакции скопированный объект удаляется (по образцу `deleteOnRollback` в `ReceiptService`). Общий объект между бакетами не используется, чтобы чат и акты жили независимо.
14. **Статусная модель.** `RequestStatus` (enum, колонка `status varchar(16) not null default 'ACCEPTED'` + CHECK) и `RequestKind` (`kind varchar(16) not null default 'GENERAL'` + CHECK) — миграция `018`; старые заявки получают значения по умолчанию. Переходы — таблица «следующий допустимый» (`ACCEPTED→IN_PROGRESS→DONE→CLOSED`), смена через условный `UPDATE requests SET status = :next WHERE id = :id AND status = :current`, чтобы параллельные запросы не проходили оба (проигравший — `409`). `PUT /api/requests/{id}/status` — только ADMIN. Перевод `ACCEPTED→IN_PROGRESS` заявки `VERIFICATION` вызывает в той же транзакции метод применения акта (п. 11); при исключении статус не меняется.
15. **Номер заявки.** `RequestNumbers.next(kind)`: буква `О`/`П`, общая последовательность `request_number_seq`. Поле `varchar(24)` и поиск по фрагменту не меняются.
16. **Закрытая заявка:** запись сообщений проверяет статус (`409`); `awaiting_reply` ложен для `CLOSED`. Опрос/автообновление фронтенда продолжают работать (читать закрытую можно).
17. **Граница модулей:** сервис счётчиков зависит от публичного метода `RequestService` (создание заявки вида `VERIFICATION` по готовым данным и копирование вложения), а не от репозиториев заявок; `RequestService` получает от модуля счётчиков вызов «применить акт» через небольшой интерфейс, чтобы не было циклической зависимости пакетов.
18. **Фронтенд, статусы:** метки и кнопки выводятся из `status` и `kind` ответа; обновление после перехода — по ответу `PUT` с элементом заявки.

## Risks / Trade-offs

- [Сироты в S3 от неиспользованных загрузок] → фоновая очистка через 24 часа; объекты архивных актов сознательно остаются (мягкое удаление).
- [Рассинхрон S3 и БД при падении между записью объекта и строкой] → объект удаляется при сбое записи; редкий остаток подберёт очистка не может (строки нет) — принято, объём пренебрежимо мал; в сообщение лога пишется ключ.
- [Одновременные изменения срока] → блокировка строки счётчика и частичный уникальный индекс; проигравший получает `409` из `DataIntegrityViolationException`, как у показаний.
- [Один пользователь грузит несколько файлов] → использован будет только переданный ключ, остальные уйдут в очистку.
- [Срок меняется только после подтверждения администратором] → собственник не может изменить срок в обход проверки; акт обязателен и сохраняется в истории.
- [Заявка о проверке никогда не подтверждена] → черновик остаётся навсегда (отклонение вне рамок); срок счётчика не меняется.
- [Возврат статуса заявок, ранее удалённого миграцией 015] → новая миграция `018` добавляет колонки заново, старые заявки получают «Принята»; тесты заявок обновляются.
- [Два черновика одного счётчика подтверждены в обратном порядке] → действует последний подтверждённый, прежний уходит в архив.

## Migration Plan

Применить миграции `017` (новые таблицы) и `018` (колонки `kind`, `status` со значениями по умолчанию для существующих заявок). Бакет создаётся автоматически. Откат: rollback миграции и возврат версии; объекты в бакете актов можно удалить вручную.

Принятые допущения: «ссылка на файл» — ключ объекта (UUID); изменять срок могут ADMIN (применяется сразу, без заявки) и OWNER связанного счёта (через заявку «П» и подтверждение); «Подтвердить» = «Взять в работу»; «Закрыть» и остальные переходы делает администратор; в закрытую заявку писать нельзя; номер заявки о проверке использует общий сквозной счётчик; допустимые форматы акта — PDF/JPEG/PNG до 10 МБ; нового срока достаточно, чтобы это была валидная дата 2000–2100 (прошлая допустима).
