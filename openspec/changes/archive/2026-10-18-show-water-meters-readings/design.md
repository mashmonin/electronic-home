## Context

Таблицы `water_meters` и `meter_readings` созданы (`water-meter-data-model`): счётчик принадлежит адресу (квартире), тип `HOT`/`COLD`, показание ссылается на предыдущее через `previous_reading_id`. Бэкенд уже отдаёт `GET /api/accounts/{number}` через `AccountService` и read-only сущности `AccountEntity`, `AddressEntity`, `OwnerEntity` (пакет `account`); `ddl-auto: validate`. Фронтенд строит карточки «Стояк N» из заглушки `getRisers()` и показывает ошибку/загрузку по состояниям страницы. Решение владельца: пары HOT+COLD образуют «Стояк N». Мотивация — в proposal.md, требования — в дельта-спеках.

## Goals / Non-Goals

**Goals:**
- Отдать счётчики и показания в существующем ответе по счёту, без поломки клиентов.
- Показать на экране номер счётчика и предыдущее показание из БД.

**Non-Goals:**
- Запись показаний (API и сохранение), проверка «не меньше предыдущего» на сервере.
- Хранение стояков в БД, привязка счётчиков к конкретному стояку.
- Пагинация и ограничение истории показаний.

## Decisions

- **Счётчики — вложенное поле `meters` существующего ответа, а не отдельный эндпоинт.** Как у смежной системы (`meters` внутри `account`), один запрос на экран. Поле добавляется — старые клиенты не ломаются. Альтернатива `GET /api/accounts/{n}/meters`: чище для отдельной загрузки, но второй запрос и второе состояние ошибки на фронте.
- **Состав элемента:** `number`, `water_type`, `readings[]` (от новых к старым), у показания — `value` (число), `reading_date`, `previous` (`{value, reading_date}` или `null`). Идентификаторы и `is_test` не отдаются. `water_type` — строки `HOT`/`COLD`, как в БД.
- **Полная история показаний в `readings`:** экрану нужно только последнее, но «предыдущий» — часть модели, а история пока мала. Если вырастет, добавится ограничение или отдельный эндпоинт; зафиксировано в рисках.
- **JPA:** `WaterMeterEntity` (адрес `@ManyToOne` lazy, `waterType`, `number`, `readings` `@OneToMany(mappedBy = "meter")` как `Set`) и `MeterReadingEntity` (`meter` `@ManyToOne` lazy, `value` `BigDecimal`, `readingDate` `LocalDate`, `previousReading` `@ManyToOne` lazy на себя по `previous_reading_id`). `AddressEntity` получает `meters` `@OneToMany(mappedBy = "address")`. Сущности только для чтения, `is_test` не отображается (как у существующих). Составной внешний ключ `(previous_reading_id, meter_id)` в Hibernate не описывается: на чтение он не влияет.
- **Загрузка без N+1 и без декартова произведения:** счёт грузится как сейчас (`@EntityGraph`: адрес и совладельцы), счётчики квартиры — отдельным запросом `WaterMeterRepository.findByAddressId` с `@EntityGraph(attributePaths = {"readings", "readings.previousReading"})`. Одна коллекция в графе (`readings`), остальное `ManyToOne`, поэтому дублей строк по совладельцам нет. Репозиторий — пакетный интерфейс `Repository<WaterMeterEntity, Long>`, как `AccountRepository`.
- **Сортировка в сервисе:** счётчики по `number`, затем `id`; показания по `readingDate` убыв., затем `id` убыв. Порядок на уровне БД не гарантируется, поэтому сортируется в коде (как и совладельцы).
- **DTO:** вложенные records `AccountResponse.Meter(number, @JsonProperty("water_type") String waterType, readings)`, `Reading(value, @JsonProperty("reading_date") LocalDate readingDate, previous)`, `PreviousReading(value, readingDate)`. `LocalDate` сериализуется как `ГГГГ-ММ-ДД` (Jackson 3 по умолчанию, без временных меток); это проверяется тестом. `BigDecimal` уходит JSON-числом.
- **Фронтенд, сборка стояков:** чистая функция `buildRisers(meters)` в `readings/risers.ts`: счётчики разделяются по `water_type` с сохранением порядка API; `i`-й HOT и `i`-й COLD образуют стояк `i`; длина — максимум из двух списков. Элемент стояка: `hot?` и `cold?` с `number` и `previous?` (значение `readings[0].value` либо `undefined`).
- **Фронтенд, отображение:** `ReadingField` получает `meter?: { number, previous? }` и показывает «Счётчик № {number | —}» и «Пред. показание: {previous.toFixed(3)} м³ | —»; проверка «не меньше предыдущего» применяется только при наличии `previous`. `RiserCard` убирает «Счётчик № —» из заголовка. Добавленные пользователем стояки не имеют счётчиков и ведут себя как раньше (прочерки, поля доступны).
- **Заглушка:** `getRisers()` и тип `Riser` с `meterNumber` удаляются; `submitReadings` остаётся заглушкой. `MeterReadingsPage` больше не вызывает `getRisers()` и строит стояки из `account.meters`; `Promise.all` заменяется одним запросом.
- **Тесты:** бэкенд — расширение `AccountApiIT` на тестовых данных (порядок счётчиков, типы, показания, `previous`, формат даты, отсутствие `id`/`is_test`, пустой `meters`, счётчик без показаний). Фронтенд — мок ответа со `meters`: сборка пар, прочерки, непарный счётчик, пустой список, без показаний, проверка «не меньше предыдущего» по данным счётчика; юнит-тест `buildRisers`.

## Risks / Trade-offs

- [История показаний в каждом ответе растёт со временем] → допустимо при текущем объёме; позже ограничение по числу/периоду или отдельный эндпоинт без поломки `readings[0]`.
- [Пары HOT+COLD «по порядку» могут не соответствовать реальным стоякам] → стояки не хранятся в БД; соответствие условное и заменится, если появится модель стояков.
- [Эндпоинт без авторизации отдаёт номера счётчиков и показания] → тот же риск, что у ФИО (см. архив `add-account-info-endpoint`): авторизация обязательна до появления реальных данных в prod.
- [Отправка остаётся заглушкой: введённые значения нигде не сохраняются] → осознанная граница; API записи — отдельное изменение.
- [Несовпадение формата числа: `BigDecimal` 245.300 в JSON приходит как число, JS теряет хвостовой ноль] → фронтенд форматирует `toFixed(3)`, тест покрывает.
- [Ленивые связи `previousReading` вне транзакции] → DTO строится внутри `@Transactional(readOnly = true)` сервиса; `open-in-view` выключен, поэтому ошибка обнаружится тестами.
