## Why

В БД уже есть счётчики воды и показания с цепочкой «предыдущее» (`water-meter-data-model`), а экран ввода показаний по-прежнему берёт стояки и «Пред. показание» из заглушки `getRisers()` на фронтенде. Нужно отдать реальные данные через API и показать их на экране.

## What Changes

- JPA: добавляются сущности счётчиков воды и показаний (с самоссылкой на предыдущее показание), только для чтения; квартира получает связь со счётчиками.
- API: ответ `GET /api/accounts/{number}` дополняется списком `meters` — счётчики квартиры счёта (номер, тип воды `HOT`/`COLD`, показания от новых к старым; у каждого показания значение, дата и `previous` — предыдущее показание или `null`). Существующие поля ответа не меняются, поэтому клиенты не ломаются.
- Фронтенд: карточки «Стояк N» строятся из счётчиков — N-й горячий и N-й холодный счётчик (по порядку номеров) образуют «Стояк N». Под каждым полем показывается «Счётчик № …» и «Пред. показание» — значение последнего показания счётчика. Заглушка стояков `getRisers()` удаляется; в заголовке карточки «Счётчик № —» больше нет.
- Отправка показаний остаётся заглушкой: API записи в изменение не входит.

### Modified Capabilities
- `account-info-api`: ответ получает поле `meters` со счётчиками и показаниями.
- `meter-readings-screen`: карточки стояков строятся из счётчиков, из API берутся номер счётчика и предыдущее показание.

## Impact

- `backend/src/main/java/com/example/electronichome/account/`: новые сущности `WaterMeterEntity`, `MeterReadingEntity`, репозиторий счётчиков, расширение `AddressEntity`, `AccountService` и `AccountResponse`.
- `backend/src/test/`: расширение `AccountApiIT` (счётчики, порядок, `previous`, отсутствие внутренних полей).
- `frontend/src/readings/`: тип `Account`, сборка стояков из счётчиков, `RiserCard`, `ReadingField`, `readingsApi.ts`, `MeterReadingsPage`, `ReadingsForm`, тесты.
- БД, nginx, зависимости не меняются.
