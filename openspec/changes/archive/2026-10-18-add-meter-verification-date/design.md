## Context

`water_meters` (миграция `004`) хранит `address_id`, `water_type`, `number`, `is_test`; сид тестовых счётчиков — `005` с контекстом `dev`, уже применённый во многих dev-БД, поэтому его нельзя менять. `GET /api/accounts/{number}` отдаёт `meters` через `AccountService` и `AccountResponse.Meter`. Фронтенд собирает карточки через `buildRisers(meters)`; `ReadingField` рисует под полем «Счётчик № …» и «Пред. показание…»; страница получает `today` (по умолчанию `new Date()`) для периода. Мотивация — в proposal.md, требования — в дельта-спеках.

## Goals / Non-Goals

**Goals:**
- Хранить дату проверки счётчика и отдавать её клиентам.
- Показывать статус «Просрочено» на фронтенде по системной дате устройства, как просил владелец.

**Non-Goals:**
- Вычисление статуса на сервере, блокировка ввода или отправки при просрочке, уведомления.
- Редактирование даты проверки через API (она задаётся миграциями/администратором в БД).
- Часовые пояса и время суток: сравниваются только календарные даты.

## Decisions

- **Колонка `verification_date date NULL`** в `water_meters` (миграция `006-add-meter-verification-date.yaml`). Необязательная, потому что у существующих счётчиков даты нет, а `NOT NULL` потребовал бы выдумывать значения. `date`, а не `timestamp`: срок проверки — календарная дата. Название отражает «дату проверки» из требования; в интерфейсе подпись «Дата проверки».
- **Тестовые даты — новый changeSet с `context: dev`,** а не правка `005`: в уже созданных dev-БД `005` не выполнится повторно. `UPDATE water_meters SET verification_date = … WHERE number = 'Тест 1' AND is_test` (и `'Тест 2'`), `rollback` — обнуление. На чистой БД changeSet выполняется сразу после `005`, на старой — один дозаполняет даты. «Тест 1» — `2028-01-01`, «Тест 2» — `2026-10-17`; порядок соответствует порядку в запросе владельца.
- **API:** `AccountResponse.Meter` получает `@JsonProperty("verification_date") LocalDate verificationDate` (порядок полей: `number`, `water_type`, `verification_date`, `readings`); значение читается из `WaterMeterEntity.verificationDate`. Пустое значение сериализуется как `null`. Статус сервер не отдаёт: клиент сравнивает сам.
- **Проверка срока — чистая функция на фронтенде** `isExpired(verificationDate, today)` в `readings/verification.ts`: даты сравниваются как строки `ГГГГ-ММ-ДД` (лексикографический порядок совпадает с календарным), текущая дата берётся из `today` по локальным `getFullYear/getMonth/getDate` (не `toISOString`, чтобы не сдвинуться по UTC). Просрочено, если дата проверки строго раньше сегодняшней; в день даты проверки счётчик не просрочен. Функция `formatVerificationDate` переводит `ГГГГ-ММ-ДД` в `ДД.ММ.ГГГГ` без `Date` (без часовых сдвигов). Альтернатива — `new Date(verificationDate) < new Date()`: ловушки с UTC и временем суток.
- **Где считается статус:** в `buildRisers(meters, today)` — каждый `Meter` получает `verificationDate?: string` и `expired: boolean`. Страница передаёт свой `today` (тот же, что для периода), поэтому тесты задают дату явно, а повторный рендер после полуночи подхватывает новую дату. Компоненты полей остаются глупыми.
- **Отображение:** в `ReadingField` третья строка под полем: «Дата проверки: ДД.ММ.ГГГГ» (или «—») и, при `expired`, красная `Tag` antd «Просрочено». Просрочка не влияет на валидацию и отправку.
- **Тесты:**
  - бэкенд: `MeterSchemaIT` (дата сохраняется, `NULL` допустим), `MeterTestDataIT` (даты тестовых счётчиков), `AccountApiIT` (`verification_date` в ответе, `null` без даты, имена полей), отдельный `MeterVerificationUpgradeIT` на Testcontainers: Liquibase применяет первые 15 changeSet'ов (до `005`), затем остальные — даты появляются у уже созданных тестовых счётчиков;
  - фронтенд: `verification.test.ts` (граничные даты: раньше, сегодня, позже, смена месяца и года, поздний вечер локального времени, отсутствие даты, формат), `risers.test.ts` (флаг `expired`), тесты страницы (строка и метка для «Тест 1»/«Тест 2» при `today = 18.10.2026`, день окончания, нет даты, поле без счётчика, просрочка не мешает отправке).

## Risks / Trade-offs

- [Системная дата устройства может быть неверной, и статус «Просрочено» ошибётся] → осознанное решение владельца (логика на фронтенде); сервер отдаёт только дату, поэтому позже статус можно перенести на сервер без изменения контракта.
- [Дата «Тест 2» зашита как 2026-10-17: после этой даты счётчик всегда просрочен] → так и задумано как демонстрация статуса; тест фронтенда задаёт `today` явно и не зависит от реальных часов.
- [Новый changeSet сида меняет данные по номеру и `is_test`] → затрагивает только тестовые счётчики в `dev`; в `prod` не выполняется.
- [Дата проверки без времени и зоны] → сравнение календарное, расхождения возможны только если у пользователя неверная дата.
- [Статус без блокировки может ввести в заблуждение, будто ввод запрещён] → метка только информирует; поведение закреплено сценарием спеки и тестом.
