## Context

Фронтенд: `MeterReadingsPage` загружает счёт и строит `buildRisers(account.meters, today)` (пары HOT+COLD); `ReadingsForm` содержит `Form` с `Form.List` стояков и кнопкой «+ Добавить стояк», собирает запрос из полей `risers[i].hot/cold`, сопоставляя их с `knownRisers[i].hot/cold.number`; `RiserCard` рисует заголовок «Стояк N» и два `ReadingField`, а `ReadingField` — подпись, поле и под ним строки «Счётчик № …», «Предыдущее показание», «Дата проверки …» с меткой. Данные API не меняются: `meters[]` с `number`, `water_type`, `verification_date`, `readings[]`. Мотивация — в proposal.md, требования — в дельта-спеке.

## Goals / Non-Goals

**Goals:**
- Одна карточка на счётчик: слева название и срок проверки, справа блок показаний.
- Сохранить всё поведение ввода, отправки, ошибок сервера и обновления «Предыдущее показание».
- Убрать то, что стало бессмысленным: стояки, ручное добавление, поля без счётчика.

**Non-Goals:**
- Изменения бэкенда, API и БД.
- Новые проверки или поля; перестановка шапки и остальных блоков.
- Сортировка или фильтры счётчиков (порядок — как в API).

## Decisions

- **Модель карточки.** Тип `Meter` на фронтенде: `{ number, waterType: 'HOT' | 'COLD', previous?, verificationDate?, expired }`. Функция `toMeters(meters: AccountMeter[], today: Date): Meter[]` в `readings/meters.ts` заменяет `buildRisers`: сохраняет порядок API, берёт `previous` из `readings[0]`, считает `expired` через `isExpired`. Типы `Riser`, `RiserValues` и файлы `risers.ts`, `RiserCard.tsx` удаляются.
- **Компоненты.** `MeterCard` (новый) — `Card` с `Row`: левая колонка (`xs=24`, `md=10`) — название счётчика заголовком того же стиля, что был у «Стояк N» (`Typography.Title level=5`, 15px), под ним строка даты проверки, а на следующей строке метка `Tag` «Просрочено» (вертикальный `Flex`); правая колонка (`xs=24`, `md=14`) — `ReadingField`. Адаптивность даёт `Row/Col`: на узком экране колонки встают друг под другом, поэтому правка CSS не нужна. `ReadingField` упрощается до подписи по типу воды, `Input` и строки «Предыдущее показание»; строки «Счётчик № …» и «Дата проверки» из него уходят.
- **Форма.** Значения — массив по индексу карточки: `Form` с полями `['values', index]`, `initialValues = { values: meters.map(() => '') }`. `Form.List` и кнопка «+ Добавить стояк» убираются: набор карточек задаётся данными. Сбор запроса: для каждой карточки с заполненным значением → `{ meterNumber: meters[i].number, value: normalizeReading(value) }`; ошибки сервера по `meterNumber` ставятся на поле `['values', i]`. Правило «Для этого поля нет счётчика» удаляется: полей без счётчика не бывает.
- **Пустой список счётчиков.** `ReadingsForm` не рендерится; вместо него `Alert type="info"` «Для этого лицевого счёта счётчики не найдены». Кнопки отправки и сброса тем самым не показываются.
- **Подпись поля** по типу воды: `HOT` → «Горячая вода, м³», `COLD` → «Холодная вода, м³» (те же тексты, что были у полей стояка, поэтому клиентская валидация и тесты привязаны к ним же).
- **`today` и просрочка.** Страница по-прежнему передаёт свой `today` в `toMeters`; логика `isExpired`/`formatVerificationDate` не меняется.
- **Обновление данных после сохранения.** Без изменений: `onChanged` перезапрашивает счёт, `toMeters` пересобирает карточки, форма не размонтируется (`key={account.number}`); после `resetFields` значения возвращаются к пустым.
- **Тесты.** Обновляются `MeterReadingsPage.test.tsx`, `MeterReadingsSubmit.test.tsx`; `risers.test.ts` заменяется `meters.test.ts`. Новые проверки: порядок и независимость карточек, подпись по типу воды, расположение (название и дата в левой части, поле в правой — через `within(card)`), отсутствие «Стояк» и кнопки добавления, сообщение для пустого списка, два счётчика одного типа, ошибки сервера на нужной карточке, обновление «Предыдущее показание» в нужной карточке. Тесты `isExpired` без изменений.
- **Purpose основной спеки** («…по стоякам своей квартиры») правится при архивации вместе с синхронизацией дельт.

## Risks / Trade-offs

- [Отход от макета Figma: карточка «Стояк N» с двумя полями заменена карточкой счётчика] → решение владельца, зафиксировано в спеке «Соответствие макету»; макет в Figma стоит обновить отдельно.
- [Много счётчиков — длинная страница] → допустимо для одного дома; при росте — группировка или сворачивание отдельным изменением.
- [Удаление «+ Добавить стояк» убирает возможность ввести значение без счётчика] → это и было целью: такие значения никогда не отправлялись.
- [Две карточки с одинаковым типом воды имеют одинаковую подпись поля] → поле находится в карточке с названием счётчика; в тестах поля выбираются внутри карточки.
- [Большая перестройка компонентов может задеть уже проверенное поведение отправки] → логика отправки не переписывается, а меняется только источник имён полей; регрессию ловят существующие тесты отправки, адаптированные под карточки.
