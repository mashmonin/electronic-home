## Context

Бэкенд принимает `POST /api/accounts/{number}/readings` с телом `{"readings": [{"meter_number", "value"}]}` и отвечает `201`, `400 {"errors": [{"meter_number", "code"}]}`, `404`, `409` (спека `meter-readings-api`). Экран: `MeterReadingsPage` один раз загружает счёт (`fetchAccount`) и строит карточки из `account.meters` через `buildRisers`; `ReadingsForm` содержит `Form` с `Form.List` стояков и вызывает заглушку `submitReadings({accountNumber, risers})` из `readingsApi.ts`; `ReadingField` проверяет значение через `validateReading(value, meter?.previous)`. Мотивация — в proposal.md, требования — в дельта-спеке.

## Goals / Non-Goals

**Goals:**
- Реальная отправка показаний и актуальные «Пред. показание» сразу после сохранения.
- Понятные сообщения на каждый ответ сервера.

**Non-Goals:**
- Любые изменения бэкенда и API.
- Авторизация, выбор даты, редактирование отправленного.
- Привязка добавленных вручную стояков к реальным счётчикам.

## Decisions

- **Клиент отправки в `readingsApi.ts`:** `submitReadings(accountNumber, readings: { meterNumber: string; value: string }[])` делает `fetch(POST /api/accounts/{number}/readings)` с телом `{readings: [{meter_number, value: Number(value)}]}` и возвращает объединение результатов: `ok`, `invalid` (с `errors: {meterNumber | null, code}[]`), `not-found` (404), `conflict` (409), `error` (прочее и сетевые ошибки). Исключения наружу не выбрасываются — как у `fetchAccount`. Значение уходит JSON-числом: до 12 значащих цифр число точно представимо в `double`; строка с запятой уже нормализована в точку (`normalizeReading`).
- **Сопоставление поля и счётчика:** при отправке для заполненного поля `risers[i].hot` номер берётся из `knownRisers[i]?.hot?.number` (аналогично `cold`). Ошибки сервера по `meter_number` возвращаются на то же поле: строится карта «номер счётчика → имя поля `[i, 'hot'|'cold']`», ошибки выставляются `form.setFields`.
- **Поля без счётчика — правило в `ReadingField`:** если значение заполнено, а `meter` не задан, валидатор возвращает «Для этого поля нет счётчика». Так отправка блокируется штатной валидацией `Form`, и в `onFinish` попадают только поля со счётчиком. Альтернатива — молча пропускать такие поля: пользователь решит, что значение отправлено.
- **Сообщения по кодам** (константа в `ReadingsForm`): `VALUE_LESS_THAN_PREVIOUS` — «Показание не может быть меньше предыдущего», `INVALID_VALUE` — «Введите число, не более трёх знаков после запятой» (те же тексты, что у клиентской проверки), `METER_NOT_FOUND` — «Счётчик не найден»; неизвестный код — общее сообщение об ошибке. Для `409` — «Показания не сохранены из-за одновременного изменения. Повторите отправку», для `404` — «Лицевой счёт не найден», для `error` — прежнее «Не удалось отправить показания, попробуйте позже».
- **Перезапрос счёта после ответа:** `ReadingsForm` получает проп `onChanged: () => Promise<boolean>`; страница реализует его как `fetchAccount` без перехода в `loading`: при `ok` заменяет `account` в состоянии `ready` (форма не размонтируется, `key={account.number}` не меняется), иначе возвращает `false`. Вызывается после `ok` (чтобы обновить «Пред. показание»), после `invalid` (на случай устаревшего предыдущего значения) и после `conflict`. Полноэкранной загрузки нет, карточки не мигают.
- **Очистка формы:** только после `ok` — `form.resetFields()`; при ошибках введённое сохраняется, чтобы пользователь мог поправить. Порядок: сообщение об успехе → сброс формы → перезапрос. Если перезапрос не удался после успеха — `message.warning('Показания сохранены, но данные на экране не обновились. Обновите страницу')`.
- **Состояние отправки:** остаётся `sending` на кнопке (`loading`), включая перезапрос; повторный клик во время отправки невозможен.
- **Добавленные вручную стояки** остаются как есть (кнопка «+ Добавить стояк»): у них нет счётчиков, значение в них блокирует отправку (см. выше). Удалять кнопку не нужно — это отдельное решение продукта.
- **Тесты (vitest + Testing Library, `fetch` подменяется):**
  - клиент `readingsApi`: тело и URL запроса, разбор `201`, `400` с ошибками, `404`, `409`, сетевой ошибки;
  - страница: успешная отправка (запрос с номерами счётчиков, очистка полей, «Пред. показание» меняется на новое значение после перезапроса), отправка одного поля из двух, ошибка `VALUE_LESS_THAN_PREVIOUS` у нужного поля с сохранением введённого и обновлением предыдущего, `INVALID_VALUE`/`METER_NOT_FOUND`, `409`, `404`, ошибка сети, поле без счётчика блокирует отправку, неудачный перезапрос после успеха даёт предупреждение.

## Risks / Trade-offs

- [Гонка: между загрузкой экрана и отправкой кто-то сохранил показание, предыдущее на экране устарело] → сервер проверяет по актуальным данным, ошибка показывается у поля, а «Пред. показание» перезапрашивается.
- [Без авторизации любой, открывший экран, отправит показания по номеру из адресной строки] → тот же риск, что у API (см. архив `add-save-meter-readings`); авторизация — отдельное изменение.
- [Число через `Number()` теряет точность при > 15 значащих цифр] → сервер принимает не более 9 целых и 3 дробных (12 цифр), клиентская валидация уже ограничивает 3 знака после запятой; значения шире 9 цифр отклоняет сервер.
- [Если перезапрос после успеха упал, экран показывает старое «Пред. показание»] → предупреждение с предложением обновить страницу; данные в БД корректны.
- [Заблокированная отправка из-за значения в «лишнем» стояке может озадачить] → понятное сообщение под полем; вручную добавленные стояки без счётчиков остаются из прежнего макета.
- [Главная спека экрана ещё содержит сценарий «Добавление третьего стояка», устаревший после перехода на счётчики из API] → в этом изменении не правится (не относится к отправке), отмечено для отдельной ревизии.
