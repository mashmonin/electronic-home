## Context

БД (`housing-data-model`) хранит `addresses` (адрес = квартира), `accounts` (адрес 1:N счета), `owners` и связку `account_owners`; в dev есть тестовый счёт `000000000001` (две совладельца). В бэкенде нет контроллеров, JPA-сущностей и сервисов; `ddl-auto: validate`; actuator живёт под `/api/actuator`, CORS профиля `dev` открывает `/api/**` для `localhost:5173` и `https://localhost`. Фронтенд берёт квартиры и счета из заглушки `readingsApi.ts` (две квартиры), стояки и показания тоже заглушка. Образец контракта — ресурс `account` смежной системы (номер, адрес строкой, помещение, вложенные данные, `snake_case`). Мотивация — в proposal.md, требования — в спеках.

## Goals / Non-Goals

**Goals:**
- Один эндпоинт чтения по лицевому счёту с вложенными адресом и совладельцами.
- Фронтенд показывает реальные адрес, номер счёта и совладельцев; заглушка квартир удаляется.

**Non-Goals:**
- Авторизация и привязка пользователя к счетам, список счетов, ресурс «владелец».
- Счётчики, показания, платежи, квитанции и прочие поля `account` смежной системы.
- Запись данных через API.
- Фильтрация по `is_test`.

## Decisions

- **Ресурс — лицевой счёт: `GET /api/accounts/{number}`.** Ключ — бизнес-номер (как в смежной системе), а не внутренний `id`: он стабилен и не раскрывает последовательность идентификаторов. Альтернатива `GET /api/owners/{id}` отвергнута владельцем.
- **Ответ — DTO, а не сущности:** Java-record `AccountResponse(number, address, premise, owners)`, вложенные `Premise(street, house, apartment)` и `Owner(fullName)`; `snake_case` задаётся аннотацией явным `@JsonProperty("full_name")` на единственном составном поле (Spring Boot 4 использует Jackson 3, глобальная смена стратегии не нужна и затронула бы actuator). Идентификаторы и `is_test` в DTO не попадают.
- **Адрес строкой собирается на бэкенде:** `"{street}, д. {house}, кв. {apartment}"` — единый формат для всех клиентов, как поле `address` у смежной системы.
- **Слои:** `AccountController` → `AccountService` → `AccountRepository` (Spring Data JPA). Сущности `AccountEntity`, `AddressEntity`, `OwnerEntity` только для чтения; совладельцы — `@ManyToMany` через таблицу `account_owners`, адрес — `@ManyToOne` (lazy). Колонка `is_test` в связке не отображается: чтение с ней не мешает, а для записи сущности пока не используются. Загрузка одним запросом через `@EntityGraph` (адрес и совладельцы), чтобы не было N+1; `spring.jpa.open-in-view` уже выключен, DTO собирается внутри транзакции сервиса (`@Transactional(readOnly = true)`).
- **Альтернатива — `JdbcClient` без сущностей:** меньше кода сейчас, но сущности понадобятся для записи; `ddl-auto: validate` сверяет их со схемой, что полезно.
- **Сортировка совладельцев** по ФИО, затем по `id` — детерминированный порядок для тестов и UI.
- **Ошибки:** отсутствие счёта — `ResponseStatusException(NOT_FOUND)`; в prod тело не раскрывает подробностей (уже настроено `server.error.*`).
- **Фронтенд, получение номера счёта:** `?account=` из `window.location.search`; fallback `import.meta.env.VITE_DEFAULT_ACCOUNT_NUMBER`, значение `000000000001` лежит в `frontend/.env.development` и поэтому не попадает в рабочую сборку (там нет fallback → сообщение «не указан»).
- **Фронтенд, клиент:** `fetchAccount(number)` в `readings/accountApi.ts` на `fetch('/api/accounts/' + encodeURIComponent(number))`; различает 404 (`not-found`) и прочие ошибки (`error`). Состояние страницы: `loading | ready | not-found | error | no-account`.
- **Шапка:** `AppHeader` принимает `account` (адрес, номер) и `owners`; `Dropdown` выбора квартиры убирается, блок адреса становится статичным; иконка профиля открывает `Popover` со списком ФИО (или «Совладельцы не указаны»). Иконки остаются интерактивными только в части профиля.
- **Заглушка:** из `readingsApi.ts` удаляются квартиры и `getApartments`; стояки (`risers`) выделяются в `getRisers()` — те же две карточки с данными из макета, не зависящие от квартиры. `ReadingsForm` принимает стояки, а не квартиру; `submitReadings` принимает номер счёта вместо `apartmentId`.
- **Тесты:** бэкенд — `AccountApiIT` (Testcontainers, профиль `dev`, `TestRestTemplate`/`HttpClient`): 200 на тестовом счёте, состав и порядок `owners`, пустой список совладельцев, 404, отсутствие `id`/`is_test`, `snake_case`. Фронтенд — vitest с подменой `fetch`: успешная загрузка, `?account=`, loading, 404, ошибка сети, нет номера, поповер совладельцев.

## Risks / Trade-offs

- [Эндпоинт без авторизации отдаёт ФИО владельцев по любому номеру счёта; номера угадываются перебором] → допустимо пока в БД только тестовые данные; **до появления реальных данных в prod обязательна авторизация** (отдельное изменение). Зафиксировано как предусловие, в prod сейчас тестовых записей нет.
- [Ресурс «счёт» без списка счетов: пользователь не может переключить квартиру] → осознанная потеря возможности; вернётся вместе с авторизацией (список счетов текущего пользователя).
- [Стояки на заглушке не соответствуют конкретному счёту] → видно в тексте экрана только по цифрам из макета; заменяется при появлении счётчиков в БД.
- [Лишние поля смежной системы (долг, платежи, счётчики) не реализованы] → контракт расширяется добавлением полей без поломки клиентов.
- [Имя составного поля нужно задавать `@JsonProperty` на новых DTO] → покрыто тестом на имена полей.
- [Значение по умолчанию номера счёта зашито в `.env.development`] → не влияет на prod-сборку; тест на отсутствие fallback при пустой переменной.
