## Context

Квитанции хранятся файлами на томе Docker: `FileSystemReceiptStorage` за интерфейсом `ReceiptStorage` (`save`/`open`/`delete`), ключ — UUID, в БД `receipts.file_key`, размер и SHA-256. Бэкенд — Spring Boot 4 (MVC, `JdbcClient`), nginx пропускает тела до 6 МБ, чат заявок (`request` пакет) принимает только JSON. Всё запускается в Docker (`docker-compose.yml` + `dev`/`prod`). Мотивация — в `proposal.md`, требования — в спецификациях `object-storage` и `request-attachments`.

## Goals / Non-Goals

**Goals:**
- Один S3-совместимый сервис для файлов проекта: квитанции всех квартир и вложения чатов.
- Файлы закрыты от внешнего мира: только бэкенд, только по правам пользователя.
- Безопасный одноразовый перенос уже опубликованных квитанций.
- Минимум нового в эксплуатации: один контейнер, один том, ключи из окружения.

**Non-Goals:**
- Отказоустойчивость и репликация (один узел), жизненные циклы и версионирование объектов, квоты.
- Антивирус, миниатюры и предпросмотр, удаление и редактирование вложений.
- Предподписанные ссылки и публикация хранилища наружу, веб-консоль.

## Decisions

### 1. SeaweedFS вместо MinIO
Бесплатные образы MinIO больше не публикуются, репозиторий заархивирован. SeaweedFS: Apache 2.0, образы публикуются, S3 API на одном контейнере `weed server -s3`; платная Enterprise-версия существует отдельно и нам не нужна. Движок спрятан за S3 API, поэтому его замена (Garage, Ceph RGW) потребует только правки Compose. Образ закрепляется на конкретной версии (не `latest`), которую выбираем при реализации после проверки (см. задачу 1.1: сначала проверка, что нужные S3-операции работают).
*Альтернативы:* Garage (AGPL, ручная инициализация кластера), RustFS (молодой проект), MinIO из исходников (сборка на хосте, нет поддержки).

### 2. Контейнер хранилища
Сервис `s3` в базовом `docker-compose.yml`: том `s3_data:/data`, только внутренняя сеть. Ключи доступа попадают в хранилище через конфигурацию идентификаций (JSON), которую `entrypoint` создаёт при старте из `S3_ACCESS_KEY` и `S3_SECRET_KEY` и передаёт серверу; секреты не лежат в репозитории и образе. В dev значения по умолчанию (в `docker-compose.dev.yml`), порт S3 публикуется на `127.0.0.1` для бэкенда, запущенного из IDE; в prod переменные обязательны (`${S3_ACCESS_KEY:?...}`), порт не публикуется. Бэкенд `depends_on: s3 (service_healthy)`; проверка готовности — запрос к мастеру `/cluster/status` и ответ порта S3 (точная команда подтверждается при реализации).

### 3. Клиент: AWS SDK for Java v2
`software.amazon.awssdk:s3` — стандартный клиент, работает с любым S3-совместимым сервером. `S3Client` создаётся один раз: `endpointOverride`, статические ключи, регион (по умолчанию `us-east-1`, SeaweedFS его не проверяет), `forcePathStyle(true)`. Известная совместимость: новые версии SDK по умолчанию добавляют контрольные суммы запросов; для самохостинговых серверов включаем `requestChecksumCalculation(WHEN_REQUIRED)` и `responseChecksumValidation(WHEN_REQUIRED)`; проверяется интеграционным тестом на настоящем SeaweedFS. Spring Cloud AWS не используем (не нужен).

### 4. Слои: `ObjectStore` и два хранилища файлов
Пакет `storage`: интерфейс `ObjectStore` (`put(bucket, key, file, size, contentType)`, `open(bucket, key)`, `delete`, `exists`, `ensureBucket`) и реализация `S3ObjectStore`. Над ним: `S3ReceiptStorage` (сохраняет интерфейс `ReceiptStorage`, поэтому `ReceiptService` и контроллер не меняются) и `AttachmentStorage` для вложений. Общая вспомогательная `SpooledUpload` читает поток во временный файл, считая размер, SHA-256 и считывая начало файла для проверки сигнатуры, с жёстким пределом размера; затем файл отправляется в S3 (`RequestBody.fromFile`) и временный файл удаляется. Так память не растёт с размером файла, а Content-Length известен заранее.
`FileSystemReceiptStorage` и параметр `receipts.storage.path` удаляются; каталог остаётся только как источник переноса.

### 5. Бакеты: лениво
`ensureBucket` вызывается при первой операции с бакетом (HeadBucket → CreateBucket; «уже существует» — не ошибка) и запоминается в `AtomicBoolean`. Старт приложения хранилища не требует, поэтому интеграционные тесты, не трогающие файлы, и запуск бэкенда до готовности S3 не ломаются; в Compose порядок запуска всё равно обеспечен `depends_on`. Состояние хранилища показывает `ObjectStorageHealthIndicator` (HeadBucket по обоим бакетам с коротким таймаутом) под именем `objectStorage`; в prod подробностей нет (`show-details: never`). Тесты без хранилища отключают его свойством `management.health.objectStorage.enabled=false`.

### 6. Конфигурация и секреты
`StorageProperties` (`storage.s3.*`) с валидацией в конструкторе: в prod ключи обязательны и секрет не короче 16 символов (как `AuthProperties` для `JWT_SECRET`); в `application-prod.yml` `access-key: ${S3_ACCESS_KEY}`, `secret-key: ${S3_SECRET_KEY}` без значений по умолчанию; в `application-dev.yml` ключи для разработки. Названия бакетов, endpoint и регион переопределяются переменными.

### 7. Перенос существующих квитанций
`ReceiptFileMigration` — `ApplicationRunner`, срабатывает, только если `receipts.migration.source-path` задан и каталог есть. Для каждой строки `receipts` (`file_key`, `size_bytes`, `sha256`): если объект уже есть — «уже было»; иначе читает исходный файл, сверяет размер и SHA-256 с БД и загружает; отсутствие файла и расхождения — в журнал, не останавливая остальное. Исходные файлы не меняются и не удаляются (откат — просто вернуть прежнюю версию приложения). Исключения не пробрасываются: недоступное хранилище при старте не должно ронять приложение, перенос повторится при следующем запуске. В Docker том `receipts_data` монтируется в бэкенд только для чтения в `/data/receipts-legacy`, а `RECEIPTS_MIGRATION_SOURCE_PATH` указывает на него; в dev по умолчанию `./data/receipts`. После проверки оператор может удалить старый том вручную (описано в README).

### 8. Вложения: модель и запись
Миграция `016`: `request_attachments(id, message_id → request_messages ON DELETE CASCADE, object_key varchar(36) UNIQUE, file_name varchar(255), content_type varchar(100), size_bytes bigint CHECK > 0, sha256 varchar(64), created_at, is_test)`, индекс по `message_id`. Текст сообщения при вложениях может быть пустым: ограничение `request_messages.body` (`length(btrim(body)) > 0`) заменяется проверкой «пустой текст разрешён, если есть вложение» — реализовать ограничением невозможно без триггера, поэтому колонка `body` допускает пустую строку, а правило «текст или файл» проверяет сервис (в БД остаётся ограничение длины). Спека хранения и тест схемы обновляются.
Порядок записи: сервис сначала проверяет все файлы (число, пустота, размер, тип, имя) и только потом загружает их по одному в бакет вложений, затем в одной транзакции сохраняет сообщение и записи вложений; при исключении загруженные объекты удаляются (best-effort, сбой удаления — в журнал). Загрузка идёт до открытия транзакции, чтобы не держать соединение с БД на время сети.

### 9. Приём multipart и лимиты
Эндпоинты получают две ветки: `consumes = application/json` (как раньше) и `multipart/form-data` (`text`, `files`, `account_number`). Для Spring задаются `spring.servlet.multipart.max-file-size=10MB` и `max-request-size=26MB` (25 МБ файлов и запас на служебные части); превышение превращается в `413` обработчиком `MaxUploadSizeExceededException`. Пределы дополнительно проверяются по реально прочитанным байтам. Tomcat сам складывает загрузки во временные файлы, из которых сервис читает.

### 10. Типы файлов
Белый список расширений → назначаемый тип (`image/jpeg`, `image/png`, `image/gif`, `image/webp`, `application/pdf`, `application/msword`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `application/vnd.ms-excel`, `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, `text/plain; charset=utf-8`) и проверка сигнатуры (JPEG `FF D8 FF`, PNG `89 50 4E 47 0D 0A 1A 0A`, GIF `GIF87a`/`GIF89a`, WebP `RIFF....WEBP`, PDF `%PDF-`, DOCX/XLSX `PK 03 04`, DOC/XLS `D0 CF 11 E0 A1 B1 1A E1`, TXT без NUL в первых 8 КБ). Тип клиента игнорируется. SVG и HTML исключены из-за возможности встроенных скриптов. Ограничение условное: проверка сигнатуры не заменяет антивирус.

### 11. Скачивание только через бэкенд
`GET /api/requests/{id}/attachments/{attachmentId}`: один SQL с проверкой прав (`request_id`, автор или администратор), затем потоковая отдача `GetObject` без буферизации в память. Заголовки: `Content-Type` из записи, `Content-Length`, `Content-Disposition: attachment; filename*=UTF-8''...` (RFC 5987), `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`. Предподписанные ссылки не используются — они бы вывели хранилище наружу и обошли проверку прав.

### 12. nginx
В `dev.conf` и `prod.conf` добавляется `location /api/requests { client_max_body_size 30m; ... }` с теми же настройками проксирования, что у `/api/`; остальной `/api/` остаётся с лимитом 6 МБ (квитанции), S3 не проксируется.

### 13. Фронтенд
`requests/attachments.ts` — чистая проверка файлов (число, размер, суммарный размер, расширение, пустота) и формат размера; `requestsApi`: `sendMessage(id, text, files)` и `createRequest(text, files, account)` формируют `FormData`, когда есть файлы, и JSON, когда их нет; `downloadAttachment` через `apiFetch` → blob → `saveFile` (функция переезжает из `ReceiptsTab` в общий модуль). Компоненты: `AttachmentPicker` (кнопка «Прикрепить файл», список выбранных с удалением и сообщениями о проверке, на основе antd `Upload` с `beforeUpload={() => false}`), `AttachmentList` (файлы под сообщением, клик скачивает). Опрос сообщений уже возвращает вложения, дополнительных запросов нет.

### 14. Тесты
Бэкенд: общий `SeaweedFsTestContainer` (синглтон на JVM, запускается один раз и переиспользуется всеми интеграционными тестами, которым нужны файлы) задаёт `storage.s3.*` через `@DynamicPropertySource`; тесты S3-слоя (запись, чтение, удаление, ленивые бакеты, здоровье, недоступное хранилище), квитанций на S3 (существующие IT переводятся на контейнер), переноса (во временный каталог кладутся файлы и записи), вложений (границы, типы, имена, права, транзакционная чистка, скачивание). Фронтенд: стаб `fetch`, проверка `FormData`, правила выбора файлов, отображение и скачивание.

## Risks / Trade-offs

- [Флаги и версия SeaweedFS подбираются при реализации] → задача 1.1 — проверка контейнера и S3-операций до остальной работы; версия закрепляется.
- [Совместимость SDK с самохостинговым S3] → `WHEN_REQUIRED` для контрольных сумм, интеграционный тест на настоящем контейнере.
- [Один узел без репликации] → данные на томе, резервное копирование тома описано в README; осознанное ограничение размера проекта.
- [Потеря связи с хранилищем] → операции с файлами завершаются ошибкой (`5xx` без деталей), `health` показывает `DOWN`; остальной функционал (показания, текст чата) работает.
- [Осиротевшие объекты после ручного удаления заявок или квитанций SQL-ом] → вне API удаления нет; процедуру очистки добавим отдельным изменением при необходимости.
- [Крупные загрузки и временные файлы] → пределы на запрос, потоковая отправка, Tomcat/наши временные файлы удаляются в `finally`; нужен запас места во временном каталоге контейнера (~50 МБ).
- [Расширение и сигнатура не гарантируют безопасность файла] → `nosniff`, скачивание как `attachment`, исключены SVG/HTML; антивирус вне рамок.
- [Очень длинные имена файлов] → имя идёт в заголовке части multipart-формы, который сервер читает примерно до 500 байт: имена в сотни символов отклоняются (`413`) ещё до нашей обрезки до 255; обычные имена проходят.
- [Проба здоровья и кэш бакетов] → индикатор использует `check` (запрос к хранилищу каждый раз, таймаут 3 с), а не запомненные бакеты; иначе остановленное хранилище осталось бы `UP`. Найдено проверкой вживую.
- [Перенос при старте] → идемпотентен, не блокирует запуск, исходные файлы не трогает; при тысячах файлов старт замедлится — тогда вынесем в отдельную команду.

## Migration Plan

1. Развернуть новую версию: Compose поднимает `s3`, бэкенд ждёт его готовности; миграция БД `016`.
2. В prod до выкладки задать `S3_ACCESS_KEY`/`S3_SECRET_KEY` (без них приложение не стартует) и смонтировать старый том `receipts_data` в `/data/receipts-legacy`.
3. При первом старте квитанции переносятся; проверить журнал («перенесено N, ошибок 0») и скачать пару квитанций.
4. После проверки старый том `receipts_data` можно удалить вручную.
5. Откат: вернуть предыдущую версию — она читает исходные файлы со старого тома (его не меняли); новые вложения и квитанции, созданные в S3 после перехода, при откате будут недоступны.

## Open Questions

- Нужна ли ротация ключей доступа и отдельный ключ только для чтения (для резервного копирования) — отдельное изменение.
- Нужна ли очистка осиротевших объектов (сверка бакета с БД) — по мере роста.
