## ADDED Requirements

### Requirement: Отправка сообщения с вложениями
Эндпоинты `POST /api/requests` (первое сообщение новой заявки) и `POST /api/requests/{id}/messages` SHALL принимать, кроме JSON, запрос `multipart/form-data` с частями: `text` (необязательная), `files` (от нуля до пяти файлов) и для создания заявки — `account_number` (необязательная). Сообщение MUST содержать текст или хотя бы один файл; сообщение без текста с файлами допустимо. Текст проверяется по прежним правилам (обрезка пробелов, не длиннее 2000 символов). JSON-запрос без файлов работает как раньше. Права доступа — как у переписки: автор заявки и администратор, остальным `404`/`403` по правилам спецификации `requests-api`.

#### Scenario: Сообщение с файлом
- **WHEN** собственник отправляет в свою заявку multipart с текстом «Вот фото» и одним JPEG
- **THEN** ответ `201`, сообщение содержит текст и одно вложение

#### Scenario: Только файл
- **WHEN** отправлено сообщение без текста с одним PDF
- **THEN** ответ `201`, текст пуст, вложение сохранено

#### Scenario: Ни текста, ни файла
- **WHEN** в multipart нет текста и нет файлов
- **THEN** ответ `400`, ничего не сохранено

#### Scenario: Вложение в первом сообщении заявки
- **WHEN** собственник создаёт заявку multipart-запросом с текстом и файлом
- **THEN** ответ `201`, первое сообщение заявки содержит вложение

#### Scenario: JSON как раньше
- **WHEN** отправлен JSON `{"text": "Привет"}`
- **THEN** ответ `201`, `attachments` пуст

### Requirement: Ограничения вложений
Система SHALL принимать не более 5 файлов в одном сообщении, размером не более 10 МБ каждый и не более 25 МБ вместе. Файл не может быть пустым. Превышение числа файлов или пустой файл дают `400`, превышение размера — `413`; ничего не сохраняется (ни в БД, ни в хранилище). Размеры проверяются по фактически полученным байтам, а не по заявленному клиентом.

#### Scenario: Шесть файлов
- **WHEN** в сообщении шесть файлов
- **THEN** ответ `400`, сообщение не сохранено

#### Scenario: Слишком большой файл
- **WHEN** один из файлов больше 10 МБ
- **THEN** ответ `413`, сообщение и остальные файлы не сохранены

#### Scenario: Слишком большой общий размер
- **WHEN** пять файлов по 6 МБ (30 МБ вместе)
- **THEN** ответ `413`, ничего не сохранено

#### Scenario: Пустой файл
- **WHEN** один из файлов пуст
- **THEN** ответ `400`

#### Scenario: Ровно на границе
- **WHEN** отправлен файл ровно 10 МБ
- **THEN** ответ `201`

### Requirement: Допустимые типы файлов
Допустимы файлы с расширениями `jpg`, `jpeg`, `png`, `gif`, `webp` (изображения), `pdf`, `doc`, `docx`, `xls`, `xlsx`, `txt`. Тип определяется по расширению (без учёта регистра) и MUST подтверждаться содержимым: у изображений и PDF — сигнатурой формата, у `docx`/`xlsx` — сигнатурой ZIP-контейнера, у `doc`/`xls` — сигнатурой составного документа, у `txt` — отсутствием нулевых байтов. Заявленный клиентом `Content-Type` не используется: сервер сам назначает тип по расширению. Файлы других типов (в том числе `svg`, `html`, `js`, `exe`, архивы) и файлы, чьё содержимое не соответствует расширению, отклоняются ответом `415` и не сохраняются.

#### Scenario: Допустимые типы
- **WHEN** отправлены файлы `a.JPG`, `b.png`, `c.pdf`, `d.docx`, `e.xlsx`, `f.txt` с корректным содержимым
- **THEN** все принимаются

#### Scenario: Запрещённое расширение
- **WHEN** отправлен файл `page.html` или `icon.svg`
- **THEN** ответ `415`, сообщение не сохранено

#### Scenario: Расширение не соответствует содержимому
- **WHEN** отправлен файл `photo.jpg`, внутри которого текст или исполняемый код
- **THEN** ответ `415`, сообщение не сохранено

#### Scenario: Тип клиента игнорируется
- **WHEN** клиент указал для `report.pdf` тип `text/html`
- **THEN** вложение сохранено с типом `application/pdf`

### Requirement: Имя вложения
Имя файла от клиента SHALL использоваться только для показа и для имени при скачивании: из него отбрасывается путь (всё до последнего `/` или `\`), удаляются управляющие символы, пробелы по краям; длина — не более 255 символов (длинное имя укорачивается с сохранением расширения); пустое имя после очистки даёт `400`, имя без допустимого расширения — `415`. Имя MUST NOT влиять на ключ объекта и путь.

#### Scenario: Путь в имени
- **WHEN** загружен файл с именем `..\..\secret\схема.pdf`
- **THEN** имя вложения — `схема.pdf`

#### Scenario: Длинное имя
- **WHEN** имя файла длиннее 255 символов
- **THEN** оно укорочено до 255 с сохранением расширения

### Requirement: Хранение вложений
Для каждого вложения система SHALL хранить запись (сообщение, ключ объекта, имя для показа, назначенный тип, размер, SHA-256, время, признак `is_test`), а содержимое — в бакете вложений. Содержимое в БД храниться не должно. Запись вложения и сообщение создаются в одной транзакции; если она не удалась, загруженные объекты MUST быть удалены. Вложения нельзя изменить или удалить через API, они удаляются вместе с заявкой каскадно в БД (объекты при удалении заявок вне API обслуживаются отдельно, см. design).

#### Scenario: Запись о вложении
- **WHEN** сообщение сохранено с файлом
- **THEN** в БД есть запись с именем, типом, размером и SHA-256 файла, а в бакете вложений есть объект под её ключом

#### Scenario: Сбой БД
- **WHEN** запись сообщения не удалась после загрузки файлов в хранилище
- **THEN** загруженные объекты удалены

#### Scenario: Нельзя удалить
- **WHEN** клиент пытается удалить или изменить вложение через API
- **THEN** операции нет (ответ `405` или `404`), вложение остаётся

### Requirement: Вложения в ответах
Каждый элемент сообщения в ответах `GET /api/requests/{id}/messages` и `POST .../messages` SHALL содержать массив `attachments` (пустой, если файлов нет); элемент массива: `id`, `name`, `size`, `content_type`. Ключей объектов, адресов хранилища, SHA-256 и `is_test` в ответах нет. Сообщение без текста возвращается с `text` равным пустой строке. В элементе списка заявок `last_message.text` для сообщения без текста SHALL быть «Вложение: <имя>» (для нескольких файлов — «Вложений: N»); при наличии текста берётся он.

#### Scenario: Вложения в ленте
- **WHEN** запрошены сообщения заявки, в одном из которых два файла
- **THEN** у него `attachments` из двух элементов с `id`, `name`, `size`, `content_type`

#### Scenario: Без служебных полей
- **WHEN** клиент получает вложение
- **THEN** в нём нет ключа объекта, SHA-256 и адреса хранилища

#### Scenario: Превью вложения без текста
- **WHEN** последнее сообщение заявки — один файл `схема.pdf` без текста
- **THEN** в списке `last_message.text` равно «Вложение: схема.pdf»

#### Scenario: Превью нескольких вложений
- **WHEN** последнее сообщение — три файла без текста
- **THEN** в списке `last_message.text` равно «Вложений: 3»

### Requirement: Скачивание вложения
Система SHALL предоставлять эндпоинт `GET /api/requests/{id}/attachments/{attachmentId}`, отдающий содержимое файла вложения. Права — как у переписки заявки: автор заявки и администратор; чужая заявка, чужое или несуществующее вложение, вложение другой заявки и вложение, чей объект потерян, дают `404`; жилец получает `403`, без токена `401`. Ответ `200` содержит `Content-Type` назначенного типа, `Content-Length`, `Content-Disposition: attachment` с именем файла (корректно закодированным для кириллицы), `X-Content-Type-Options: nosniff` и `Cache-Control: private, no-store`. Содержимое MUST совпадать с загруженным байт в байт.

#### Scenario: Скачивание автором
- **WHEN** собственник скачивает вложение своей заявки
- **THEN** ответ `200`, содержимое совпадает с загруженным, имя в `Content-Disposition` — исходное

#### Scenario: Скачивание администратором
- **WHEN** администратор скачивает вложение любой заявки
- **THEN** ответ `200`

#### Scenario: Чужая заявка
- **WHEN** собственник запрашивает вложение заявки другого собственника
- **THEN** ответ `404`, содержимое не раскрывается

#### Scenario: Вложение другой заявки
- **WHEN** запрошена пара «заявка A, вложение из заявки B»
- **THEN** ответ `404`

#### Scenario: Жилец и аноним
- **WHEN** жилец или клиент без токена запрашивает вложение
- **THEN** ответ `403` и `401` соответственно

#### Scenario: Заголовки безопасности
- **WHEN** вложение скачивается
- **THEN** в ответе есть `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff` и `Cache-Control: private, no-store`
