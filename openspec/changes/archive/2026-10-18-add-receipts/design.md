## Context

Бэкенд — Spring Boot 4, PostgreSQL, Liquibase (миграции `001`–`006`), JPA с `ddl-auto: validate`, ресурсы строятся вокруг лицевого счёта (`/api/accounts/{number}/…`), есть бин `Clock`. Приложение в Docker запускается от пользователя `app` (uid 1001); томов у бэкенда нет; nginx проксирует `/api/` на бэкенд, лимит тела запроса по умолчанию 1 МБ. Авторизации нет. Решение владельца: файлы хранятся на томе, метаданные — в БД (см. обсуждение вариантов в переписке). Мотивация — в proposal.md, требования — в спеке `receipts`.

## Goals / Non-Goals

**Goals:**
- Вкладка «Квитанции» на экране: список по месяцам и скачивание PDF для текущего лицевого счёта.
- Надёжное хранение PDF вне БД с метаданными в БД и целостностью при сбоях.
- Минимальный набор API: опубликовать (заменить), список, скачать.
- Хранилище, которое можно заменить на S3/MinIO без изменения остального кода.

**Non-Goals:**
- Интерфейс администратора (публикация из браузера), уведомления жильцам, предпросмотр PDF на странице.
- Авторизация жильцов и ролей; генерация квитанций; удаление квитанций; история версий.
- Сканирование PDF на вирусы и разбор содержимого.

## Decisions

- **Таблица `receipts`** (миграция `007-create-receipts.yaml`): `id bigint identity`, `account_id` → FK на `accounts` (`NOT NULL`), `period_month date` (первое число месяца квитанции — календарный тип удобнее для сортировки и ограничений, чем строка), `file_key varchar(36)` (`UNIQUE NOT NULL`), `size_bytes bigint`, `sha256 char(64)`, `published_at timestamptz` (`NOT NULL DEFAULT now()`), `is_test boolean NOT NULL DEFAULT false`. `UNIQUE(account_id, period_month)`, `CHECK (size_bytes > 0)`, FK без каскада (как в остальной модели). В API месяц — строка `ГГГГ-ММ`, преобразование в сущности/сервисе.
- **Интерфейс хранилища:** `ReceiptStorage` — `String save(InputStream content, long maxBytes)` (возвращает ключ, бросает `PayloadTooLargeException`), `Optional<InputStream>`/`Resource open(String key)`, `void delete(String key)`. `FileSystemReceiptStorage` — реализация на каталоге `receipts.storage.path`. Альтернатива «bytea в БД» не выбрана по обсуждению: раздувает БД и бэкапы; S3 сразу — избыточно.
- **Запись файла.** Тело читается потоком в временный файл `<key>.tmp` в том же каталоге с подсчётом байт (прерывание на `maxBytes + 1` → удаление временного файла → `413`), параллельно считается SHA-256 и проверяется заголовок `%PDF-` в первых байтах. После успеха — `Files.move(..., ATOMIC_MOVE)` в `<key>`. Ключ — `UUID.randomUUID()`; на чтении и удалении ключ проверяется регулярным выражением UUID (защита от обхода каталогов), итоговый путь дополнительно проверяется `startsWith(base)` после `normalize()`.
- **Целостность при сбоях.** Порядок: записать файл → в транзакции вставить/обновить запись → при ошибке БД удалить новый файл (в `catch`); при замене старый файл удаляется в `TransactionSynchronization.afterCommit`, чтобы откат транзакции не оставил запись без файла. Остаточные `.tmp` файлов после падения процесса безвредны; при старте их можно подчищать (удаляются `.tmp` старше суток).
- **Публикация — `PUT` с телом `application/pdf`, а не multipart:** операция идемпотентна (то же состояние при повторе), не требует увеличения лимитов multipart и разбора формы; администратор загружает через `curl --data-binary @file.pdf`. Размер ограничивается самим чтением потока (`receipts.max-size`), поэтому настройки `spring.servlet.multipart` не нужны. Ответ: `201` для нового, `200` для замены, тело `{month, size, sha256, published_at}`.
- **Проверка месяца.** Формат `^\d{4}-(0[1-9]|1[0-2])$`; месяц из будущего (после текущего месяца по `Clock`) отклоняется `400`, чтобы опечатка не создала «будущую» квитанцию. Для скачивания неверный формат даёт `404` (ресурса нет).
- **Токен администратора** — временная мера, пока нет авторизации: заголовок `X-Admin-Token` сравнивается с `receipts.admin-token` через `MessageDigest.isEqual` (постоянное время). Пустой/незаданный токен → публикация всегда `403`. В `application-dev.yml` — токен `dev-admin-token`; в `prod` значения по умолчанию нет (`RECEIPTS_ADMIN_TOKEN` из `.env.prod`, добавляется в `.env.example` и в `docker-compose.prod.yml`). Чтение квитанций токеном не защищено — см. риски.
- **Скачивание.** Контроллер возвращает `ResponseEntity<Resource>` (потоковая отдача, без загрузки файла в память) с `Content-Type: application/pdf`, `Content-Length` из метаданных и `Content-Disposition: attachment; filename="receipt-<номер>-<месяц>.pdf"`. Если файла на диске нет — `404` и запись в журнал (`ERROR`), метаданные не трогаются. Заголовок `X-Content-Type-Options: nosniff` добавляет nginx.
- **Структура кода** (пакет `receipt`): `ReceiptEntity`, `ReceiptRepository`, `ReceiptStorage`, `FileSystemReceiptStorage`, `ReceiptService`, `ReceiptController`, `ReceiptProperties` (`@ConfigurationProperties("receipts")`: `storage.path`, `maxSize`, `adminToken`), DTO ответов. `@ConfigurationPropertiesScan` уже включён.
- **Docker.** В `docker-compose.yml` для `backend` добавляется том `receipts_data:/data/receipts` и `RECEIPTS_STORAGE_PATH: /data/receipts`; в `backend/Dockerfile` перед `USER app` создаётся `/data/receipts` с владельцем `app` (иначе новый именованный том принадлежит root, и запись упадёт). В `infra/nginx/dev.conf` и `prod.conf` для `location /api/` — `client_max_body_size 6m`. Локально (IDE) каталог по умолчанию `./data/receipts` (профиль `dev`), добавляется в `.gitignore`.
- **Фронтенд: вкладки без роутера.** Активная вкладка — состояние `MeterReadingsPage` (он уже владеет загрузкой счёта, шапкой и состояниями ошибок, поэтому они общие для вкладок). Начальное значение берётся из `?tab=` (`receipts`, любое другое → показания), переключение — `window.history.replaceState` с сохранением остальных параметров (`account`) и обновлением состояния. Не вводим `react-router`: на экране одна страница и две вкладки, зависимость не оправдана; адрес остаётся пригодным для ссылок и обновления.
- **Фронтенд: компоненты.** `ReceiptsTab` (заголовок «Квитанции» тем же стилем, что `PeriodCaption`, список строк `Card` antd, `Spin`, сообщение о пустом списке, `Alert` с кнопкой «Повторить»). `receiptsApi.ts`: `fetchReceipts(number)` → `ok | error` (404 счёта уже обработан оболочкой) и `receiptUrl(number, month)`. `receiptFormat.ts`: размер (`Б`, `КБ`, `МБ`, десятичная запятая) и дата `ДД.ММ.ГГГГ`. `months.ts`: названия месяцев (именительный и родительный падежи), вынесенные из `PeriodCaption`, чтобы не дублировать. Месяц квитанции `ГГГГ-ММ` превращается в «Октябрь 2026» без `Date` (без часовых сдвигов).
- **Суммы и их мета (миграция `008-add-receipt-amounts.yaml`).** В `receipts` добавляются `capital_repair_amount numeric(12,2)`, `utilities_amount numeric(12,2)`, `amounts_source varchar(16)` и `amounts_at timestamptz`, все `NULL`. Ограничения БД: суммы неотрицательны, обе заданы или обе `NULL` (`(capital_repair_amount IS NULL) = (utilities_amount IS NULL)`), источник из `MANUAL`/`PARSED`, и источник с временем обязательны, когда суммы заданы (и пусты, когда нет). Так будущий разбор PDF просто пишет те же столбцы с `PARSED`. Рубли — единственная валюта, отдельной колонки нет. Деньги — `numeric`/`BigDecimal`, не `double`.
- **Суммы при публикации (пока нет разбора PDF).** `PUT …/{month}` принимает необязательные параметры `capital_repair` и `utilities`. Строгая проверка текстом (`^\d{1,10}(\.\d{1,2})?$`): без знака, экспоненты и лишних знаков; только один параметр — `400`. Замена файла без параметров сбрасывает суммы (они относились к старому файлу). Ответы публикации и списка получают `capital_repair_amount` и `utilities_amount` (`BigDecimal`, при `null` — `null`); источник и время записи наружу не отдаются. Параметры — временный способ ввода, который не конфликтует с будущим разбором: разбор выставит `PARSED` и вправе перезаписать их.
- **Разбор PDF — не в этом изменении.** Место для него — сервис публикации после проверки заголовка PDF и до записи в БД (получить суммы из файла, источник `PARSED`); потребует выбора библиотеки разбора и устойчивости к формату квитанции. Здесь только схема и контракт.
- **Фронтенд: аккордеон.** Вместо карточек — `Collapse` из antd с `accordion` (одна открытая панель), в `items` — по панели на квитанцию; заголовок — `formatReceiptMonth`, содержимое — две строки «Капитальный ремонт» и «Коммунальные услуги» с суммами через `formatMoney` и ссылка «Скачать PDF». Открыта по умолчанию самая новая (`defaultActiveKey`). Размер и дата публикации не рисуются, поэтому `formatFileSize` и `formatPublishedDate` удаляются как неиспользуемые (поля `size` и `published_at` в ответе API остаются). `formatMoney`: `toFixed(2)`, десятичная запятая, неразрывный пробел между тысячами, суффикс « ₽»; `null` → «—».
- **Фронтенд: скачивание ссылкой.** Строка содержит `<a href="/api/accounts/{n}/receipts/{ГГГГ-ММ}" download>`: браузер скачивает файл по `Content-Disposition: attachment`, без `fetch` и без хранения файла в памяти страницы; через Vite-прокси и nginx адрес работает одинаково. Токен администратора на фронтенде не используется и нигде не хранится.
- **Шапка.** `AppHeader` получает активную вкладку и обработчик выбора; «Показания» и «Квитанции» — кнопки-ссылки, активный пункт выделен основным цветом, «Заявки» остаётся неактивным текстом. Изменение требования «Шапка экрана с данными лицевого счёта» оформляется дельтой `meter-readings-screen` (см. задачу 8.3).
- **Тесты фронтенда** (vitest + Testing Library, `fetch` подменяется): форматирование размера и даты на границах, `receiptUrl`, переключение вкладок кликом и по `?tab`, сохранение `account` в адресе, список в порядке API, ссылки скачивания, загрузка, пустой список, ошибка и повтор, отсутствие элементов публикации, независимость вкладки показаний от ошибки списка.
- **Тесты.**
  - Юнит: `FileSystemReceiptStorage` во временном каталоге (запись, чтение, удаление, лимит размера, мусорный ключ с `..`, отсутствие `.tmp` после отказа), проверка формата месяца.
  - Интеграционные (Testcontainers + временный каталог): публикация и скачивание байт в байт с проверкой SHA-256; замена файла (старый удалён); список в порядке «новые первыми»; чужие счета не пересекаются; токен (нет, неверный, не настроен); не PDF, пусто, слишком большой (`413`, ничего не создано); неверный и будущий месяц; неизвестный счёт; потерянный файл; откат файла при сбое БД (имитация исключения); ограничения БД (повтор счёта и месяца); `is_test` наследуется от счёта.
  - Миграция проверяется в `MeterVerificationUpgradeIT`-стиле не нужна (таблица новая); достаточно общих IT.

## Risks / Trade-offs

- [Суммы вводит человек вместе с публикацией и могут не совпасть с суммами в PDF] → до разбора PDF это единственный источник, поэтому он помечен `MANUAL`; разбор позже выставит `PARSED` и сделает данные проверяемыми.
- [Прочерк вместо сумм у квитанций без сумм может сбить с толку] → допустимо: так выглядят все квитанции, опубликованные без параметров.
- [Вкладка и ссылки скачивания открыты без авторизации: по номеру счёта из адреса любой видит список и скачивает PDF, а адрес со вкладкой легко переслать] → усиливает главный риск ниже; до публикации реальных квитанций нужна авторизация жильцов.
- [Адрес со вкладкой меняется вручную через `history.replaceState`, без роутера: кнопка браузера «назад» не возвращает на прошлую вкладку] → допустимо для двух вкладок; при росте числа разделов переходим на роутер отдельным изменением.
- [Чтение квитанций без авторизации: по номеру счёта любой получит персональные данные] → наиболее серьёзный риск изменения; допустимо только для тестовых данных. **До публикации реальных квитанций обязательна авторизация жильцов** (скачивание — только своих счетов); токен администратора — временная мера для загрузки.
- [Токен администратора в заголовке и в `.env`: утечка даёт право перезаписывать квитанции] → хранится только в окружении, передаётся только по HTTPS (nginx), сравнивается за постоянное время; настоящая роль администратора — вместе с авторизацией.
- [Файлы и БД бэкапятся раздельно, возможен рассинхрон] → в README описывается, что том `receipts_data` и БД резервируются вместе; потерянный файл даёт `404` и запись в журнал, а не ошибку сервера. Сверка метаданных с диском вне рамок.
- [Размер: несколько МБ на файл при ≈100 квартир × 12 месяцев в год] → порядка сотен МБ в год, том справляется; лимит `receipts.max-size` ограничивает нагрузку.
- [Замена квитанции без истории] → осознанно (исправленная квитанция заменяет прежнюю); версионирование — отдельное изменение при необходимости.
- [Временные файлы после аварийного завершения] → не видны через API; подчищаются при старте (старше суток).
- [Лимит nginx 6 МБ и лимит приложения 5 МБ могут разойтись при смене настроек] → значения описаны в README рядом; запас в nginx сделан намеренно, точную проверку выполняет приложение.
