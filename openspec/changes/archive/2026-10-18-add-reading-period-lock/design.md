## Context

Бэкенд: `AccountService` собирает ответ `GET /api/accounts/{number}` (счётчики, показания, `previous`), `ReadingService` сохраняет показания (проверки значения, дубли, `METER_NOT_FOUND`, блокировка счётчиков, атомарность), бин `Clock` уже есть. Конфигурация: `application.yml`, профильные `application-dev.yml` и `application-prod.yml`. Фронтенд: `MeterReadingsPage` строит карточки из `toMeters(account.meters, today)` и подзаголовок из месяца и `DEADLINE_DAY`; `ReadingsForm` собирает запрос из заполненных полей; `MeterCard`/`ReadingField` рисуют карточку и поле. Сдача определяется по датам существующих показаний — отдельной таблицы или колонки не нужно. Решения владельца: проверка на бэкенде, периоды с 26-го по 25-е (день закрытия настраивается), параметр тестирования на бэкенде, фронтенд только показывает состояние. Мотивация — в proposal.md, требования — в дельта-спеках.

## Goals / Non-Goals

**Goals:**
- Единый источник правды о периоде и блокировке — бэкенд.
- Простое отображение на фронтенде без собственных сравнений дат.
- Переключатель для тестирования, не затрагивающий рабочий режим.

**Non-Goals:**
- Правка и отмена уже сданных показаний, ввод задним числом за пропущенные периоды.
- Часовые пояса, праздники, уведомления о начале периода.
- Новые таблицы, миграции и колонки.
- Авторизация (остаётся отдельным изменением).

## Decisions

- **Период — чистый класс `ReadingPeriod`** (record `start`, `end`, `next`; фабрика `ReadingPeriod.containing(LocalDate date, int closingDay)`). Правило: если `date.day <= closingDay` — период кончается `closingDay` текущего месяца, иначе `closingDay` следующего; начало — день после `closingDay` предыдущего месяца; `next` = `end + 1 день`. Календарные особенности отсутствуют, пока `closingDay` в диапазоне 1–28 (проверка при старте, чтобы 29–31 не ломались на февральских месяцах); значение по умолчанию 25. Название месяца в API не передаётся: клиент берёт его из `end`.
- **Конфигурация:** `@ConfigurationProperties("readings.period")` record `ReadingPeriodProperties(int closingDay, boolean enforced)` с `closingDay = 25`, `enforced = true` в `application.yml`; профили `dev` и `prod` значение не переопределяют: проверка включена везде (решение владельца: иначе блокировка не видна при разработке). Переопределение окружением: `READINGS_PERIOD_ENFORCED=true|false` (relaxed binding). Валидация `closingDay` через `@Min(1)`/`@Max(28)` не добавляется (нет зависимости Bean Validation) — проверка вручную в конструкторе record'а с понятной ошибкой старта.
- **Сдача по датам существующих показаний.** «Показание за текущий период» — последнее показание счётчика с `reading_date` в `[start, end]`. Показания в `AccountService` уже загружены, поэтому выбор делается в памяти; для записи (`ReadingService`) используется запрос «последнее показание счётчика» (уже есть) и сравнение его даты с периодом. Тестовые показания (25 августа и 25 сентября) относятся к периодам «сентябрь» и «сентябрь» соответственно; 25 сентября — последний день периода «сентябрь» (26 августа — 25 сентября), поэтому 18 октября форма открыта.
- **Ответ API.** `AccountResponse` получает `readingPeriod` (`@JsonProperty("reading_period")`: `start`, `end`, `next_start`, `all_submitted`, `enforced`); `Meter` — `current_period_reading` (тип `Reading`, nullable) и `input_locked`. `all_submitted = !meters.isEmpty() && every meter has current_period_reading`. `input_locked = enforced && current_period_reading != null`. Дублирование сдачи/блокировки на клиенте не нужно — клиент читает флаги.
- **Запись.** `ReadingService` перед проверкой значения определяет для каждого счётчика запроса «последнее показание» (уже делает) и, если `enforced` и дата последнего показания в текущем периоде, добавляет `ReadingError(meter, ALREADY_SUBMITTED)`. Код добавляется в тот же список `errors`; при любой ошибке ничего не сохраняется (поведение не меняется). При `enforced = false` проверка пропускается. Значение сравнения «не меньше предыдущего» не меняется.
- **Фронтенд — типы и данные.** `AccountMeter` получает `current_period_reading` и `input_locked`; `Account` — `reading_period`. `Meter` (карточка) получает `locked` и `submitted?: { value, previous? }`. Предыдущее значение для заблокированного счётчика берётся из `current_period_reading.previous`, для остальных — из `readings[0]` (как сейчас).
- **Фронтенд — подпись периода.** Новый компонент `PeriodCaption` получает `reading_period` и считает только текст: месяц из `end` (массив названий в именительном падеже) и «<день> <месяц>» из `end` (родительный падеж); состояние — `all_submitted`, «часть» (есть заблокированные, но не все) или «ничего». Сравнения с текущей датой нет. Старая константа `DEADLINE_DAY` и строка «Месяц Год · Передайте показания до 25 числа» удаляются.
- **Фронтенд — карточка и форма.** `ReadingField` для `locked` рисует `Input disabled` с отформатированным значением без привязки к `Form.Item` (значение не участвует в форме); в `ReadingsForm` собираются только незаблокированные поля. Если заблокированы все карточки (и их хотя бы одна), кнопки остаются на экране, но получают `disabled`. После сохранения срабатывает уже существующий перезапрос счёта: флаги приходят с сервера, поля блокируются, подпись меняется. Для ошибки `ALREADY_SUBMITTED` показывается общее предупреждение «Показания за этот период уже сданы» (а не ошибка под полем: после перезапроса карточка становится заблокированной и поле исчезает); перезапрос уже есть для `invalid`.
- **Тестовый режим.** Пометка рисуется при `reading_period.enforced === false`; никаких фронтенд-переменных окружения не добавляется.
- **Тесты.**
  - Бэкенд: `ReadingPeriodTest` (18 октября, 25 октября, 26 октября, 1 января, 26 декабря, февраль/високосный год, 1 и 31 число, `closingDay` 1/28 и недопустимые 0/29); `AccountApiIT` с фиксированным `Clock` (поля `reading_period`, `current_period_reading`, `input_locked`, `all_submitted` для сдано/не сдано/часть/нет счётчиков/`enforced` выкл.); `ReadingsApiIT` с `readings.period.enforced=true` (повтор → `ALREADY_SUBMITTED`, новый период → успех, прошлый период → успех, один из двух счётчиков → ничего не сохранено, смешанные ошибки списком) и с `false` (повтор разрешён); `ReadingsApiIT` явно выключает проверку (`readings.period.enforced=false`), потому что подаёт показания по одному счётчику много раз.
  - Фронтенд: `PeriodCaption` (три состояния, январь/декабрь для падежей), карточки (заблокированная, частичная, все сданы — кнопки недоступны), запрос не содержит заблокированные счётчики, `ALREADY_SUBMITTED`, пометка тестового режима, новый период после перезапроса.

## Risks / Trade-offs

- [Дата сервера определяет период: если часы сервера уйдут, граница сместится] → ожидаемо для серверной проверки; часы сервера надёжнее устройств пользователей.
- [День закрытия 25 «зашит» в конфигурацию, а не в БД] → настраивается свойством без пересборки; индивидуальных периодов по домам нет (дом один).
- [Сдача определяется по дате показания, а не по явному признаку: показание, внесённое администратором в БД в текущем периоде, заблокирует счётчик] → осознанно: так «сдано» совпадает с тем, что видно в истории; для исправления нужны правки в БД.
- [Показания нельзя исправить после сдачи, а ошибка ввода возможна] → вне рамок; нужен отдельный сценарий исправления с правилами.
- [При разработке блокировка мешает повторно проверять отправку] → проверка выключается переменной `READINGS_PERIOD_ENFORCED=false`, а пометка «Тестовый режим» не даёт забыть, что она выключена; README объясняет оба случая.
- [Периоды называются по месяцу окончания: 28 октября экран покажет «за ноябрь»] → следует из модели «26-е — 25-е»; зафиксировано в спеке сценариями границ.
- [Блокировка по периоду на сервере не защищает от неверных значений внутри периода] → остаются существующие проверки (не меньше предыдущего, формат).
