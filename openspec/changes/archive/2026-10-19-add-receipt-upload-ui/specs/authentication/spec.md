## MODIFIED Requirements

### Requirement: Защита API по умолчанию
Все эндпоинты `/api/**`, кроме `POST /api/auth/login` и публикации квитанции `PUT /api/accounts/{number}/receipts/{month}`, SHALL требовать валидный токен в заголовке `Authorization: Bearer <token>`. Публикация квитанции не требует токена входа, если запрос содержит верный `X-Admin-Token`; токен входа, если он передан, MUST быть действительным и учитывается (роль `ADMIN` разрешает публикацию). Запрос без токена или с невалидным токеном SHALL получить `401` с заголовком `WWW-Authenticate: Bearer`. `/api/actuator/health` MUST оставаться доступным без токена. Сессии на сервере создаваться не должны.

#### Scenario: Запрос без токена
- **WHEN** клиент запрашивает `GET /api/accounts/000000000001` без `Authorization`
- **THEN** ответ `401`, данных счёта в теле нет

#### Scenario: Проверка работоспособности
- **WHEN** клиент запрашивает `GET /api/actuator/health` без токена
- **THEN** ответ `200`

#### Scenario: Публикация квитанции
- **WHEN** клиент отправляет `PUT` публикации квитанции с верным `X-Admin-Token` и без JWT
- **THEN** запрос не отклоняется как неаутентифицированный и обрабатывается по правилам спецификации `receipts`

#### Scenario: Публикация с токеном входа администратора
- **WHEN** клиент отправляет `PUT` публикации квитанции с токеном входа администратора и без `X-Admin-Token`
- **THEN** запрос обрабатывается по правилам спецификации `receipts`

#### Scenario: Нет серверной сессии
- **WHEN** клиент успешно выполнил запрос с токеном
- **THEN** ответ не содержит `Set-Cookie`
