## Context

Публикация уже реализована в `ReceiptController.publish`/`ReceiptService.publish`: тело запроса — сырой PDF, суммы — параметры `capital_repair` и `utilities`, право даёт заголовок `X-Admin-Token`. После изменения `add-authentication` в системе есть роль `ADMIN` и JWT; маршрут публикации в `SecurityConfig` открыт (`permitAll`), но фильтр resource server всё равно проверяет и аутентифицирует токен, если он передан. Вкладка «Квитанции» (`ReceiptsTab`) читает список и скачивает файлы через `apiFetch`; в первой версии изменения в неё была встроена форма, теперь форма уходит на отдельную вкладку. Мотивация — в `proposal.md`.

## Goals / Non-Goals

**Goals:**
- Администратор публикует и заменяет квитанции из интерфейса, не зная общего токена.
- Скриптовый путь с `X-Admin-Token` продолжает работать без изменений.
- Сервер сам решает, кому можно публиковать; интерфейс — лишь удобство.

**Non-Goals:**
- Удаление квитанций, пакетная загрузка, автоматический разбор сумм из PDF.
- Серверный поиск и пагинация списка квартир.
- Отказ от `X-Admin-Token` и перенос публикации на `multipart`.

## Decisions

### 1. Право публикации: `ADMIN` из JWT или верный `X-Admin-Token`
Контроллер получает `Authentication` (может быть `null`/анонимной, т. к. маршрут `permitAll`) и передаёт в сервис флаг `admin` — `true`, если среди authorities есть `ROLE_ADMIN`. `ReceiptService.checkToken` заменяется на `checkAllowed(admin, token)`: пропускает при `admin == true`, иначе проверяет токен прежним способом (постоянное по времени сравнение, пустой токен конфигурации = отказ). Не-админ с JWT и без токена получает `403` — как и анонимный клиент без токена.
*Альтернативы:* (а) `@PreAuthorize("hasRole('ADMIN')")` на методе — сломал бы скриптовый путь по токену; (б) убрать токен совсем — ломает существующие скрипты и тесты, а это отдельное решение. Выбран компромисс с минимальным изменением поведения.

Недействительный JWT на этом маршруте даёт `401` ещё в фильтре — это зафиксировано в спеке и совпадает с поведением остальных эндпоинтов.

### 2. Маршрут в `SecurityConfig` не меняется
`PUT /api/accounts/*/receipts/*` остаётся `permitAll`: иначе потребовался бы условный матчер «JWT или заголовок». Авторизационное решение принимается в сервисе, где уже находится проверка токена, — одно место вместо двух.

### 3. Загрузка из браузера: `fetch` с телом `File`
`publishReceipt(accountNumber, month, file, amounts)` вызывает `apiFetch(url, { method: 'PUT', headers: { 'Content-Type': 'application/pdf' }, body: file })`. Браузер отправляет файл потоком, без `multipart` и без чтения в память; это ровно то, что ожидает сервер. Параметры сумм добавляются в query только если заполнены оба. Результат — размеченный union (`created | replaced | invalid | too-large | not-found | forbidden | error`), функция не бросает исключений, как остальной `*Api`-код. `401` обрабатывает `apiFetch` (завершает сессию).

### 4. Форма на antd, без `Upload`-загрузчика
Используются `Form`, `Select showSearch` для квартиры, `DatePicker picker="month"` (с `disabledDate` для будущих месяцев), `Upload` в режиме `beforeUpload={() => false}` с `maxCount={1}` и `accept=".pdf"` — компонент только выбирает файл, отправку делает наш код, так что прогресс-бар и автозагрузка не нужны. `InputNumber` с `decimalSeparator=","`, `precision=2`, `min=0` для сумм. Правила валидации (PDF, ≤ 5 МБ, обе суммы или ни одной) живут в чистой функции `validatePublication` — её проще тестировать, и она не дублирует сервер, а лишь экономит запрос. Лимит 5 МБ — константа на фронтенде, комментарием связанная с `receipts.max-size` (nginx пропускает до 6 МБ). Квартира не входит в `validatePublication`: пока она не выбрана, кнопка просто недоступна.

### 5. Квартира выбирается явно, список — отдельный эндпоинт
Квартира соответствует лицевому счёту (по одному счёту на квартиру). Чтобы публикация «не туда» была невозможна, поле «Квартира» обязательно, по умолчанию пусто, а счёт шапки не подставляется. Список даёт новый `GET /api/accounts` (только `ADMIN`, `@PreAuthorize("hasRole('ADMIN')")`): запрос через `JdbcClient` по `accounts` и `addresses`, сортировка по номеру счёта, без пагинации — в одном доме счетов сотни, а `Select` с поиском с этим справляется. `/api/auth/me` для этого не годится: он возвращает только номера, без адреса и квартиры. Элемент списка: «кв. 1 · ул. Тестовая, д. Тест (счёт 000000000001)»; поиск идёт по этому тексту.
*Альтернатива:* расширить `/api/auth/me` адресами — раздувает ответ, который запрашивается при каждом входе и нужен всем ролям.

### 6. Подтверждение замены — по квитанциям выбранной квартиры
Форма запрашивает `GET /api/accounts/{number}/receipts` при выборе квартиры и после каждой публикации и хранит только список месяцев. Пока список выбранной квартиры не загружен, кнопка недоступна (иначе можно молча заменить квитанцию), при ошибке показывается «Повторить». Гонка (месяц опубликовали в другой вкладке между загрузкой и нажатием) безопасна: сервер заменит файл, ответ `200` покажет «заменена». Подтверждение — `Popconfirm`, открывающийся программно после успешной проверки формы.

### 7. Вкладка «Выставить квитанции»
Вкладки задаются ролью: у `ADMIN` одна вкладка `upload` («Выставить квитанции»), у `OWNER` — `readings` и `receipts`, у `RESIDENT` — только `readings`. `allowedTab(tab, role)` сводит запрошенную вкладку к допустимой (администратору любая сводится к `upload`, жильцу `receipts` к `readings`); в адресе остаётся только `tab=receipts` собственника, у администратора параметр `tab` не пишется и не читается. Пункты «Показания» и «Квитанции» администратору не рисуются. Вкладка не зависит от лицевого счёта шапки и не использует `ReceiptsTab`: `ReceiptsTab` снова только читает список и скачивает файлы, а `MeterReadingsPage` рисует `UploadReceiptTab` (заголовок «Выставить квитанции» и `PublishReceiptForm`). Скрытие вкладки — удобство, защита — решение 1 и роль `ADMIN` на `GET /api/accounts`.

### 8. Шапка и экран администратора без лицевого счёта
У администратора нет «своей» квартиры, поэтому `MeterReadingsPage` для роли `ADMIN` вообще не вызывает `GET /api/accounts/{number}` и не показывает состояния «Лицевой счёт не найден»/«не привязан». `AppHeader` принимает `account: Account | null`: при `null` скрываются блок с адресом и номером счёта и список совладельцев в меню профиля, остаётся название ТСЖ, навигация, иконки, логин и роль, «Выйти». Параметр `?account=` для администратора больше не используется (`resolveAccountNumber` берёт первый счёт пользователя только для собственника и жильца). Серверное API не меняется: администратор по-прежнему может читать счета и показания напрямую, скрыты только вкладки интерфейса.

### 9. Обновление после публикации
После успеха форма очищает месяц, файл и суммы, оставляет квартиру выбранной (администратор обычно грузит несколько месяцев подряд) и перезапрашивает список месяцев этой квартиры. Сообщение об успехе — `Alert` над формой, а не `message.success`, чтобы его было видно в тестах и не терялось на мобильных.

## Risks / Trade-offs

- [Ошибочная замена существующей квитанции] → подтверждение (решение 5); суммы при замене сбрасываются, если не указаны, — это поведение сервера, и подтверждение прямо об этом предупреждает.
- [Публикация не на ту квартиру] → квартира обязательна и не подставляется; в сообщении об успехе и в подтверждении указан номер квартиры.
- [Длинный список квартир в `Select`] → поиск по тексту; при росте дома — серверный поиск и пагинация отдельным изменением.
- [Большой файл по медленной связи] → кнопка блокируется на время запроса, показывается индикатор загрузки; отмену не делаем.
- [Расхождение лимитов клиента и сервера] → клиентская проверка лишь предварительная, сервер возвращает `413`, и интерфейс показывает то же сообщение.
- [`X-Admin-Token` остаётся обходным путём без аудита пользователя] → вне рамок; кандидат на отдельное изменение.

## Migration Plan

Миграций БД и новых переменных окружения нет. Выкладываются бэкенд и фронтенд вместе; откат — предыдущие образы (скриптовая публикация по токену продолжает работать в обеих версиях).
