## Context

См. proposal.md. `ReceiptFileMigration` — `ApplicationRunner`, который при старте копирует файлы записей `receipts` из каталога `receipts.migration.source-path` в бакет квитанций. Каталог в dev — `./data/receipts`, в Docker — том `receipts_data`, смонтированный только для чтения в `/data/receipts-legacy`. Других потребителей настройки нет.

## Decisions

1. **Удалить, а не отключить.** Код, настройка и том нужны были только для разового переноса; оставлять их «на всякий случай» значит держать мёртвый код при каждом старте.
2. **Порядок в окружениях.** Перед выкладкой в окружении со старым томом нужно убедиться по журналу прежней версии («copied N, already there M, no source file 0, errors 0») и скачав пару квитанций, что всё перенесено. Сам том `receipts_data` после выкладки остаётся на диске, пока его не удалят вручную (`docker volume rm <проект>_receipts_data`): удаление данных не входит в это изменение.
3. **Конфигурация.** `ReceiptProperties` сохраняет `maxSize` и `adminToken`; блок `receipts` в `application-prod.yml` пустеет и удаляется, в `application-dev.yml` остаётся только `admin-token`. Лишний параметр, заданный в окружении, Spring Boot игнорирует, поэтому старые `.env`-файлы не ломаются.
4. **Спеки.** Требование «Перенос существующих квитанций» удаляется (`REMOVED`); в требованиях «Файловое хранилище» и «Конфигурация квитанций» убираются ссылки на него; описание назначения `object-storage` правится после синхронизации.

## Risks / Trade-offs

- [В каком-то окружении перенос не выполнен] → условие выкладки (п. 2); том не удаляется автоматически.
- [Проверка в dev] → три файла `data/receipts` уже сверены с S3 по SHA-256 и удалены.
