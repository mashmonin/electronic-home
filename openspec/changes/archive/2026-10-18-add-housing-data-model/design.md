## Context

Бэкенд — Spring Boot 4, PostgreSQL, Liquibase (`classpath:db/changelog/db.changelog-master.yaml`, сейчас `databaseChangeLog: []`), `ddl-auto: validate`. Схема меняется только Liquibase. Интеграционные тесты используют Testcontainers (`postgres:16`, см. `HealthEndpointIT`). Требования — в `specs/housing-data-model/spec.md`; мотивация — в proposal.md. Решения пользователя: «адрес» = квартира; совладельцы лицевого счёта задаются отдельной связкой; полей минимум.

## Goals / Non-Goals

**Goals:**
- Создать таблицы и ограничения, выраженные декларативно (PK, FK, UNIQUE, NOT NULL), чтобы целостность гарантировала БД, а не код.
- Покрыть миграцию интеграционным тестом на реальном PostgreSQL.

**Non-Goals:**
- JPA-сущности, репозитории, REST API, перевод фронтенда с заглушки.
- Доли собственности, периоды владения, контакты, документы, показания и счётчики.
- Проверка, что совладелец счёта обязательно является собственником адреса этого счёта (см. Риски).
- Тестовые и демонстрационные данные в миграции.

## Decisions

- **Схема (все имена в snake_case, таблицы во множественном числе):**
  - `addresses(id, street, house, apartment)`, `UNIQUE(street, house, apartment)`, все три поля `NOT NULL`.
  - `accounts(id, number, address_id)`, `number` `UNIQUE NOT NULL`, `address_id` `NOT NULL` → FK на `addresses`.
  - `owners(id, full_name)`, `full_name` `NOT NULL`, без уникальности.
  - `address_owners(address_id, owner_id)`, составной PK, FK на обе таблицы.
  - `account_owners(account_id, owner_id)`, составной PK, FK на обе таблицы.
- **Идентификаторы — `bigint generated by default as identity`.** Альтернатива — UUID: удобнее для публичных ссылок, но дороже по индексам и не нужна, пока идентификаторы не отдаются наружу. Если понадобится, меняется отдельной миграцией.
- **Номер дома и квартиры — строки (`varchar`).** Встречаются «12А», «3/1», поэтому числовой тип не подходит. Номер счёта — `varchar(32)`, а не число, чтобы сохранять ведущие нули (`0004521873`).
- **Связки с составным PK, без собственного `id`.** Пара уникальна по определению, дополнительный суррогатный ключ не нужен; при добавлении полей (доля, даты) PK пересматривается отдельным изменением. Индекс по второй колонке (`owner_id`) создаётся явно для обратных выборок «квартиры собственника».
- **FK без каскадного удаления (`RESTRICT`).** Удаление записи со связями отклоняется БД; случайно стереть собственника или адрес нельзя. Альтернатива `ON DELETE CASCADE` скрыто теряет данные.
- **Индекс по `accounts.address_id`** для выборки счетов адреса.
- **Один changelog-файл на изменение:** `db/changelog/changes/001-create-housing-tables.yaml`, подключается в master через `include`. Формат YAML — как в уже существующем master. Альтернатива — один большой master: хуже читается при росте числа миграций.
- **Тест:** интеграционный тест на Testcontainers применяет миграции и через JDBC проверяет сценарии спеки: дубли адреса/счёта/связок отклоняются, несколько счетов у адреса и несколько владельцев допускаются, удаление со связями отклоняется. Сущности JPA не создаются, поэтому `ddl-auto: validate` ничего не проверяет.

## Risks / Trade-offs

- [Совладелец счёта не обязан быть собственником адреса: БД это не проверяет] → осознанно оставлено на уровень приложения (будущий API/сервис); декларативное решение — составные FK с `address_id` в `account_owners` — усложняет модель и откладывается до появления бизнес-правил.
- [Минимальные поля не хватит для реальной работы: нет доли, дат, контактов] → дополняется отдельными миграциями; составной PK связок и nullable-добавление колонок делают это дёшево.
- [`UNIQUE(street, house, apartment)` чувствителен к написанию: «Садовая» и «садовая» — разные адреса] → нормализация ввода — задача API; в БД регистронезависимость не вводится.
- [Однофамильцы неотличимы без доп. полей] → допускается в этой версии; идентификация собственников появится вместе с контактами/авторизацией.
- [Миграция уже применённого changeSet не должна изменяться] → дальнейшие правки только новыми changeSet.
