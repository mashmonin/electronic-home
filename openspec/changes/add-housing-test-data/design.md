## Context

Схема из `housing-data-model` создана миграцией `001-create-housing-tables.yaml`, таблицы пусты. Профили `dev` и `prod` обязательны (`ProfileGuard`); конфигурация профилей — `application-dev.yml` и `application-prod.yml`. Liquibase запускается при старте приложения. Интеграционные тесты идут в профиле `dev` на Testcontainers. Решения владельца: признак — колонка `is_test` во всех пяти таблицах, данные только в `dev`, город не хранится, счёт на квартире 1 с двумя совладельцами. Мотивация — в proposal.md, требования — в спеке.

## Goals / Non-Goals

**Goals:**
- Отличать тестовые записи от настоящих на уровне данных.
- Гарантировать, что в `prod` тестовых записей нет, а в `dev` они воспроизводимо создаются.

**Non-Goals:**
- Город в адресе, любые новые поля кроме `is_test`.
- Перевод фронтенда на тестовые данные; API.
- Механизм массовой очистки тестовых данных (достаточно `DELETE ... WHERE is_test`).

## Decisions

- **`is_test boolean NOT NULL DEFAULT false` во всех пяти таблицах**, отдельной миграцией `002-add-is-test-column.yaml`. Существующий changeSet 001 не правится. Альтернатива — отдельная схема или отдельная БД для тестовых данных: сложнее запросы и миграции, не нужно при одном экземпляре.
- **Данные грузятся Liquibase changeSet'ами с `context: dev`** (`003-seed-test-data.yaml`). В `application-dev.yml` задаётся `spring.liquibase.contexts: dev`, в `application-prod.yml` — `prod`. Так сид физически не выполняется в prod и повторно не применяется в dev (Liquibase запоминает changeSet). Альтернатива — `CommandLineRunner`/SQL-скрипт при старте в dev: придётся самим обеспечивать идемпотентность.
- **Явный контекст и в prod**, а не «отсутствие контекстов»: без контекстов Liquibase выполнит все changeSet'ы, в том числе dev-сид, поэтому оба профиля обязаны задавать `contexts`.
- **Связи в сиде — через подзапросы** (`valueComputed: (SELECT id FROM owners WHERE full_name = ... AND is_test)`), а не через зашитые числовые id: identity-последовательность не зависит от порядка и состояния БД.
- **Значения адреса:** `street = 'ул. Тестовая'`, `house = 'Тест'`, `apartment = '1'` и `'2'` (префикс «ул.» — как в заглушке фронтенда). Счёт: `000000000001` (12 цифр, строка, `varchar(32)` вмещает).
- **Откат сида:** `rollback` с `DELETE ... WHERE is_test = true` в порядке «связки → счета → адреса и собственники».
- **Тесты:** (1) профиль `dev` — после миграций есть ровно ожидаемые строки и связи, все с `is_test = true`; (2) `spring.liquibase.contexts=prod` — таблицы пусты, колонка `is_test` существует; (3) вставка без `is_test` даёт `false`. Существующий `HousingSchemaIT` очищает таблицы перед каждым тестом (`TRUNCATE`) и остаётся независимым от сида; его вставки без `is_test` должны продолжать работать благодаря значению по умолчанию.

## Risks / Trade-offs

- [Забытый `contexts` в новом профиле или окружении запустит сид там, где его быть не должно] → контексты заданы в обоих профильных файлах, тест на отсутствие данных при `contexts=prod`.
- [Тестовые данные с `is_test` в общей БД могут попасть в выборки настоящих данных] → будущие запросы API должны фильтровать `is_test = false`; фиксируется как требование к следующим изменениям, здесь только колонка.
- [Без города адрес «ул. Тестовая, д. Тест» неполный] → осознанное решение; при добавлении `city` отдельной миграцией сид дополняется новым changeSet'ом.
- [Сид использует поиск по ФИО с `is_test` — при ручном добавлении однофамильца с `is_test = true` в dev подзапрос вернёт несколько строк] → маловероятно в dev; подзапросы ограничены `LIMIT 1` не используются сознательно, чтобы ошибка была видна.
