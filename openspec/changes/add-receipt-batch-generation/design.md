## Context

Квитанции уже умеют: `ReceiptService.publish` (PDF, суммы, источник `MANUAL`/`PARSED`, замена), хранение в бакете квитанций, список и скачивание для собственников, ручная форма администратора. Бакеты: квитанции, вложения, акты. Фоновой обработки в проекте нет, PDF не генерируется, Excel не читается.

Ведомость (`сентябрь_2026.xls`, один лист, 8722 строки, 55 столбцов, ~48 тыс. объединённых ячеек): 284 блока «Раздел 1…»; на каждый лицевой счёт два блока подряд — первый ~36 строк «Жилищно-коммунальные услуги» (р/с ТСЖ ...0732), второй ~26 строк «Капитальный ремонт» (р/с ...1112). Блок: заголовок периода «за Сентябрь 2026 г.», ФИО плательщика, адрес (`Кв. N`, `Оф. N`), л/с, площадь, число проживающих, реквизиты получателя, долг, аванс, оплаты, дата последней оплаты, итог, таблица услуг (объёмы, тарифы, начисления) и справочная часть. Мотивация — см. proposal.md.

## Goals / Non-Goals

**Goals:**
- Один загруженный файл → квитанции всех счетов, доступные собственникам; прозрачный ход и итог.
- Использовать существующую публикацию, чтобы собственники и вкладка «Квитанции» не менялись.

**Non-Goals:**
- Другие форматы (`.xlsx`, `.csv`), редактирование ведомости, отправка писем/уведомлений, оплата.
- Пиксельная точность и шрифт Arial печатной формы (используется свободный DejaVu Sans Condensed); состав, порядок, сетка таблиц и пропорции повторяют образец дома.
- Создание отсутствующих счетов/собственников (этим занимается импорт собственников).

## Decisions

1. **Разбор — Apache POI (HSSF, `.xls`)**, потоково по строкам листа; блок находится по «Раздел 1», поля — по меткам и столбцам, как в проверочном скрипте. Альтернатива — просить `.xlsx`/CSV: усложняет работу бухгалтерии. Структура проверяется до создания пакета (период и хотя бы один блок), ошибки структуры — `422`.
2. **Генерация PDF — OpenPDF** (LGPL/MPL) с вложенным в `resources` шрифтом DejaVu Sans Condensed (свободная лицензия, узкий, ближе по ширине к Arial образца). Одна страница A4 альбомная на часть (ЖКУ и капремонт) → PDF из двух страниц на счёт. Вёрстка по образцу PDF дома («61 кв. ком.услуги и кап,ремонт»): разделы 1 и 2 пишутся рядом отдельными таблицами (чтобы рамка раздела 1 не растягивалась до высоты раздела 2), раздел 3 и раздел 4 — одной таблицей с общей сеткой строк; у капремонта раздела 4 нет. Альтернативы: iText 7 (AGPL), PDFBox (больше ручной вёрстки), HTML→PDF (тяжёлый движок). Покрытие шрифтом проверяется тестом на всей кириллице и «№ ₽».
3. **Пакет и позиции в БД** (Liquibase `022-…`): `receipt_batches` (id, month, source_key UUID, size, sha256, status, total/processed/created/replaced/skipped/failed, created_by, created_at, finished_at, error) и `receipt_batch_items` (batch_id, account_number, status, reason). Позиции не хранят ФИО, адреса и суммы. Статусы строками с `CHECK`.
4. **Фоновая обработка** — один `ThreadPoolTaskExecutor` с одним потоком (пакеты по очереди), запуск после коммита создания пакета; файл читается из S3 по ключу, а не из памяти запроса. При старте приложения пакеты `RUNNING`/`QUEUED` помечаются «ошибка: прервана перезапуском». Альтернатива — планировщик/очередь вне процесса: избыточно для одного дома и ~140 квитанций.
5. **Публикация через `ReceiptService`**: PDF → существующий путь (SHA-256, замена, `is_test` совпадает со счётом); суммы `utilities`/`capital_repair` берутся из «Итого к оплате» блоков, источник `PARSED` (значение, зарезервированное спецификацией `receipts` для автоматически полученных сумм, миграция БД не нужна). Каждый счёт — в своей транзакции, чтобы ошибка не откатывала остальные.
6. **Сопоставление счетов**: номер л/с → 12 знаков с нулями слева (как у импортированных счетов); нет в БД — «пропущена». Организации и офисы естественным образом отсеиваются.
7. **Новый бакет `electronic-home-statements`** (закрытый, как остальные) и ключ-UUID; конфигурация `storage.s3.statements-bucket` / `S3_STATEMENTS_BUCKET`. Хранится исходный файл для разбора и повторной обработки; политика хранения — вне объёма.
8. **API и UI**: `POST/GET /api/receipt-batches`, `GET /api/receipt-batches/{id}` только `ADMIN`; карточка на вкладке «Выставить квитанции» (antd `Upload`/`Progress`/`Table`), опрос раз в 2 с, пока пакет не завершён. Размер файла — до 20 МБ (`spring.servlet.multipart` и проверка в сервисе).
9. **Персональные данные**: ведомость, PDF и позиции не пишутся в журналы; ответы API без ФИО, адресов и сумм (см. спецификацию); бакет закрыт, как у квитанций.

## Risks / Trade-offs

- [Бухгалтерия изменит выгрузку, и разбор сломается] → строгая проверка структуры с понятной ошибкой `422`, тест на образце (синтетический файл с тем же устройством блоков, без реальных данных), отчёт по позициям.
- [Большое число объединённых ячеек и 8–9 тыс. строк: память и время POI] → потоковое чтение листа, проверка на реальном файле (5 МБ); PDF формируются по одному и сразу выгружаются.
- [Вид PDF отличается от печатной формы дома] → вёрстка сверена с реальным PDF дома; шрифт отличается (DejaVu вместо Arial), итоговые суммы сверяются тестом с ведомостью.
- [Шрифт без нужных глифов даст пустые квадраты] → тест на кириллицу и спецсимволы, выбор шрифта с полным покрытием.
- [Перезапуск во время обработки] → пакет «ошибка», повторная загрузка безопасна (замена по счёту и месяцу).
- [Повторная загрузка заменяет квитанции, которые уже видят собственники] → ожидаемое поведение для исправленной ведомости; прежние файлы удаляются тем же механизмом, что при ручной замене.
- [Ведомость в S3 содержит персональные данные всего дома] → закрытый бакет, доступ только через приложение, не попадает в журналы; удаление старых ведомостей — вне объёма (открытый вопрос).
