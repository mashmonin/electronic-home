# Электронный дом: эксплуатация и настройка

Веб-сервис передачи показаний ЖКУ. Бэкенд — Java 21 + Spring Boot + Gradle, БД — PostgreSQL,
фронтенд — React + TypeScript + Ant Design, веб-сервер — nginx с SSL. Разработка ведётся через
[OpenSpec](openspec/) (`/opsx:propose` → `/opsx:apply` → `/opsx:archive`).

## Требования

Только **Docker** (с Compose). JDK, Node.js, PostgreSQL и nginx на машине не нужны —
всё собирается и запускается в контейнерах.

## Dev (локальная разработка)

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build
```

- Приложение: https://localhost (самоподписанный сертификат — браузер предупредит, это нормально).
- Фронтенд работает через Vite с HMR: правки в `frontend/` подхватываются без пересборки.
- Бэкенд работает в профиле `dev`; после правок в `backend/`: `... up -d --build backend`.
- PostgreSQL доступен только с localhost: `127.0.0.1:5435` (БД/пользователь/пароль: `electronic_home`).

Остановка и полная очистка (контейнеры, тома, сертификат):

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml down -v
```

## Dev: бэкенд из IDE, фронтенд из терминала, БД в Docker

Для отладки: в Docker только PostgreSQL и хранилище файлов, остальное запускается на хосте (нужны JDK 21 и Node.js 22).

1. БД и хранилище файлов: `docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d postgres s3`
   (S3 API хранилища доступен на `127.0.0.1:8333`, бэкенд подключается к нему по умолчанию)
2. Бэкенд: открыть `backend/` как Gradle-проект в IntelliJ, запустить `ElectronicHomeApplication`
   с переменной окружения `SPRING_PROFILES_ACTIVE=dev` (без профиля приложение не стартует).
   Подключение к БД по умолчанию — `localhost:5435`.
3. Фронтенд: `cd frontend && npm install && npm run dev` → http://localhost:5173
   (запросы `/api` проксируются на `localhost:8080`).

Проверка: на странице должно быть «Сервис работает»; `curl localhost:8080/api/actuator/health` → `UP`.
В этом режиме nginx и HTTPS не участвуют — они проверяются полным dev-окружением выше.

## Prod (промышленная эксплуатация)

1. `cp .env.example .env.prod` и заполнить `DB_USER`, `DB_PASSWORD`, `JWT_SECRET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`
   (значений по умолчанию нет; ключи хранилища — буквы, цифры и `- _ . + = /`, секрет не короче 16 символов).
2. Положить сертификат и ключ в `infra/certs/` как `tls.crt` и `tls.key` (в git не попадают).
3. Запуск:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.prod up -d --build
```

Бэкенд работает в профиле `prod`; порт PostgreSQL наружу не публикуется, бэкенд снаружи недоступен —
весь трафик идёт через nginx (80 → редирект на 443).

## Период передачи показаний

Показания сдаются раз в период. Период идёт с 26-го числа по 25-е включительно и называется по месяцу, в котором
заканчивается (26 сентября — 25 октября — «октябрь»). Период и блокировку определяет бэкенд по своей дате: после
сдачи поле счётчика закрыто до начала следующего периода, повторная отправка отклоняется (`ALREADY_SUBMITTED`).

| Параметр | По умолчанию | Описание |
|---|---|---|
| `readings.period.closing-day` | `25` | Последний день периода (1–28). |
| `readings.period.enforced` | `true` (во всех профилях, включая `dev`) | При `false` повторная подача за период разрешена (для тестирования), экран показывает «Тестовый режим». |

Любой параметр можно переопределить переменной окружения: `READINGS_PERIOD_ENFORCED=false`,
`READINGS_PERIOD_CLOSING_DAY=25`. Чтобы отключить блокировку при тестировании, запустите бэкенд с `READINGS_PERIOD_ENFORCED=false`
(в docker compose — через `environment` сервиса `backend`).

## Хранилище файлов (S3)

Квитанции и вложения чатов хранятся в собственном S3-совместимом хранилище **SeaweedFS** (лицензия Apache 2.0): сервис `s3`
в Docker Compose, данные на томе `s3_data`, образ `chrislusf/seaweedfs:4.48`. Выбран он потому, что бесплатные образы MinIO
больше не выпускаются; бэкенд говорит с хранилищем по S3 API, поэтому движок можно заменить правкой Compose.

- **Доступ.** Только из сети контейнеров: в prod порты не публикуются, nginx хранилище не проксирует; в dev S3 API открыт
  на `127.0.0.1:8333` (для бэкенда из IDE). Анонимный доступ запрещён, ссылок на файлы наружу нет — скачивание только
  через бэкенд с проверкой прав.
- **Ключи.** `S3_ACCESS_KEY` и `S3_SECRET_KEY`: в dev заданы для разработки, в prod обязательны (без них приложение не
  стартует), секрет не короче 16 символов. Остальные параметры: `S3_ENDPOINT` (в Compose `http://s3:8333`), `S3_REGION`,
  `S3_RECEIPTS_BUCKET` (`electronic-home-receipts`), `S3_ATTACHMENTS_BUCKET` (`electronic-home-attachments`),
  `S3_METER_ACTS_BUCKET` (`electronic-home-meter-acts`, акты проверки счётчиков), `S3_STATEMENTS_BUCKET`
  (`electronic-home-statements`, загруженные ведомости начислений). Бакеты создаются сами при первом обращении.
- **Состояние.** Входит в `GET /api/actuator/health` (компонент `objectStorage`); при остановленном хранилище здоровье
  `DOWN`, операции с файлами дают `503`, остальные возможности (показания, текст чатов) работают.
- **Резервное копирование.** Один узел без репликации: сохраняйте том `s3_data` вместе с БД (например, остановив `s3` и
  скопировав том, либо `docker run --rm -v <проект>_s3_data:/data -v $PWD:/backup alpine tar czf /backup/s3.tgz /data`).
- **Ограничения.** Версий объектов, репликации, антивируса и очистки осиротевших объектов нет.

## Квитанции

PDF-квитанции всех квартир лежат в собственном S3-хранилище проекта (бакет квитанций, см. «Хранилище файлов»), а записи о
них — в таблице `receipts` (счёт, месяц, ключ файла, размер, SHA-256). Файл хранится под случайным ключом (UUID), имя от
клиента не используется. Для каждого счёта и месяца — одна квитанция; повторная публикация заменяет файл.

Администратор публикует квитанции из интерфейса: войдите под ролью `ADMIN` (в `dev` — `admin` / `Admin-dev-123`), откройте
единственную вкладку «Выставить квитанции» (пунктов «Показания» и «Квитанции» у администратора нет) и заполните карточку «Опубликовать квитанцию» — обязательно выберите квартиру, затем месяц,
PDF до 5 МБ и, по желанию, обе суммы. Список квартир отдаёт `GET /api/accounts` (только администратору). Если квитанция
этой квартиры за месяц уже есть, перед заменой будет запрос подтверждения.

Для скриптов остаётся публикация по токену (токен — `RECEIPTS_ADMIN_TOKEN`; в `dev` это `dev-admin-token`; без токена и без
входа администратора публикация выключена, `403`):

```bash
curl -X PUT https://localhost/api/accounts/000000000001/receipts/2026-10 \
  -H 'X-Admin-Token: dev-admin-token' -H 'Content-Type: application/pdf' \
  --data-binary @receipt.pdf
```

Суммы квитанции — капитальный ремонт и коммунальные услуги в рублях — пока передаются при публикации необязательными
параметрами `capital_repair` и `utilities` (оба или ни одного, число с точкой, не более двух знаков после запятой):

```bash
curl -X PUT 'https://localhost/api/accounts/000000000001/receipts/2026-10?capital_repair=1842.50&utilities=6318.27' \\
  -H 'X-Admin-Token: dev-admin-token' -H 'Content-Type: application/pdf' --data-binary @receipt.pdf
```

Без параметров суммы не заданы (на вкладке — прочерк); замена файла без параметров сбрасывает прежние суммы. В БД суммы лежат
с источником (`MANUAL`) и временем записи: так их позже заполнит автоматический разбор PDF при загрузке
(источник `PARSED`) — он пока не реализован.

Список и скачивание: `GET /api/accounts/{номер}/receipts` и `GET /api/accounts/{номер}/receipts/{ГГГГ-ММ}`.
На вкладке «Квитанции» месяцы показаны аккордеоном, внутри панели — две суммы и кнопка «Скачать PDF».

| Параметр | По умолчанию | Описание |
|---|---|---|
| `receipts.max-size` (`RECEIPTS_MAX_SIZE`) | `5MB` | Максимальный размер файла; nginx пропускает тело до 6 МБ (`client_max_body_size`), при изменении лимита поправьте и его. |
| `receipts.admin-token` (`RECEIPTS_ADMIN_TOKEN`) | нет (`dev`: `dev-admin-token`) | Токен публикации. |

### Квитанции из ведомости начислений

Администратор на вкладке «Выставить квитанции» в карточке «Загрузить ведомость» выбирает `.xls` ведомость (файл до 20 МБ,
структура как у выгрузки «сентябрь_2026.xls»: по два блока на лицевой счёт, «Жилищно-коммунальные услуги» и «Капитальный
ремонт»). Файл сразу сохраняется в закрытом бакете ведомостей, а в фоне для каждого лицевого счёта формируется PDF (две
страницы A4 альбомные по образцу печатной формы дома) и публикуется как квитанция счёта за расчётный месяц ведомости; суммы берутся из итогов ведомости (источник
`PARSED`), существующая квитанция за месяц заменяется. Счета, которых нет в базе (организации, офисы), пропускаются и
перечисляются в итоге пакета; ошибка одного счёта остальные не останавливает. Ход виден в карточке (опрос раз в 2 секунды).

- API (только `ADMIN`): `POST /api/receipt-batches` (`multipart`, поле `file`, ответ `202`), `GET /api/receipt-batches`,
  `GET /api/receipt-batches/{id}`. В ответах нет ФИО, адресов и сумм.
- Пакет, прерванный перезапуском приложения, получает статус «Ошибка»; повторная загрузка той же ведомости безопасна.
- Ведомость содержит персональные данные всего дома: она лежит только в закрытом бакете и не пишется в журналы.
  Срок хранения старых ведомостей не ограничен (удаляйте вручную при необходимости).
- Разбор — Apache POI (`.xls`), PDF — OpenPDF со встроенным шрифтом DejaVu Sans Condensed (лицензия в `src/main/resources/fonts`).

**Резервное копирование.** Том `s3_data` (хранилище) и БД нужно сохранять вместе: запись без файла отдаёт `404` и ошибку в
журнале. **Доступ.** Список и скачивание доступны администратору и собственнику своего счёта (см. «Вход и роли»);
публикация — администратору по входу или любому, кто знает `RECEIPTS_ADMIN_TOKEN`.

## Вход и роли

Вход по логину и паролю: `POST /api/auth/login` возвращает JWT (`Authorization: Bearer ...`), `GET /api/auth/me` — логин, роль и номера доступных счетов. Токен живёт 8 часов (`auth.jwt.ttl`), на фронтенде хранится в `sessionStorage` вкладки.

Роли и полномочия:

| Действие | ADMIN | OWNER | RESIDENT |
|---|---|---|---|
| Просмотр счёта, подача показаний | любой счёт | свои счета | свои счета |
| Список и скачивание квитанций | любой счёт | свои счета | запрещено |

«Свои счета» — строки таблицы `user_accounts`. Публикация квитанций по-прежнему идёт по `X-Admin-Token` без JWT.

Тестовые учётные записи есть только в `dev`: `owner` / `Owner-dev-123` (роль `OWNER`, счёт `000000000001`) и `admin` / `Admin-dev-123` (роль `ADMIN`, видит все счета). Если вы уже создали `admin` вручную, миграция его не трогает.

Секрет подписи токенов — `JWT_SECRET` (не короче 32 байт). В `dev` задан по умолчанию, в `prod` обязателен: без него приложение не стартует (`docker-compose.prod.yml` тоже требует переменную).

В `prod` пользователей по умолчанию нет. Первые записи создаются вручную (хэш — BCrypt, например `htpasswd -nbBC 10 x 'пароль' | cut -d: -f2`):

```sql
INSERT INTO users (login, password_hash, role) VALUES ('admin', '$2a$10$...', 'ADMIN');
-- OWNER и RESIDENT нужно привязать к счёту:
INSERT INTO user_accounts (user_id, account_id)
SELECT u.id, a.id FROM users u, accounts a WHERE u.login = 'ivanov' AND a.number = '000000000001';
```

Собственников, лицевые счета и логины из ведомости начислений загружает отдельный скрипт, см. [`tools/owners-import/README.md`](tools/owners-import/README.md): персональные данные и пароли остаются вне git.

## Заявки

Заявки — это чаты. Вкладка «Заявки» есть у собственника и администратора (у жильца её нет). Слева список заявок, справа
чат выбранной (на узком экране по одному). Собственник видит только свои заявки, создаёт новую кнопкой «Новая заявка»
(одно первое сообщение, темы нет) и пишет в свои заявки. Администратор видит все заявки с квартирой и логином
автора, сам выбирает любую для чтения и отвечает. Заявки не закрываются и не открываются: у заявки только номер и
переписка. Чужая заявка для собственника неотличима от несуществующей (`404`).

**Порядок и выделение.** Сверху всегда заявки без ответа — те, чьё последнее сообщение написал собственник: чем дольше
заявка ждёт (с первого сообщения после последнего ответа администратора), тем она выше. Дописка собственника ожидание не
сбрасывает. Ниже идут отвеченные заявки по времени последнего сообщения, новые выше. Заявка без ответа выделена цветом,
полосой слева и меткой «Ждёт ответа»; после ответа администратора выделение пропадает, а после нового вопроса возвращается.

**Поиск.** Над списком поле «Поиск по номеру заявки»: совпадение с любой частью номера (`1910`, `0002`, `191026-00`),
регистр не важен, латинская `O` равна кириллической `О`. Запрос уходит на сервер (`GET /api/requests?q=...`) через 300 мс
после последнего нажатия; порядок найденных заявок тот же. Открытый чат при поиске не закрывается.

Номер заявки присваивается сервером и служит её названием: `О-ддммгг-NNNN`, например `О-191026-0001` (`О` — «обращение»,
дата создания, сквозной порядковый номер: он не обнуляется на следующий день). Порядковая часть берётся из
последовательности `request_number_seq`; если создание заявки не удалось, в нумерации может остаться пропуск, но номер
не повторяется.

**Вложения.** К сообщению (и к первому сообщению новой заявки) можно прикрепить до 5 файлов: каждый до 10 МБ, всего до
25 МБ; допустимы JPEG, PNG, GIF, WebP, PDF, DOC, DOCX, XLS, XLSX и TXT. Тип определяется по расширению и подтверждается
содержимым (SVG, HTML и исполняемые файлы не принимаются), тип от клиента игнорируется. Сообщение может состоять из одних
файлов; в списке заявок оно показано как «Вложение: имя» или «Вложений: N». Файлы нельзя изменить или удалить. Скачивание —
`GET /api/requests/{id}/attachments/{attachmentId}` (автор заявки и администратор). Запросы с файлами идут как
`multipart/form-data` (`text`, `files`, `account_number`), через nginx на `/api/requests` проходит тело до 30 МБ. Имя файла
в заголовке формы сервер читает примерно до 500 байт, поэтому очень длинные имена (сотни символов) не принимаются.

Чат обновляется опросом: список раз в 15 секунд, открытый чат раз в 5 (запросом `?after=<последний id>`), пока вкладка
открыта и страница видна. API: `GET/POST /api/requests`, `GET /api/requests/{id}`,
`GET/POST /api/requests/{id}/messages`. Лимиты: сообщение до 2000 символов, в списке до 200 заявок, в чате
до 500 последних сообщений. В `dev` есть тестовая заявка собственника `owner` (с номером) с ответом `admin`.

## Тесты (тоже в контейнерах)

```bash
# backend (Testcontainers использует docker.sock)
docker run --rm -v "$PWD/backend":/app -w /app -v eh-gradle-cache:/home/gradle/.gradle \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -e TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal -e TESTCONTAINERS_RYUK_DISABLED=true \
  gradle:9.5.1-jdk21 gradle test --no-daemon

# frontend
docker run --rm -v "$PWD/frontend":/app -w /app -v eh-npm-cache:/root/.npm \
  node:22-alpine sh -c 'npm ci && npm test'
```
